# `@allow` on a Test Block — Design Rationale

### Panel Deliberation

Six panelists (systems, web/scripting, PLT, DevOps/tooling, AI/ML, minimalism) deliberated
in independent-proposal → debate → vote rounds. The question: the §11.1 `@allow` row listed `fn, type`, and rule 2 makes any other target `UnexpectedAnnotation` (E1110). gen1 accepted `@allow` on a test block and did nothing: the warning still printed, and a bad name gave no E0842 or E0847. The §2.20 `TodoInCode` sentence told users to write `@allow(TodoInCode)` in a test. Does `@allow` on a test block suppress the warnings in its body, or is it E1110?

Phase A ran, then Phase B (one round), then a Phase C silent ballot, then a Phase D round on Q2 and Q3 only.

#### Phase A — Independent proposals

Excerpts follow, each with its seat. "…" marks a cut.

- **Systems:** "`@allow(...)` on a `test` block suppresses the named warnings in the whole test body. A test body is a function body that lowers to a C function, so the diagnostic pass treats it as a `fn` scope. Scope is lexical, the same as for `fn`: the body, closures written in it, and nested `assert_panics` blocks. It does not reach helper functions the test calls (those need their own `@allow`)." … "Hardware view: zero runtime cost. `@allow` is compile-time only, and tests are stripped from release builds." Fallback (sys-2): "Rule 2 stays. §11.1 gains one sentence: \"`@allow` on a test block is E1110; use `[lints]` for the package or move the code into a `fn` with `@allow`.\"" Other annotations: "Limit the decision to `@allow`."
- **Web/Scripting:** "A test is a function body that the runner calls. A JS or Python developer who writes `@allow(X)` above `test \"t\" { ... }` expects the warning to go away. Today the compiler accepts the annotation and prints the warning anyway (r1, r8). That is the silent failure that `decisions/annotation-list.md` calls the worst result a diagnostic can give." … "Nobody should have to restructure a test to quiet a warning." Proposed row text: "On a test block it suppresses the named warnings in the whole body, including closures written in it and the body of an `assert_panics` block." Proposed one line in §2.20 *Syntax*: "`@allow` is valid on a test block (§11.1)." "Limit to `@allow`."
- **PLT:** "§4.16.8 already defines `@allow` by scope: the warnings inside the annotated body. The rule for the target set is \"every body-bearing declaration.\"" … "`@allow(N...)` on a declaration `d` removes every warning named in `N` whose source span lies inside `d`'s body. Scope is a property of source spans, not of the call graph or the runtime." … "suppression only removes diagnostics; it adds no run-time behavior and changes no types, so it is sound by construction." Cost: "the test target must be implemented in the warning-suppression pass, which today keys on `fn` and `type` spans." "I reject \"silent accept\" outright: it is the failure annotation-list fixed."
- **DevOps:** "A test body is a function body. Warnings fire in it (W0703 says \"test blocks included\"; W0706, W0707, W0708 and W1011 can fire). The only other tool is `[lints]`, which is package-wide. That is too wide: a user who wants `x == -0.0` in one test, to prove the warning's own subject, must turn the lint off for the whole package." … "E0842 and E0847 apply with no change: the argument check does not depend on the target." Proposed that the §2.20 W0703 sentence read "…on the test or on the enclosing function…"; the seat withdrew this in Phase B.
- **AI/ML:** "A test block is a function body (§2.20: it sees module items, has an effect row, is a peer of `fn`). `@allow` on it suppresses the named warnings in the whole body. That includes closures written in the body and nested `assert_panics` blocks." … "An LLM that knows Rust `#[allow]` on a `#[test]` fn, or `@SuppressWarnings` on a JUnit method, will write `@allow` on a test first. The spec already tells it to do so for W0703. If we say E1110, the model must learn an exception to \"a test is a function\"." Proposed row sentence: "On a test block it suppresses the named warnings in the test body." Fallback (aiml-2): keep E1110 and make the help name `[lints]`, a helper `fn` and `@skip("reason")`.
- **Minimalism:** "min-1 (recommended): keep E1110. `@allow` has no `test` target. Add one sentence. Fix the impl." "The spec already decides this. The §11.1 `@allow` row lists \"fn, type\". Rule 2 makes any other target E1110." Proposed row sentence: "A `test` block is not a target; `@allow` on one is E1110. Move the code to a helper `fn`, or set the level under `[lints]`." "Adding the target would force 4 new answers: body only? closures? nested `assert_panics`? Does `@allow` on a test override `[lints]`? Each is new spec text and new tests." Fallback (min-2): "add `test` to the `@allow` row … I vote against it."

All six seats: today's accept-and-ignore is wrong under every option.

#### Phase B — Debate highlights

One round. Excerpts, attributed. The digest listed two options: O1 add `test block` as an `@allow` target, O2 keep E1110 and state it.

- **Minimalism moved to O1 (position change):** "**Position change: I now back O1 (add `test block` as an `@allow` target), with the shortest text.** O2 stays on the ballot as the fallback." "My min-1 argument was \"no new answers\". The other five files show that O1 adds none. The scope is lexical, which is the `fn` rule already in §4.16.8. A test is the only body-bearing declaration with no local waiver. The `TodoInCode` sentence tells users to write `@allow(TodoInCode)` in a test. O1 makes that sentence true."
- **PLT on the "a test is not a `fn`" point:** "The question is what the target set should be, and the spec gives a rule for it: §4.16.8 defines `@allow` by the span of the annotated body. A test block has a body and a span. Excluding it needs a reason beyond \"the row does not list it today\", and the reason offered (\"a test is not a `fn`\") does not matter: the suppression rule does not use the syntactic kind of the declaration, only its span."
- **DevOps on the helper-`fn` escape:** "Its \"helper `fn`\" escape does not cover every case: W0703 fires on the `todo()` call, and W1011 fires on a local binding. A helper moves the code out of the test, and the test no longer shows what it checks."
- **AI/ML conceded the wording (position change):** "I wrote \"a test is a function body\". The facts say no sections/ text calls a test a `fn`, and §11.1 already uses \"test block\" as its own target sort. I drop that wording. The real argument is narrower: §4.16.8 defines `@allow` by the scope of a body, and a test has a body."
- **Systems conceded the same point (position change):** "I drop my claim that the diagnostic pass treats a test as a `fn` scope; that is an implementation fact, not spec."
- **DevOps withdrew the `TodoInCode` rewrite (position change):** "I withdraw my change. \"On the enclosing function\" is wrong: a test has no enclosing function. Keep the sentence as written. It becomes true under O1." Web, Systems, PLT, AI/ML and Minimalism each rejected the rewrite for the same reason.
- **Minimalism on the row text (open at the end of Phase B):** "Do not list closures and `assert_panics` blocks (sys-1, web-1, plt-1, devops-1). \"Body\" already includes them, and a list invites the question of what else is not listed. If the panel wants the list, I do not oppose it."
- **DevOps, AI/ML, PLT, Systems, Web (the row text):** these five held a text that names closures and `assert_panics` blocks. Web: "aiml-1's short form leaves the question open; reject it."
- **§2.20 line (split):** Web: "Yes, add the one line to §2.20 *Syntax*: \"`@allow` is valid on a test block (§11.1).\"" DevOps and Systems held it as optional. PLT: "Oppose the extra §2.20 line. §11.1 is the one table (annotation-list). A second statement of a target in §2.20 can drift from it. §2.20 *Syntax* names no other annotation's targets." Minimalism and AI/ML preferred no line.
- **Agreed (no ballot):** target list "`fn, type, test block`" (DevOps: "I withdraw my order and take \"`fn, type, test block`\""); §4.16.8 "inside the annotated function or test block"; the answer limited to `@allow`.

#### Phase C — Final vote

Votes are verbatim from each seat's ballot file.

- **Q1: The rule.** A: add `test block` as an `@allow` target, lexical scope. B: keep E1110 for `@allow` on a test block and state it in words. **6-0 for A.**
  - **Systems:** A — "`@allow` is a compile-time scope rule with no run-time or codegen cost, and tests are stripped from release builds. The suppression rule keys on a source span, so a test body fits it with one more scope push in the lint pass. O2 leaves a test with only package-wide `[lints]` or a helper `fn`, which pushes users to weaken lints for production code." Concern: "a broad `@allow` on a long test body can hide a real defect in a line the author did not mean to cover."
  - **Web/Scripting:** A — "A JS or Python developer who sees W0703 or W0706 in a test writes `@allow` on the test first, and the §2.20 `TodoInCode` sentence tells them to. Rust, pytest and eslint all give a per-test waiver. O1 makes that existing sentence true, costs one word in one row, and gives a local waiver. O2 leaves only a helper `fn` that changes the shape of the test, or a package-wide `[lints]` change." Concern: "A broad `@allow` on a long test body can hide a real warning, but `fn` already has that risk and the helper `fn` stays available."
  - **PLT:** A — "§4.16.8 defines `@allow` by the source span of the annotated body, not by the syntactic kind of the declaration. A test block has a body and a span, so listing it as a target adds no new rule. Suppression only removes diagnostics, so it is sound by construction and composes by span containment. It also makes the §2.20 `TodoInCode` sentence true without a rewrite." Concern: "The test target must be implemented in the suppression pass, which keys on `fn` and `type` spans today. A pass that handles only the `fn` span will keep accepting `@allow` on a test and doing nothing, which is the failure annotation-list fixed."
  - **DevOps:** A — "A test body gets warnings (W0703, W0706, W0707, W0708, W1011 on a local), and `[lints]` is the only other control. It is package-wide, so a user who needs one waiver weakens the check for production code. A helper `fn` cannot carry W0703 on `todo()` or W1011 on a local without moving code out of the test. One lexical rule for `fn` and test gives the LSP suppress-warning action a single rule, and it makes the §2.20 `TodoInCode` advice true." Concern: "If the winning text is thin on scope, the suppression pass may handle closures and `assert_panics` blocks differently from `fn`, and the user sees a warning that the annotation should have silenced."
  - **AI/ML:** A — "One rule (\"`@allow` suppresses warnings in the lexical span of the annotated body\") is easier for a model to learn from the spec alone than a target table plus a test-block exception. The §2.20 `TodoInCode` sentence already tells a model to write `@allow(TodoInCode)` in a test, so A makes the spec consistent and adds no decision point. B sends the model to a helper `fn` that exists only to carry an annotation." Concern: "Silent acceptance may stay in the compiler (r1, r3, r4, r8), so the spec says \"valid\" while the warning still prints; the impl must land with a test for it."
  - **Minimalism:** A — "The scope rule is the one §4.16.8 already uses for `fn`: the span of the annotated body. So the target adds no new rule. It removes an exception, and it makes the §2.20 `TodoInCode` sentence true without a rewrite. O2 would add a sentence that states an exception and would force that rewrite. A test is the only body with no local waiver, and the alternative pushes users to weaken `[lints]` for the whole package." Concern: "A broad `@allow` on a long test body hides warnings on lines that did not need it, and the row text invites copying it onto every test."

- **Q2: The sentence added to the §11.1 `@allow` row.** **2-1-1-1-1 in Phase C** (E, A, B, C, D); settled in Phase D. Options:
  - A: "On a test block it suppresses the named warnings in the test body."

  - **Systems:** B — "The sentence must name closures and `assert_panics` blocks, so the reader does not infer scope. B is the shortest text that does so. B, D and E carry the same meaning; I take B and accept any of them." Concern: "a list of named constructs invites the question of what an unlisted construct (a future block form) does."
  - **Web/Scripting:** C — "The reader should not have to infer scope. Text C names closures and the `assert_panics` body, which are the two places a user wonders about. Text A leaves scope open. Texts B, D and E differ from C only in wording." Concern: "Naming closures and `assert_panics` invites a question about other nested forms (for example `assert_matches`), so the list must stay true as test forms grow."
  - **PLT:** D — "Scope must be stated, not inferred, and span containment gives one exact rule. \"Including closures and `assert_panics` blocks written in it\" names the two nested forms and ties them to the test with \"written in it\". It does not say \"operands\", which was imprecise. Text A leaves the scope open, and B omits \"written in it\"." Concern: "Any listed form invites the question of which other nested forms are excluded; the answer must stay \"none inside the span\"."
  - **DevOps:** E — "The text names closures and `assert_panics` blocks, so a reader and a tool author do not infer scope. The word \"whole\" matches the lexical-span rule. \"Written in it\" says plainly that suppression does not follow calls into a helper `fn`." Concern: "A long list invites the question of which other block forms are not listed; the test must cover every nested form so the list is not a partial one."
  - **AI/ML:** E — "A model should not have to infer scope. Text E names closures and `assert_panics` blocks and uses \"whole body\", with no extra clause. Concern: "A listed scope invites the question of what else is not listed (min's point); the \"written in it\" wording limits that, but a future body-bearing form needs a spec edit."
  - **Minimalism:** A — "\"Body\" already includes closures and `assert_panics` blocks under lexical span, as it does for `fn`. A list of what is included makes the reader ask what is not listed. The row stays short and does not repeat the `fn` rule." Concern: "If the longer text wins, a later scope (for example a nested `test` helper form) must be added to a list that can drift."

- **Q3: A line in §2.20 *Syntax*.** **4-2 in Phase C** (B, A); settled in Phase D. A: add "`@allow` is valid on a test block (§11.1)." B: no §2.20 line; the §11.1 row is the single source.

  - **Web/Scripting:** A — "A developer reading §2.20 to learn about tests sees the rule where tests live. It is one line and costs nothing to read." Concern: "The line is a second statement of the target and can drift from the §11.1 row."
  - **PLT:** B — "§11.1 is the one closed table (annotation-list). A second statement of a target in §2.20 can drift from the row, and §2.20 states no other annotation's targets. The row is the single source." Concern: "A reader who starts in §2.20 may not learn that `@allow` is valid on a test block, though the `TodoInCode` sentence there already names it."
  - **DevOps:** A — "A reader who starts in §2.20 sees the rule where tests live, and the LSP hover text can link to either place. The line is cheap. I accept B if the panel wants §11.1 as the sole source." Concern: "A second statement of a target can drift from the §11.1 row."
  - **AI/ML:** B — "The §11.1 row is the single source for targets (annotation-list). A second statement in §2.20 can drift, and a model reading §2.20 gains nothing it does not get from the row. I do not oppose A." Concern: "A reader who starts in §2.20 sees no sign that a test block takes `@allow` (only the `TodoInCode` sentence implies it)."
  - **Minimalism:** B — "§11.1 is the one table of targets (annotation-list), and §2.20 *Syntax* names no other annotation's targets. A second statement can drift from the row.
