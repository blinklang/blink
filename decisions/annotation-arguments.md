# Annotation Arguments That Do Not Match a Row's Form — Design Rationale

§11.1 is the one normative annotation table. Rules 1 to 3 cover the name, the target and the repeat. No rule said what happens when the arguments of an annotation do not match the form that the row's Annotation column writes. gen1 accepted `@handle_all(B)`, `@pure(x)`, a bare `@requires`, a bare `@derive` and `@ffi("c", "abs", "extra")` with no annotation diagnostic. `@skip(1, 2)` gave a raw `UnexpectedToken`. The duplicate half of the question (a second `@handle_all`) was already decided: rule 3 makes it `DuplicateAnnotation`, and this ruling does not reopen it.

### Panel Deliberation

Six panelists (systems, web/scripting, PLT, DevOps/tooling, AI/ML, minimalism) deliberated in independent-proposal → debate → vote rounds. Quotes below are the panelists' own text. Where a Phase A or Phase B text is long, the quote is an excerpt, marked with attribution.

#### Phase A — Independent proposals

- **Systems (sys-1, excerpt):** "**Rule.** Each §11.1 row's Annotation column is the full argument grammar of that row. Arguments that do not fit it are an error, never a warning, never accepted." "**Code.** One new code, `AnnotationArgumentMismatch`, in the E11xx range next to E1110. One diagnostic keeps the family small: the message always has the same shape, the help always prints the row's form from the table." "The parser must no longer leak `UnexpectedToken` for an annotation. It parses the argument list loosely (any `(...)`), and one checker pass compares it with the row's form."
- **Web/Scripting (web-1, excerpt):** "**Rule 4 (Arguments).** The Annotation column of a row gives the only legal form. An occurrence that does not match it is the error `AnnotationArgs`. It is always an error, never a warning, and the compiler never accepts it silently." "Existing per-row codes stay and win. ... `@trusted` with no `audit:` stays E0836; `@trusted(why: "x")` is `AnnotationArgs` (unknown key), because the key is not in the row." "The help always prints the row's form from §11.1. A near-miss key gets "did you mean `audit`"."
- **PLT (plt-1, excerpt):** "An annotation argument that does not match its row's form is an error. Never a warning, never accepted. One new diagnostic for the family, `AnnotationArgs` ... It is the argument-shape twin of rules 1-3 (name, target, repeats)." "Each row's form is a signature: `@skip : () | (Str)`, `@ffi : (Str, Str)`, `@derive : (Trait, ...)`, `@trusted : (audit: Str)`. A call that does not fit the signature is ill-formed." "Where a row has a specific code for a shape failure, that code wins and `AnnotationArgs` does not fire. ... One diagnostic per annotation, never two." "A shape failure marks the annotation invalid. The checker for its claim does not run, so no second error appears. The declaration is still checked."
- **DevOps (devops-1, excerpt):** "Shape (count, kind, key names, presence) = `AnnotationArgumentMismatch`, a new E11xx parser code next to E1110. It runs before any name or scope lookup. Value meaning (is `Foo` a derivable trait, is the audit ID in the audit file, is `Foo` a warning name) = the existing per-row codes." "**Parser, not typecheck.** ... The annotation parser must catch a bad argument list per row and report `AnnotationArgumentMismatch` with the span of the bad arguments. Raw `UnexpectedToken` must never leak from inside an annotation." "**Recovery.** Skip to the closing `)`, keep the declaration, so later errors in the file still show." "`@deprecated(since, removal, replacement, fix)` needs the grammar to allow named keys in any order and say which are optional. The table must say that, or the check cannot test it."
- **AI/ML (aiml-1, excerpt):** "4. **Arguments.** The Annotation column of a row gives the only form that row accepts. Arguments that do not match that form are `AnnotationArguments` (E1111). This covers: arguments on a row written without parentheses, no arguments on a row that needs them, the wrong count, the wrong kind, and a named key the row does not list. It is an error, never a warning." "The help line always prints the row's form from the table, verbatim. One shape, so a model that reads the error can fix the code with no other lookup." "Silent acceptance is worse for AI-written code: the model sees a green build and stops."
- **Minimalism (min-1, excerpt):** "Add one line to *Rules for Every Annotation*. Add no new syntax and no new code per row." "Why one rule: the table already holds the grammar. Rules 1 to 3 cover the name, the target and the repeat. The argument is the one part with no rule." "Not "accepted". Accepting `@handle_all(B)` makes users think the argument selects something. Later we cannot give it a meaning without a breaking change." "No mainstream compiled language accepts them silently." min-2, "do nothing, leave to per-row codes": "rejected by me; listed for the record."

All six seats put the family error (Option 1) first. sys-2, aiml-2 and min-2 listed per-row codes only as a fallback and opposed it. devops listed it under "Reject alternatives".

Points all six B1 replies stated (not put to the vote):

- Option 1: a new §11.1 rule 4. Arguments that do not match the row's form are one family error, never a warning, never accepted.
- The parser reads any annotation argument list in one general form; one check after the parse compares it with the row's table data. The check runs before any name or scope lookup. A list that does not parse at all recovers at the closing `)`.
- One diagnostic per annotation. A row's own code wins for the exact failure it names (bare `@trusted` stays E0836; `@derive(Foo)` stays E1402). An unknown key, such as `@trusted(why: "x")`, is the family error.
- A shape failure marks the annotation invalid; its claim checker does not run; the rest of the declaration is still checked.
- The help prints the row's form. A near-miss key gets a "did you mean" hint.
- LSP quick fix: "remove arguments" only on a row that takes none. No other automatic fix.
- `blink fmt` leaves a mismatched annotation as written and does not report the check error.

#### Phase C — Final vote

Silent ballot. Each seat read the brief, the Phase B digest and all Phase A and B1 texts. Reasoning and concern are each seat's own text.

- **Q1: The name of the family code.** Option A `AnnotationArguments`; Option B `AnnotationArgumentMismatch` (**6-0 for A**)
  - **Systems:** A — "The catalog spells diagnostic names in full words (`UnexpectedAnnotation`, `DuplicateAnnotation`), and five seats already use this form. The name has no run-time or codegen effect, so the cheapest choice is the one that matches the neighbours." Concern: "The name says where the error is but not what is wrong, so the message text must carry that detail every time."
  - **Web/Scripting:** A — "A dev reads the name in the error line and types it into a search box. `AnnotationArguments` reads clear with no guess, and it matches the full-word names of rules 1 to 3 (`UnknownAnnotation`, `DuplicateAnnotation`). `AnnotationArgumentMismatch` adds length and no meaning once the message says what is wrong. Five seats already chose A." Concern: "A noun-only name does not say "error" or "wrong", so a new user may read `AnnotationArguments` as a topic and not as a failure; the message text must carry the fault."
  - **PLT:** A — "Rules 1-3 use full-word names (`UnknownAnnotation`, `UnexpectedAnnotation`, `DuplicateAnnotation`), and the family code should read the same way. "Mismatch" adds no information: every error in this family is a mismatch of the arguments against the row's form. Five seats chose A, and the name has no effect on soundness." Concern: "A noun phrase for the code does not say that the form failed to match, so the message line must carry the "takes no arguments / found 3" text to make up for it."
  - **DevOps:** A — "The user reads this name in the error line and in `blink explain`, and `AnnotationArguments` is a plain full-word noun phrase that matches `UnknownAnnotation` and `DuplicateAnnotation`. The message text ("`@ffi` takes 2 arguments, found 3") already says what went wrong, so the code name does not need "Mismatch". I said in B1 that I would not block on this, and five seats chose this name." Concern: "A noun-only name does not say "error", so a reader who sees only the code name in a grep or a log may take it for a note about arguments, not a failure."
  - **AI/ML:** A — "The name is a plain full-word noun phrase, like `UnknownAnnotation` and `DuplicateAnnotation`, so a model that learns rules 1-3 can guess rule 4's name. Five of six seats chose it. The message text, not the code name, says what went wrong." Concern: "Without "Mismatch" in the name, a reader may not see at once that the code is for a bad form, so the first line of the message must say it."
  - **Minimalism:** A — "The catalog spells names in full words (`UnexpectedAnnotation`, `DuplicateAnnotation`, `UnknownAnnotation`), and `AnnotationArguments` follows that with no extra letters. Concern: "If B wins, the catalog gets a second naming style (a "Mismatch" suffix on one code) that every later family code must either copy or break."

- **Q2: The diagnostic span.** Option A the bad argument, or the argument list when the count is wrong, or the annotation name when no list exists; Option B the whole annotation (**6-0 for A**)
  - **Systems:** A — "The span is data the checker already has, because the general parse keeps a source range for every argument. A narrow span shows which of three strings in `@ffi("c", "abs", "extra")` is the surplus one. The help line already prints the form of the whole annotation, so a whole-annotation span adds nothing." Concern: "For a wrong-kind or wrong-count error the checker must pick between the argument and the list, and a bad pick gives a misleading underline."
  - **Web/Scripting:** A — "A dev reading `@ffi("c", "abs", "extra")` must see which string is wrong. A whole-annotation span points at too much and hides that. The help already prints the form of the whole annotation, so the span does not need to repeat it." Concern: "For a count error the span is the whole list, so the user still has to count; the message must say "takes 2 arguments, found 3"."
  - **PLT:** A — "The row's form is a signature, and an arity or kind error belongs at the argument that breaks it, as in any type checker. Under `@ffi("c", "abs", "extra")` the reader must see which of three strings is the surplus one. The help line already prints the whole form, so a whole-annotation span adds no information." Concern: "The compiler needs a span for each argument in the general parse; if it keeps only the list span, "the bad argument" silently degrades to "the list"."
  - **DevOps:** A — "The LSP squiggle and the terminal underline should sit on the part the user must change. With `@ffi("c", "abs", "extra")` a whole-annotation span hides which of three strings is wrong, and the form in the help line already covers the whole annotation. Five seats chose this span." Concern: "For a wrong kind inside a variadic list (`@allow(Foo, 1)`) the compiler must pick one bad argument and mark it, and a second bad argument stays hidden until the user fixes the first."
  - **AI/ML:** A — "I change from my Phase A position. The help line already prints the whole form, so the span does not need to cover the whole annotation. A span on the third string of `@ffi("c", "abs", "extra")` tells the model which part to fix. Five of six seats agree, and the rule is easy to state." Concern: "The model must choose between "argument" and "list" spans, so the spec must say exactly which kind of failure gets which span."
  - **Minimalism:** A — "The error is in the arguments, and the annotation name is correct. Concern: "If B wins, the span points at text that is correct and the user must find the fault alone, so the compiler needs no extra rules but the reader does more work."

- **Q3: Negative tests that the ci table check requires.** Option A for each row that can fail, one negative test per mismatch kind that row can have, and the ci check lists the missing pairs; Option B one negative test per row, and the ci check fails a row with no negative test; Option C the spec names no test count and the ci project decides (**3-2-1 in Phase C: A 3, B 2, C 1; no majority, so Phase D re-voted**)
  - **Systems:** B — "The check code is shared, so one failing case per row proves the compiler enforces the row's form and the table data matches. A per-kind matrix asks for tests that cannot exist on some rows (a no-argument row has one kind of failure). The spec should state a floor that the check can verify, not leave it to the ci project." Concern: "One test per row can cover only the likeliest kind, so a rare kind (for example an unknown key on `@verify`) can regress with no test failing."
  - **Web/Scripting:** A — "The family error is only real if the compiler enforces it per row. A data-vs-text compare cannot prove that. Concern: "Every new row adds test files, and a contributor who adds an annotation may feel the check is a tax on a small change."
  - **PLT:** A — "A check that compares only the table data with the §11.1 text proves that the data and the text agree. It does not prove that the compiler enforces the grammar. A pair of (row, mismatch kind) is the smallest unit that covers every branch of the shared checker. Concern: "Rows with a wide grammar (`@deprecated`, `@verify`) produce many pairs, and a team may start to treat the pair list as busywork instead of as the coverage check it is."
  - **DevOps:** B — "The check code is shared by every row, so a test per mismatch kind per row adds many files and little new coverage. **Fact found after the Q4 vote (not re-voted).** The panel voted as if the `@deprecated` row did not say which keys are optional. It does. The §11.1 row and §8.16.2 (sections/06_tooling.md, the *Fields* table) already mark `since` required and `removal`, `replacement` and `fix` optional. The moderator found this after the vote and did not re-run it. What was missing is the statement that key order is free. The edit that Q4 A asks for is therefore small: the row says that key order is free and keeps the optional marks visible next to the form. This change does not change which keys are required.

The ci check reads table data and tests that exist; it already fails a row the compiler does not enforce at review time, and the ci project can raise the floor for a wide row such as `@verify` or `@deprecated` when it sees a gap. A hard (row, kind) matrix needs new machinery in the check to derive kinds from table data, and every new annotation grows it. If the panel writes a floor anyway, my second choice is B, with the floor stated in the decision file and the ticket only, not in sections/." Concern: "If A wins, the ci check must derive mismatch kinds from table data, and that derivation can become the part of the check that is wrong or stale while every row looks covered."

### The Q3 requirement on the ci table check

This requirement binds the ci table check and its implementation ticket. It is not spec text. `sections/` states no test count and says nothing about the ci check.

For each annotation row that can fail, the repo must hold one negative test for each mismatch kind that row can have. The ci check lists each (row, kind) pair that has no test.

- The mismatch kinds are: arguments on a row that takes none, no arguments on a row that needs them, the wrong count, the wrong kind, and an unknown key.
- The kinds a row can have come from that row's table data. A row that takes no arguments has one kind. A row with no named keys has no unknown-key kind. The check never asks for a test that cannot exist.
- One test file may hold all the cases of a row. The check counts cases, not files. Each test file name stays unique.
- aiml's concern: the check verifies that each test fails with `AnnotationArguments` for its stated kind, so that a shallow test cannot clear the list.
- devops and plt's concern: the derivation of kinds from table data must be right. A wrong derivation asks for a test that cannot fail, or skips a kind that can, and the pair list loses trust.
- A later ruling can change this requirement. A spec edit is not needed.

### Final Spec

```blink
@handle_all(B)                  // AnnotationArguments: the row takes no arguments
effect C { effect D { fn y() -> Int } }

@requires                       // AnnotationArguments: the row needs an expression
fn g(n: Int) -> Int { n }

@ffi("c", "abs", "extra")       // AnnotationArguments: the form is @ffi("lib", "sym")
fn abs_c(n: Int) -> Int

@skip(1, 2)                     // AnnotationArguments: the form is @skip or @skip("reason")
test "slow case" { }

@trusted(why: "x")              // AnnotationArguments: the only key is audit
fn h() -> Int { 1 }

@trusted                        // TrustedRequiresAudit (E0836): the row's own code wins
fn k() -> Int { 1 }
```

- §11.1 rule 4: arguments that do not match the form of the row's Annotation column are `AnnotationArguments` (E1134), an error, never a warning, never accepted (Option 1, 6-0).
- The compiler reads any argument list in one general form and compares it with the row, before any name or scope lookup. A list that does not parse at all recovers at the closing `)`.
- One diagnostic per annotation. A row's own code wins for the exact failure it names (E0836, E1402, E0842, E0847, E0913). An unknown key is `AnnotationArguments`.
- A mismatch makes the annotation invalid: its claim is not checked, and the rest of the declaration is.
- The span is the bad argument (Q2). For too many arguments it is the first extra argument; for too few it is the argument list; with no list it is the annotation name. The help prints the row's form, and a near-miss key gets a "did you mean" hint.
- The language server offers "remove arguments" on a row that takes none, and no other automatic fix. `blink fmt` leaves the annotation as written and does not report this error.
- The `@deprecated` row says that key order is free and keeps the optional marks next to the form (Q4). Which keys are required does not change.
- The Q3 test requirement is on the ci table check only.
- A second `@handle_all` stays `DuplicateAnnotation` (rule 3).
- Open: `UnknownAnnotation`, `AnnotationNotSupported` and `DuplicateAnnotation` have no ERROR_CATALOG row. This change does not add them.
