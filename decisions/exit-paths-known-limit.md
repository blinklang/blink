# Exit Paths in a Save/Restore Pair (W0550, W0551 Known Limit) — Design Rationale

**Resolution:** Neither an exit-path warning nor a construct that restores on every exit. Only the "Exit paths" bullet of §4.16.7 Known limits changes. It keeps its two sentences (a `?` or an early `return` between the assignment and the restore leaves the bound value in `G`; neither W0550 nor W0551 looks at exit paths, so a pair that misses its restore on such an exit gives no warning) and adds two: an exit can keep the new value on purpose, for example a parser that keeps its cursor after a successful lookahead, so text alone cannot tell it from a leak; and to restore on every exit, save and restore in a wrapper function that calls the body, or write the restore before each exit. The spec text has no counts and no "by design". No new code, no change to W0550, W0551, `@allow` or `with`, no code change.

**Vote:** Q1 A 6-0. Q2 C 4-2 after Phase D (Phase C 3-3; AI/ML moved D to C; PLT and Minimalism dissent). Q3 B 6-0 after Phase D (Phase C 4-1-1; AI/ML moved A to B, Web/Scripting moved C to B). Q4 A 5-1 (AI/ML dissent). No owner tiebreak.

## The Gap

[§4.16.7](../sections/04_effects.md) Known limits said: "**Exit paths.** A `?` or an early `return` between the assignment and the restore leaves the bound value in `G`. Neither W0550 nor W0551 looks at exit paths, so a binding pair or a speculative pair that misses its restore on such an exit gives no warning." The [mutation-lint-binding-pair decision](mutation-lint-binding-pair.md) left this as a follow-up (label F19: a restore missed on a `?` or early `return` exit) and set a close gate, word for word:

> "Candidate answers: (1) an exit-path warning on binding spans; (2) a scoped-binding construct that restores on every exit. Before this ticket closes, the decision record compares both on the F19 data (leak count in src/, lib/ and the corpus). If (1) wins, the record states why (2) is not needed. If (2) wins, open a type:spec ticket for it."

F20 (write sets are gross, not net of restores) is a separate question and is not part of this decision.

## The F19 Data

A text scanner checked every `.bl` file in `src/`, `lib/` and `tests/` (2855 files; the corpus is `tests/`). Each hit was then read by hand. The definitions are the spec's: a save is `let s = G` or `let s = G.clone()` of a module `let mut G`; a restore is `G = s` in the same function. An exit is `?`, `return`, a `break` or `continue` that leaves the pair, or a call to a `-> Never` function. An exit after a restore on its own path is not a leak.

| area | class | pairs | pairs with an exit | leaks (by the definition) | leaks that are bugs |
|---|---|---|---|---|---|
| src | binding | 97 | 2 | 2 | 0 |
| src | speculative | 10 | 1 | 1 | 0 |
| lib | binding | 0 | 0 | 0 | 0 |
| lib | speculative | 15 | 2 | 0 | 0 |
| tests | binding | 0 | 0 | 0 | 0 |
| tests | speculative | 7 | 0 | 0 | 0 |
| all | both | 129 | 5 | 3 | 0 |

No pair has a `?` or a `-> Never` call between its save and restore. The 3 leaks are all intended by the author:

1. `parse_maybe_named_arg` in `src/parser.bl`, `pos` (speculative). The `return nd` is the commit path: `pos` must stay advanced. A restore on every exit would make this function wrong. An exit-path warning would fire here.
2. `infer_type_uncached` in `src/typecheck.bl`, `tc_if_value_ctx` (binding). Only some arms restore it; the caller wrapper `infer_type` restores it around each call. 367 `return` sites skip the restore. A restore on every exit would be harmless here. An exit-path warning would fire on each uncovered exit unless the function suppresses it.
3. `tc_check_body` in `src/typecheck.bl`, `tc_walk_value_tail` (binding by the text rule). `let in_value = tc_walk_value_tail`, `tc_walk_value_tail = 0` is a read-then-zero hand-off, not a save. 9 `return` sites. A restore on every exit would make it wrong. An exit-path warning would fire here.

`parse_dotted_key` in `lib/std/toml.bl` has a `return` that comes after a restore on its own path, so it is not a leak.

## The Close-Gate Comparison

| answer | what it does on the 3 leaks | true positives | wrong |
|---|---|---|---|
| (1) exit-path warning | fires on 3 pairs, 377 exit sites (1 + 367 + 9) | 0 | 3 of 3 pairs |
| (2) restore on every exit | changes 3 pairs | none: it fixes no bug | wrong for `pos` (commit path breaks) and `tc_walk_value_tail` (hand-off breaks); harmless for `tc_if_value_ctx`, whose caller already restores |
| neither | 0 | - | 0 |

- **Why (1) is not needed.** It has no true positive on the data: it fires only on intended code. The text rule cannot tell a commit path or a hand-off from a leak, and each of these is textually the same shape as a leak. Each fire would need `@allow`.
- **Why (2) is not needed.** Its rule is "restore on every exit", and 2 of the 3 intended sites need a partial restore. The third gains nothing because its caller already restores. It would need a migration of 97 binding pairs in `src/` to fix 0 bugs, and all 97 are in the compiler: `lib/` and `tests/` have 0 binding pairs. It adds a second way to write a save and a restore, and a third meaning for `with` while E0545 says `State` has no handler.

## Reopen Condition

Reopen this when one real leak (a bug, not an intended exit) is found in `src/`, `lib/` or a user package. The data from that leak then shows which of (1) or (2) fits.

## Reading Gaps

- The scanner is a text-level scan. It does not detect a save of a field path (`columns.count`, `annotations.item` in `src/parser.bl`), a save and a restore in two different functions, a restore through a helper call, a save of a global under another module (`mod.G`), or a save into a struct field. These are not pairs by the spec's definition.
- A mutating-method "assignment" (`G.push`) does not count as an assignment in the scan.
- `return`, `?` and `break` in closure bodies and nested named functions are excluded. None fell in a pair range.
- Two textual pairs are hand-offs, not saves: `tc_check_body` and `parse_dotted_key`. The 129 count includes both.
- A first scanner run lost sync on a `\{` escape inside a string and found 43 pairs; the fixed run found 129.
- "Real leak" needs a human judgment, and nobody scans for one. All six seats name this in their concerns.
- `@allow` on the three functions today: `parse_maybe_named_arg` has `@allow(UnrestoredMutation, IncompleteStateRestore)`; `infer_type_uncached` has `@allow(UnrestoredMutation)`; `tc_check_body` has none. DevOps corrected its Phase A claim on this in Phase B.

### Panel Deliberation

The ticket, verbatim:

> **Spec: W0550/W0551 exit paths: a ? or return between a binding's assignment and its restore gives no warning**
>
> W0550/W0551 do not look at exit paths: a ? or early return between the assignment and the restore of a binding pair (or a speculative pair) leaves the bound value in the global and gives no warning (sections/04_effects.md 4.16.7 Known limits).
>
> CLOSE GATE (from decisions/mutation-lint-binding-pair.md, word for word): [quoted above]

### Final Spec

§4.16.7 Known limits, the "Exit paths" bullet, as it now reads in `sections/04_effects.md`:

> - **Exit paths.** A `?` or an early `return` between the assignment and the restore leaves the bound value in `G`. Neither W0550 nor W0551 looks at exit paths, so a binding pair or a speculative pair that misses its restore on such an exit gives no warning. An exit can keep the new value on purpose, for example a parser that keeps its cursor after a successful lookahead, so text alone cannot tell it from a leak. To restore on every exit, save and restore in a wrapper function that calls the body, or write the restore before each exit.

```blink
let mut hint = 0

fn check(n: Int) -> Result[Int, Str] {
    if n < 0 { return Err("negative") }
    Ok(n + hint)
}

fn infer_body(n: Int) -> Result[Int, Str] {
    let a = check(n)?
    let b = check(a)?
    Ok(a + b)
}

fn infer(n: Int) -> Result[Int, Str] {
    let saved = hint
    hint = -1
    let r = infer_body(n)
    hint = saved
    r
}
```

- No exit-path warning and no construct that restores on every exit. No new code; W0550, W0551, `@allow` and `with` do not change. No opt-in `blink lint --exit-paths`.
- The spec text holds no counts and no "by design", "by decision" or "deliberate". The counts and the close-gate comparison are in this record.
- The bullet keeps "gives no warning" for a missed restore.
- The wrapper comes first in the advice because it holds for `?`, `return` and `break`; the restore before each exit stays as the second option.
- F20 (write sets gross, not net of restores) and panic unwinding are not part of this decision.
- Reopen this when one real leak (a bug, not an intended exit) is found in `src/`, `lib/` or a user package.
- No code change and no implementation ticket.
