# Expected Instance Fixes a Literal's Type Parameters — Design Rationale

### Question

§3.4 *Expected type at a site*, item 5, gives a brace field value the expected type "where the declared field type is `T`". It does not say what happens when `T` names the type's own type parameter and an annotation fixes it:

```blink
type GBox[T] { v: T }
type G[T] { o: Option[T], x: List[T] }
type Box[T] { Val(T)  Empty }

fn main() {
    let gs: GBox[U64] = GBox { v: 5 }
    let g: G[U8] = G { o: Some(3), x: [1] }
    let b: Box[U8] = Box.Val(5)
}
```

gen1 rejects all three (`declared GBox[U64] but got GBox[Int]`): every literal in such a field or payload becomes `Int` before the annotation can fix the parameter. This holds in let, argument, return and nested positions. `Some(5)` under `Option[U8]` (item 6) and `[1, 2]` under `List[U8]` (item 7) already work, and a non-literal value takes the instance through unification (`GBox { v: x }` with `x: U64` is accepted). Item 4 gives a callee type parameter no expected type, so `let a: U8 = id(5)` is an error. Options: (a) state that item 5, like item 4, gives none for a field declared with a type parameter; (b) let the expected instance fix the parameter, for brace fields and call-form payloads.

### Panel Deliberation

Six panelists (systems, web/scripting, PLT, DevOps/tooling, AI/ML, minimalism) deliberated in independent-proposal → debate → vote rounds. Phase A, Phase B, Phase C and Phase D ran. The record below is excerpted from each seat's own text.

#### Phase A — Independent proposals

All six seats chose option (b) first, and kept option (a) as a fallback only (web rejected it).

- **Systems:** "Choose (b), for brace fields and call-form payloads alike. Width of a literal decides the C type of the field (`uint8_t` or `int64_t`) and the layout of the monomorphized struct. Today `let gs: GBox[U64] = GBox { v: 5 }` produces a literal of `Int`, then a hard error. The programmer wrote the width one line away. The compiler has the answer and refuses to use it." On item 4: "In `id(5)` the parameter `T` belongs to the callee. Nothing at the call site fixes it. In `GBox { v: 5 }` under `GBox[U64]`, the parameter `T` belongs to the type, and the expected instance names it. These are different facts, so the rules do not conflict." Proposed text: "5. a field value in a struct or variant brace literal, and the payload of a variant constructor call, where the declared type is `T`. If the literal has an expected type, or type arguments on its head, that is an instance of the same generic type, `T` is the declared type with each type parameter of that type replaced by the matching argument. An argument that is not yet a concrete type gives no expected type;" and, added: "A type parameter of a callee still gives no expected type (item 4). A type parameter of the type being built does, when an instance fixes it." Cost: "zero. This is a front-end rule."
- **Web/Scripting:** "`let gs: GBox[U64] = GBox { v: 5 }` must compile. A JS/TS/Kotlin/Rust dev writes the annotation to say \"this is a GBox of U64\". The error \"declared GBox[U64] but got GBox[Int]\" tells them the compiler read the annotation and ignored it." Rule: "the expected type of a field value (or payload) is the declared field type with each `Ti` replaced by `Ai`. Explicit head arguments (`GBox[U64] { v: 5 }`) do the same and win over the expected type." On item 4: "Dev-facing summary: \"A literal of a generic type reads its annotation. A generic function call does not.\"" Rejected (a): "cheap, but it makes a correct annotation useless and teaches users to write `let x: U64 = 5` first."
- **PLT:** "Typing rule (checking mode). For a constructor `C : forall T. F1 * ... * Fn -> G[T]` (a struct brace literal, a variant brace literal, or a call-form variant payload) at a site with expected type `G[A]`: unify `G[T]` with `G[A]` first, then check each field `ei` against `Fi[T := A]`. If the expected type has a different head, or an unsolved variable in the argument position, the rule does not apply and synthesis runs as today." On item 4: "This is a policy asymmetry, not a soundness one: both are sound, and the user fixes `id(5)` with `id[U8](5)`. I do not reopen item 4." On option (a): "it makes `let x: GBox[U8] = GBox { v: 5 }` fail while `Some(5)` under `Option[U8]` works, a split between built-in and user generics with no typing reason."
- **DevOps:** "When a struct or variant literal has an expected type that is an instance `G[A1..An]` of the literal's own type, or its head names type arguments, each declared field or payload type is taken with the type parameters replaced by those arguments. The result is the expected type of that field value. This covers the bare form (`v: T`) and the nested form (`o: Option[T]`, `x: List[T]`), because the substituted type then reaches items 6 and 7." On the diagnostic: "Today `let gs: GBox[U64] = GBox { v: 5 }` reports \"declared type GBox[U64] but got GBox[Int]\". The span covers the whole expression and `5` is not blamed. A user cannot see why: the annotation looks sufficient." Proposed an item 4 sentence: "The expected type of the call result does not fix a type parameter of the callee."
- **AI/ML:** "A model writes `let gs: GBox[U64] = GBox { v: 5 }` and `let b: Box[U8] = Box.Val(5)` by analogy with `let o: Option[U8] = Some(5)`, which the spec already accepts (item 6). Under option (a) the spec needs a rule that says \"built-in `Some` takes the inner type, a user generic does not\". A model cannot learn that from the spec alone." Proposed text after item 4: "Item 4 is unchanged. A constructor is not a function call: its result type names the type being built, so the expected type of the site already fixes its parameters. A callee type parameter is open until the arguments solve it."
- **Minimalism:** "The gap is a special case: `Some(3)` under `Option[U8]` works and `Box.Val(5)` under `Box[U8]` does not, though both are variant constructors of a generic type. Option (a) keeps that split. It makes a user's generic type worse than a built-in one, and every user and every model must learn why. Option (b) as the ticket words it adds a rule. I propose it as a subtraction: the built-in rule becomes the general rule." Proposed to "Replace items 5 and 6 of 03_types.md (2274 ff.) with" one item 5 that ends "This includes `Some(e)`, `Ok(e)` and `Err(e)` under `Option[T]` or `Result[T, E]`."

### Final Spec

- §3.4 *Expected type at a site*, item 5, now reads: a field value in a struct or variant brace literal, and the payload of a call-form variant constructor. When the expected type is an instance `G[A1, .., An]` of the literal's own generic type, or the head writes type arguments, each type parameter of `G` takes the matching argument first, for any generic struct or enum and for nested field types such as `Option[T]` and `List[T]`. A different head, or an unsolved variable at an argument position, gives no expected type at that position. The item ends with the sentence that Q3 chose.
- Items 4, 6 and 7 do not change. Item 6 stays a separate item (Q2 A).
- A new example block after the list shows `GBox { v: 5 }` under `GBox[U64]`, `G { o: Some(3), x: [1] }` under `G[U8]`, `Box.Val(5)` under `Box[U8]`, the argument, return and nested positions, head type arguments, the head and annotation mismatch, and `let a: U8 = id(5)` as an error (Q5 B and the Concerns of all six).
- No new error code. The mismatch between head arguments and the annotation, and the `id(5)` error, use the existing `TypeError`. An integer literal that does not fit its field type is the existing E0318 at the literal.
- No `help:` text in the spec (agreed in Phase B). The implementation ticket carries the help lines: the `id(5)` error offers `id[U8](5)`, and a literal error names the field and the instance.
