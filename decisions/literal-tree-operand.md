# Literal Tree in Operand Position — Design Rationale

### Panel Deliberation

Six panelists (systems, web/scripting, PLT, DevOps/tooling, AI/ML, minimalism) deliberated
in independent-proposal → debate → vote rounds. The question: does a literal-only tree in
operand position take the other operand's integer type (`x + (2 * 3)` with `x: I8`)?

Phase A and Phase B quotes are excerpts with attribution; "…" marks a cut. Phase C and Phase D
votes are complete and verbatim.

#### Phase A — Independent proposals

- **Systems:** "Rule: in the operator list of §3.2, a *literal tree* in operand position is checked against the integer type of the other operand, on either side. A literal tree is a literal (negative included), a parenthesised literal tree, `-` over a literal tree, or a literal tree joined by `+ - * / % & | ^ << >>`. The tree is typed top-down: every `+ - * / % & | ^` node and its left operand get type `T`; the right operand of `<<` `>>` gets `U32`." Fallback: "keep the text; users write `(2 * 3)` as a typed `let`. It is zero cost but forces the user into hand-folding constants, which I reject."
- **Web/Scripting:** "**Rule.** In operand position of `+ - * / % & | ^ == != < <= > >=`, a literal-only tree takes the integer type of the other operand, on either side. "Literal-only tree" means exactly `K` from §3.6: `N`, `L`, `( K )`, `- K`, `K op K` with `op` in `+ - * / % `. Nothing wider." Fallback: "keep the text, add the diagnostic … Positional inconsistency stays, and I oppose it."
- **PLT:** "**Rule.** A *literal-only tree* is a literal, `( L )`, `- L`, or `L op L` with op in `+ - * / % & | ^ << >>`. When one operand of `+ - * / % & | ^` or a comparison is a literal-only tree, the checker synthesizes the other operand first, then checks the tree against that type. Either side." "Today `x + (2 * 3)` fails while `x * 2 + 3` passes (q16 vs q17): the type depends on how precedence groups the tokens. That is not compositional."
- **DevOps:** "Tree = the W0708 `K`: integer literals, parentheses, unary `-`, and `+ - * / %` over them. Test the tree by syntax, so the rule does not depend on types." "Today `x + 2 * 3` fails with `I8 and Int` while `x * 2 + 3` compiles (q16, q17). The user cannot see why."
- **AI/ML:** "One rule: **a literal-only tree in operand position takes the other operand's integer type, exactly as a bare literal does.** "Literal-only tree" is the W0708 grammar `K` (`N | L | (K) | -K | K op K`, op in `+ - * / %`). One definition serves both §3.2 and §3.6."
- **Minimalism:** "**Position.** Keep the §3.2 mechanism. Widen one noun. The checker already hands an expected type to a tree (q01, q06, q07). The list says a *literal* takes the other operand's type. Make that a *literal-only tree*, the W0708 `K` (parentheses, unary `-`, `+ - * / %`, literals). `K` already exists in §3.6, so this adds no new definition."

All six seats also wrote a "keep the current text" option and said they oppose it.

#### Phase B — Debate highlights

The panel dedupe gave Option 1 (a literal-only tree in operand position takes the other
operand's integer type, on either side) and Option 2 (keep the current text). Result:
**Option 1, 6-0.** The debate opened four variations: which tree (V1), the wording of the
§3.2 sentence "Its type is known at the literal" (V2), the §3.6 sentence "not decided here"
(V3) and extra diagnostic text (V4). Position shifts on V1:

- **AI/ML (changed to the wider tree):** "I change my position. Use the wider tree: `+ - * / % & | ^ << >>` over literals. My Phase A claim that `x & (1 << 63)` keeps working was wrong. It works only when an expected type reaches the tree (a `U64` return)."
- **Web/Scripting (changed to the wider tree):** "I change my vote to the wider tree (sys, plt). My A text said "exactly K, nothing wider". I was wrong."
- **Systems (held):** "I hold `K` plus `& | ^ << >>`, with one definition for §3.2 and §3.6. … I do not accept two definitions."
- **PLT (held):** "I hold this. The type rule and the W0708 rule answer different questions. … Let §3.2 define the tree, and let §3.6 keep `K` for its warning."
- **DevOps (held K):** "One definition must serve §3.2 and §3.6. If `K` grows to `& | ^ << >>`, W0708 must say what a shift that loses bits does, and that is a separate decision." "I will vote for the wider tree only if W0708 text for shifts and bit operators comes with it in this record."
- **Minimalism (held K) (dissent):** "Adding `& | ^ << >>` to the tree would also widen W0708, and W0708 for shifts and bit operations needs its own decision (what does `1 << 70` do, and at which type?)."

On V2, web and sys moved to "known at the operation that holds the tree"; min held "or at the enclosing literal tree". On V3, web, devops, min and sys accepted a pointer to §3.2; plt and aiml wanted the sentence deleted. On V4, devops and sys proposed diagnostic text; plt answered: "devops's wording "the literal tree has type Int; the other operand is F64" is wrong under Option 1: the tree is checked against `F64` and gets whatever error a bare literal gets there."

Fact put before the panel in Phase C: sections/03_types.md:1656, "Shift amounts are `U32` (matching the underlying C shift semantics). Shifting by more than the bit width is a runtime panic." The spec states no other overflow rule for `<<`, `>>`, `&`, `|` or `^`.

#### Phase C — Final vote

Options. **Q1:** A, the W0708 `K` only (`+ - * / %`); B, `K` grows to `+ - * / % & | ^ << >>` and §3.2 and §3.6 share one definition; C, §3.2 defines the wider tree and §3.6 keeps `K` for W0708. **Q2** (the §3.2 sentence "Its type is known at the literal"): A, "or at the enclosing literal tree"; B, "known at the operation that holds the tree"; C, "known when the checker finishes the enclosing operator"; D, "type known at the tree". **Q3** (the §3.6 sentence "not decided here"): A, replace with a pointer to §3.2; B, delete. **Q4** (diagnostic text in the spec): A, none; B, the devops set; C, the sys set.

- **Q1: Which tree takes the other operand's type** (4-1-1 in Phase C; 4-1-1 again in Phase D; B wins)
  - **Systems:** B — "The mask `m & (1 << 63)` is the most common constant tree in systems code. Under A or C it works with a typed return and fails in an unannotated `let`, which is the positional trap this ticket removes. B keeps one definition for §3.2 and §3.6, so codegen and the checker share one tree class. It costs nothing at run time: the tree is typed `T` and the C compiler folds it. §3.3 already says a shift by more than the bit width panics, so W0708 for a constant shift amount at or above the width has a defined meaning (a panic) and needs no new rule. A shift that drops high bits is not an overflow in the spec and does not warn." Concern: "W0708 now has to say whether a shift or `&|^` leaf warns, and the spec text is silent on signed `<<` into the sign bit (`1 << 63` at `I64`), so the record must state it or the warning definition drifts."
  - **Web/Scripting:** B — "The common tree in operand position is a bit mask (`m & (1 << 63)`, `flags | (1 << 3)`). Under A it works with a return type and fails in a `let`, which is the positional trap this ticket removes. B keeps one definition for §3.2 and §3.6, so a JS or Python dev learns one word set. The same text must say that the right operand of a shift inside the tree is `U32` and the left operand takes the tree's type, and must say W0708 now covers `& | ^ << >>`. The shift rule at 03_types.md:1656 (shift by the bit width or more is a runtime panic) gives W0708 a clear meaning for shifts." Concern: "If W0708 grows with `K`, the warning for shifts and bit operations ships without its own examples or its own review, and users meet false positives or gaps there first."
  - **PLT:** C *(dissent)* — "The two rules answer different questions. §3.2 says which literals take the other operand's type. §3.6 says where a literal tree overflows at run time. A tree with `& | ^ << >>` still needs the sibling's type, or `let d = m & (1 << 63)` fails while the same text with a return type reaching it compiles, and that is the precedence-style split this ticket removes. The shift rule at 03_types.md:1656 (shift amount `U32`, panic when the amount is at or above the bit width) is a different overflow rule from add/mul, so W0708 for shifts and bit operations is a separate decision. B forces that decision into this record, and A leaves the mask gap open." Concern: "Two lists (§3.2 wide, §3.6 `K`) can drift; the panel must state in §3.6 that `K` is a subset by design."
  - **DevOps:** B — "One tree definition for §3.2 and §3.6 is the best surface for tooling: one syntactic test in the checker, one hover and one W0708 reading. Option C gives two lists that drift apart. Option A leaves `m & (1 << 63)` an error when no type reaches it, and a user cannot tell it from the case that compiles in return position. The new fact (§3.2: a shift by more than the bit width is a runtime panic) gives W0708 a defined basis for shifts: it fires when a literal shift amount is at or over the width of the tree's type. `& | ^` and a shift within width cannot overflow. The record must say this in the §3.6 text; that is the condition I set in B1, and B meets it." Concern: "If the record widens `K` without stating when W0708 fires for `<<`, `>>`, `& | ^`, the compiler gets an ambiguous warning rule and users see W0708 on masks that are fine."
  - **AI/ML:** B — "`flags & (1 << 3)` and `m & (1 << 63)` are among the most common constant expressions a model writes. Under `K`-only they compile when a return type reaches them and fail in an unannotated `let`, which is the positional trap this ticket removes. One definition shared by §3.2 and §3.6 is one thing to learn, and W0708 already uses the type the checker gives each operation. The text must say that the right operand of a shift inside the tree is `U32` and the left takes the tree's type, or `1 << 63` gets two readings." Concern: "W0708 now covers shifts and bit operations, and the spec must state what `1 << 70` at `U64` does, or a model will guess."
  - **Minimalism:** A *(dissent)* — "One definition of the tree for §3.2 and §3.6 is the smallest change: one noun widens in one list, and W0708 does not move. Growing `K` to `<< >> & | ^` pulls W0708 into shifts and bit operations, and the spec has no overflow rule for them beyond "shift by more than the bit width panics" (§3, line 1656). What `1 << 70` or `1 << 63` at `I64` means for W0708 is a separate decision that this record does not make. The mask gap (`m & (1 << 63)` with no expected type) is real, and a follow-up ticket that widens `K` and W0708 together closes it with the shift semantics decided first. C is a second definition, which I oppose." Concern: "If B or C wins, W0708 either covers shifts without a written rule for what a lossy shift does, or §3.2 and §3.6 carry two tree definitions that drift apart."

- **Q2: The §3.2 sentence "Its type is known at the literal"** (3-1-1-1 in Phase C; B wins after Phase D)
  - **Systems:** B — ""Known at the operation that holds the tree" is exact. The checker types the tree when it checks that operation, never from a later line, so no variable is left to default. "At the literal" is false once a tree takes a sibling's type. A and D are less precise; C names a checker event, not the property." Concern: "A reader may take "the operation" to mean the outer operator and miss that the tree's own inner operators are typed the same way."
  - **Web/Scripting:** B — ""Known at the operation that holds the tree" says where the type is fixed, in words a reader can check against a bare literal and against a tree. It keeps the property that matters: no later line decides the type, and no variable is left to default. A and D name a tree without saying when; C is exact but longer than the sentence it replaces." Concern: ""The operation that holds the tree" is unclear when both operands are trees and the type comes from an expected type, so a reader may ask which operation is meant."
  - **PLT:** D — ""Type known at the tree" is exact. The property that matters holds: no later line fixes the type, and no variable is left to default. It is the shortest wording of the three that are exact." Concern: ""At the tree" can read as vague about when; the §3.2 rule text (checks the other operand first) must carry the order."
  - **DevOps:** C — ""Known when the checker finishes the enclosing operator" says exactly when the type is fixed and keeps the property that matters: no later line sets it and no variable stays open. "At the literal tree" (A) and "at the tree" (D) are shorter but do not say when. B names the operation, which is close, but it is less exact for a tree inside a comparison." Concern: "The longer wording may read as permission for later-line inference to a reader who skims it."
  - **AI/ML:** B — ""Known at the literal" no longer fits a tree. "Known at the operation that holds the tree" is short, exact, and keeps the property that no later line fixes the type and no variable is left to default. It avoids a new term such as "enclosing operator", which a model must parse." Concern: ""The operation that holds the tree" may read as the tree's own root operator and not the enclosing one."
  - **Minimalism:** A *(dissent)* — "The property that matters is "no variable is left to default, and no later line fixes the type". A keeps the sentence and adds the phrase "or at the enclosing literal tree", which is the smallest edit that stays true under A of Q1. D ("type known at the tree") is also acceptable." Concern: ""Known at the tree" or "at the operation" wording may let a reader think the type is found after the whole operator is checked, which blurs the no-later-line property."

### Final Spec

```blink
fn trees(x: I8, u: U8, m: U64) -> U64 {
    let a = x + (2 * 3)         // OK: the tree is I8
    let b = x + 2 * 3           // OK: precedence makes 2 * 3 a tree, and it is I8
    let c = (127 + 1) + x       // OK: I8; warning[LiteralArithmeticOverflow]; RUNTIME PANIC
    let d = x + -(2 * 3)        // OK: unary - passes I8 to the tree
    let e = u < (100 + 100)     // OK: the comparison passes U8 to the tree
    let f = u << (1 + 1)        // OK: the amount is U32
    let g = m & (1 << 63)       // OK: the tree is U64
    let h = u + (200 + 100)     // OK: W0708 and a RUNTIME PANIC
    let k = u + (300 - 100)     // error[IntLiteralOutOfRange]: 300 does not fit in U8
    m
}
```

- A literal-only tree in operand position takes the integer type of the other operand, on either side. The checker finds the other operand's type first; evaluation order stays as written.
- The tree is `K` (§3.6): literals, parentheses, unary `-`, and `+ - * / % & | ^ << >>`. One definition serves §3.2 and §3.6. A tree with a name or a call in it is not literal-only.
- Unary `-` over a tree is part of the tree. A comparison passes the type to the tree. A tree as the right operand of `<<` or `>>` is `U32`.
- Both operands trees and no type reaches them: `Int`. An unsolved type variable becomes `Int`.
- A literal that does not fit is E0318. Literals that fit with an operation that overflows compile, give W0708, and panic. No new error code.
- §3.2: "known at the operation that holds the tree", naming the enclosing operator. §3.6: the "not decided here" sentence is a pointer to §3.2. No diagnostic text in the spec.
- W0708: `& | ^` never warn; a shift follows the shift rule in §3.2 *Bitwise operations*, unchanged. The shift boundary is open.
