# Module-Qualified Struct Pattern — Design Rationale

### Question

May a pattern name a struct through its module, as in `geo.Point { x, .. }`? Before this decision the compiler read every dotted-brace pattern as `Type.Variant` and gave an error about variants. The literal `geo.Point { x: 1, y: 2 }` already compiled.

### Panel Deliberation

Six panelists (systems, web/scripting, PLT, DevOps/tooling, AI/ML, minimalism) deliberated in independent-proposal → debate → vote rounds.

#### Phase A — Independent proposals

All six seats proposed the same option: `mod.Type { field_patterns }` is a struct pattern wherever the bare `Type { .. }` is valid. They differed on how the compiler tells `mod.Type {` from `Type.Variant {`. The excerpts below keep each seat's rule and its parse key.

- **Systems:** "A pattern `m.T { field_patterns }`, where `m` is an imported module qualifier and `T` is a struct type of `m`, means the same as the bare pattern `T { field_patterns }` with `T` imported. It is valid at every pattern site that accepts the bare form: match arm, `let`, `for`, parameter, nested." … "The first segment decides, and the lexer already separates the classes. `TYPE_NAME` starts uppercase, a module qualifier starts lowercase." … "I would reject any rule that needs a symbol-table lookup to parse."
- **Web/Scripting:** "`geo.Point { x, .. }` is a valid struct pattern in every pattern position: match arm, nested, OR-alternative, `let`, `for`, and parameter." … "The parser keeps `A.B {` as one shape. The resolver decides by what `A` names, as a new step 0 before the E0507 → E0547 → E0300 order" … "If a module and a type share a name, the type wins and the module needs an alias."
- **PLT:** "A pattern is a **module-qualified struct pattern** when a lowercase `IDENT` (a module qualifier, §10.1) is followed by `.` and a `TYPE_NAME`." … "Compositionality: one construct (`T { .. }`) with an optional module prefix, in all positions, with one typing rule." … "`geo.Shape.Circle { r }` and `geo.Shape.Circle` in a pattern are E1007, at the second dot."
- **DevOps:** "The parser tells `mod.Type { }` from `Type.Variant { }` by the first character of the head, with no lookahead and no symbol table." … "Add a step 0 before E0507 for a module-headed pattern: resolve the module (an unknown module is the existing import error), then look up `Type` in it … E0547 never applies, because no variant is looked up." … "The help shows the fix: `import geo.{Shape}` and `Shape.Circle { r }`, machine-applicable."
- **AI/ML:** "A pattern `Q.N { field_patterns }` where `Q` resolves to an imported module is a module-qualified struct pattern. `N` names a type declared in `Q`." … "Resolve `Q` first, as a new step 0 of the 3.5 check order, before E0507" … "Replace line 2229 tail: \"both accept the bare and qualified spellings. The qualified spelling of a struct is `mod.Type`; the qualified spelling of a variant is `Type.Variant`.\""
- **Minimalism:** "I do not want a second rule for patterns. I want the existing rule to hold." … "The first token of `A.B {` already tells the parser which one it has" … "The risk is a lowercase type name. I need the grammar to forbid it, or the lowercase rule is unsound. Check this before voting." Fallback (min-2): "reject, with a real diagnostic" — keep patterns bare-only and give one new error.

#### Phase B — Debate highlights

The moderator put four facts before the panel.

- F1: gen1 accepts a lowercase type name (`type point { x: Int }`) and an uppercase module (`src/Geo.bl`).
- F2: no rule in `sections/` makes a lowercase type name or an uppercase module name an error. 02_syntax.md says "One casing rule for builtins and user types", and §10.1 states no case rule for modules.
- F3: `let` and `for` with a bare struct pattern do not parse today. The p2 parse error also occurs for the bare form.
- F4: two texts in 03_types.md disagree on the bare `Point { x, .. }` for a struct. A separate question holds it. It was not on this ballot.

**Option 1 over Option 2, 6-0.** min withdrew the fallback: "I withdraw min-2." (min). Option 2 "needs a carve-out and adds an error" (min).

**V1, how to tell `mod.Type {` from `Type.Variant {`: four seats withdrew the case rule.**
- sys: "My Phase A claim that the lexer separates the classes is wrong. F1 and F2 show no rule forbids a lowercase type or an uppercase module, so case is not a sound parse key."
- plt: "My Phase A rule rested on \"module names are lowercase, type names are not\". F1 and F2 show the spec enforces neither, so a case split is unsound."
- devops: "My case-of-head rule is unsound until a new rule enforces casing."
- min: "I concede to web and aiml; I withdraw my case-based rule." … "\"§10.1 naming already forbids it\" is false: F2 found no such text."
- Result: the parser reads `A.B {` as one dotted-brace form. If `A` is a type in scope, it is `Type.Variant`. Else, if `A` is an imported module qualifier, it is `mod.Type`. The type wins a clash (web). devops added: "The compiler should give a note that names the module and says to use an alias. That is a needed diagnostic, not an optional one."

**V2, check order.** sys, web, devops, aiml and (after V1) min and plt took one list with a new step 0 before E0507. web: "one ordered list is easier to teach than two."

**V3, `geo.Shape { .. }` on an enum.** aiml withdrew E0547: "I withdraw E0547." The spec names the diagnostic by reference ("as bare"). min: "E0547 means a variant is missing, and no variant is named here."

**V4.** A type missing from the module is E0507. An unknown module gets the existing error. No new code.

**V5.** The catalog takes the §10.8 row verbatim. devops: "Two texts with two wordings cause drift." min conceded.

**V7.** All seats supported aiml's tail edit for the construction and pattern duals sentence.

**V8, applicability of the E1007 help.** devops withdrew "machine-applicable": "The repair needs two edits (add the import, rewrite the path), and the import may already exist." web: "machine-applicable only when the module is imported and the import line is a pure addition." plt and aiml supported "machine-applicable". The panel put this to the vote as Q1.

**V6, the head name in the grammar line.** Split: `MODULE` (sys, web in Phase A), `IDENT` (plt, devops in Phase A), `MODULE_NAME` (aiml), `mod_path` (min). The panel put this to the vote as Q2.

Questions put to the Phase C ballot:

- **Q1.** Is the E1007 fix for `mod.Type.Variant` in a pattern machine-applicable? A: yes. B: only when the module is imported and the import line is a pure addition. C: only if the type is not already imported under another name. D: the help is text; applicable only when the import is present.
- **Q2.** The head of the new grammar line. A: `MODULE`. B: `IDENT`. C: `MODULE_NAME`. D: `mod_path`.
- **Q3.** A name that is both a type in scope and an imported module. A: the spec requires a note that names the module and the alias fix. B: the spec states only the rule and requires no note.

#### Phase C — Final vote

**Q1. Is the E1007 fix for `mod.Type.Variant` in a pattern machine-applicable?** B 4 (systems, web, PLT, AI/ML), D 2 (DevOps, Minimalism). Closer than 5-1, so Phase D re-debated it.

- **Systems: B.** Reasoning: The fix is two edits: add `import geo.{Shape}` and rewrite the path to `Shape.Circle`. An automatic edit is safe only when it cannot change which item a name means. It is safe when the module is imported and the new import line only adds a name. An edit that touches an existing import line, or meets a clash with a name already in scope, changes what the program resolves to, and a tool must not make that change alone. Option B states that limit as a rule the tool can test; C and D name only one of its conditions. Concern: If B wins and the tool treats "pure addition" loosely, it can add an import that shadows or clashes with a name already in scope and silently change what a pattern resolves to.
- **Web/Scripting: B.** Reasoning: The fix for `geo.Shape.Circle { r }` is two edits: add an import of `Shape`, then drop the `geo.` prefix. An editor that applies this blindly can break a file when the import line already exists as a selective import (`import geo.{Point}` must be rewritten, not added to). A fix that is machine-applicable only when the module is imported and the import is a pure addition is safe, and it still covers the common case where a dev wrote `geo.` and has no selective import yet. Options C and D are narrower or less precise than B for the same safety. Concern: If the compiler marks the fix applicable in the wrong case, a dev gets a broken edit from a button labelled "quick fix", and they stop trusting every fix.
- **PLT: B.** Reasoning: A fix marked machine-applicable must preserve meaning by construction. Two edits make this fix (add the type import, rewrite the path). It is safe only when the import line is a pure addition: no clash with a local `Shape`, no existing selective import of the module that the edit would have to merge. When those hold the rewrite is total and the result resolves to the same type, so B states a checkable condition. A over-claims. D is too narrow: with the import already present the fix is one edit and needs no label for the import. Concern: "Pure addition" needs a precise definition in the spec (no existing binding named `Type`, no alias for the type), or each tool will read it differently.
- **DevOps: D.** Reasoning: The fix has two edits: add `import geo.{Shape}` and rewrite the path to `Shape.Circle`. The import may already exist, may bind the type under another name, or may clash with a local name. A tool that applies a wrong edit automatically is worse than a tool that gives only text. The help text is always shown; the compiler marks it applicable only when the import is present and the rewrite is a pure path edit. B and C each state one part of that condition, and D states the safe default. Concern: If D loses to a looser option, an auto-fix could rewrite code in a file where `Shape` already means a different type.
- **AI/ML: B.** Reasoning: An AI repair loop applies a fix without judgment, so a wrong "applicable" mark does more harm than a missing one. The fix is two edits: add `import geo.{Shape}` and rewrite the path. That is safe only when the module is already imported and the new import line is a pure addition. B keeps the mark for the common case, where a model wrote `import geo` and then `geo.Shape.Circle`. A would break when the type is already imported under another name, which is sys's case in C. D is stricter than needed and drops the common case. Concern: If the winner is A, a loop that applies the fix when the type is already imported under an alias produces a second import or a name clash, and the model then repairs the wrong error.
- **Minimalism: D.** Reasoning: The spec should say what the help text says and nothing about applicability tiers. The repair needs two edits (an import and a path rewrite), and the import may already exist or may clash with another import, so a blanket "machine-applicable" claim is false in some cases. D states the help as text and leaves the tooling to mark it applicable when the import is present. That adds no rule to the language surface. B and C each write a precondition into the spec that tooling can check without the spec. Concern: Without a spec-level promise, each tool decides applicability by its own rule, and the repair loop may behave differently in the compiler, the LSP and the formatter.

**Q2. The head of the new grammar line.** A (`MODULE`) 3 (web, PLT, DevOps), B (`IDENT`) 2 (systems, minimalism), C (`MODULE_NAME`) 1 (AI/ML). Phase D re-debated it.

- **Systems: B.** Reasoning: The spec has no token class for a module name (03_types.md:3163: "`TYPE_NAME` and `IDENT` are both identifiers"). All seats now agree that case does not decide the parse. So the head is an ordinary identifier at parse time, and resolution decides what it names. `IDENT` says exactly that and adds no token class to the lexer or the grammar. `MODULE` and `MODULE_NAME` need a new definition, and `mod_path` implies a multi-segment path, which the spec does not use (only the leaf name qualifies, §10.1). Concern: If `MODULE` wins, the grammar names a token class that the lexer does not have, and a reader will look for a lexical rule on module names that does not exist.
- **Web/Scripting: A.** Reasoning: `MODULE` tells a JS/Python dev reading the grammar what the head is. `IDENT` is wider, and `MODULE_NAME` and `mod_path` add a second name for the same idea. The spec has no token class with this name, so the grammar change must add a one-line definition next to 03_types.md:3163: `MODULE` is an identifier that names an imported module qualifier. Concern: If the spec adds `MODULE` to the grammar without that definition line, readers will think the lexer has a separate token class, and the lowercase-module habit will come back as an unwritten rule.
- **PLT: A.** Reasoning: The head of this form is a name that resolves to an imported module. After the B1 concessions, the parser reads an identifier and resolution decides, so the grammar must name the role. The existing grammar already does this: `TYPE_NAME` and `IDENT` are both identifiers (03_types.md:3163), and `TYPE_NAME` is a role name. `IDENT` here would hide that this line applies only when resolution picks the module. `MODULE_NAME` and `mod_path` add nothing: only the leaf module name is a qualifier (§10.1), so a path is wrong. Concern: The spec has no `MODULE` token class today, so it must define `MODULE` beside line 3163 as "an identifier that resolves to an imported module qualifier", or the grammar line is undefined.
- **DevOps: A.** Reasoning: The head is a module qualifier that resolves to an imported module, and casing no longer decides it, so `IDENT` hides the point and `mod_path` suggests several segments when only the leaf module name is a qualifier (§10.1). `MODULE` reads well in diagnostics and in LSP completion docs. The spec must then define it in one line, because 03_types.md:3163 has no such token class: "`MODULE` is an `IDENT` that names an imported module." Concern: If the winner is `IDENT`, a reader of the grammar sees nothing that says resolution picks between module and type, and the grammar line looks ambiguous with `TYPE_NAME "." IDENT`.
- **AI/ML: C.** Reasoning: The grammar names token classes in capitals (`TYPE_NAME`), so `MODULE_NAME` reads the same way and tells a model what goes in the slot. The spec must define it in one line next to 03_types.md:3163, because the grammar has no module token class today. The parser accepts any identifier here and the resolver decides, so the definition should say so. `MODULE` is a close second; the difference is small. Concern: If the winner is a name that implies lowercase (`MODULE`, or `IDENT` read as "lowercase ident"), a model may infer a case rule that the spec does not state (F1, F2).
- **Minimalism: B.** Reasoning: The fact in the ballot says the grammar has no token class for a module name; 03_types.md:3163 says `TYPE_NAME` and `IDENT` are both identifiers. `IDENT` uses a class that exists. `MODULE` and `MODULE_NAME` add a token class that the lexer does not have, and the resolver, not the lexer, decides what the head is. I withdraw my own `mod_path` for the same reason: it adds a non-terminal for one line. The spec text that explains step 0 says the head must resolve to an imported module. Concern: `IDENT` in the head position reads as "any identifier", so a reader may think a local variable can qualify a type; the step 0 sentence must say the head resolves to an imported module.

**Q3. A name that is both a type in scope and an imported module qualifier.** A 5-1 (Minimalism dissent). Decided in Phase C.

- **Systems: A.** Reasoning: The type wins by rule, so the module form fails with an error that talks about variants (a different type from what the user wrote). Without a note the user cannot see why a valid module-qualified pattern was read as `Type.Variant`. The note costs one compile-time diagnostic and has no effect on codegen or on the IR. It makes the alias fix visible at the place where the resolution is silent. Concern: If B wins, the user who hits a type/module name clash gets a variant-lookup error with no hint that an alias fixes it.
- **Web/Scripting: A.** Reasoning: "The type wins and the module needs an alias" is correct, but a dev who hit it sees a type-path error for code that looks valid. A note that names the module and says to use an alias turns a Stack Overflow question into a one-step fix. It costs one note at one rare site. Concern: If the spec leaves the note out (option B), a dev with module `Geo` and type `Geo` gets a variant error with no hint that the module exists, and each compiler can word it differently.
- **PLT: A.** Reasoning: The rule "type wins, module needs an alias" is sound and keeps F4 and E0554 consistent. But it makes a valid program fail with a message about the wrong thing: `geo.Point { .. }` reports that type `geo` has no variant `Point`, and the user never wrote a variant. A note that names the module and says to use an alias costs one diagnostic and removes the misdiagnosis. A bare rule with no note leaves the only recovery path undiscoverable. Concern: If the spec requires a note, every compiler must emit it on this path, and the note must not appear when `A` is only a type, or it will give false advice.
- **DevOps: A.** Reasoning: When a name is both a type and a module, the type wins and the user may not see why `geo.Point { .. }` fails or means something else. The error then points at the type, and the fix is an alias on the import. A note that names the module and says "use an alias" costs one help line and saves a long search. The spec should require it, so every tool gives the same text. Concern: If B wins, the rule exists but the shadowing gives no signal, and users hit a confusing E0547 or E0507 on valid-looking code.
- **AI/ML: A.** Reasoning: The type-wins rule is silent: the user wrote `geo.Point { .. }` and got a variant error that names no module. A model cannot learn the alias fix from a rule it never sees in an error. A required note that names the module and says to use an alias costs one diagnostic and removes a decision point from the repair loop. Concern: If B wins, the error on a type-versus-module clash names no cause, and a model may add an enum or rename the type instead of aliasing the module.
- **Minimalism: B (dissent).** Reasoning: The spec states the rule (the type wins; the module needs an alias). A required note is a diagnostic detail, and the spec does not list required notes for other resolution rules. The error for the losing form already names both sides. A tool may add the note without a spec requirement. This adds no surface to the language. Concern: A user whose module shares a name with a type gets an error about the type with no pointer to the alias fix, until a tool adds the note.

- **Minimalism: D (dissent).** Reasoning: The spec should give the help as text. Whether a tool marks it applicable is a tool rule, and the spec needs no applicability tier for one diagnostic. B makes the spec define "pure addition" (no binding named `Type`, no alias, no selective import to merge). plt, web and devops each agree that this definition is required, so B adds a new defined term to the spec. D adds none, and it still allows the tool to mark the fix applicable when the import is present. Concern: B wins 5-1 in D1, and its "pure addition" definition must then be exact, or the compiler and the LSP will read it differently.

**D2 re-vote, Q2. The head of the new grammar line.** A (`MODULE`) 3 (web, PLT, DevOps), B (`IDENT`) 3 (systems, AI/ML, minimalism). Result 3-3. The question is wording only (the name of a grammar placeholder changes no program), so it went to the writer.

- **Systems: B.** Reasoning: The head is an ordinary identifier at parse time, and resolution decides what it names. `IDENT` is an existing class and adds nothing to the grammar. `MODULE` and `MODULE_NAME` add a term that the lexer cannot back, and `MODULE` puts a name-resolution rule into a lexical grammar. The step 0 sentence states that the head must resolve to an imported module, so the grammar line needs no new term. Concern: `IDENT` in the head position reads as "any identifier", so the step 0 text must say the head resolves to an imported module, or a reader may think a local variable can qualify a type.
- **Web/Scripting: A.** Reasoning: A JS or Python dev reading the grammar sees `MODULE "." TYPE_NAME "{"` and knows at once what goes in the first slot. `TYPE_NAME` is already a role name that the lexer does not separate from `IDENT` (03_types.md:3163), so `MODULE` follows the existing precedent and adds no lexer class. `IDENT` would make the line look like the mirror of `TYPE_NAME "." IDENT "{"` and hide that resolution picks between them. The spec adds one definition line beside 3163: "`MODULE` is an `IDENT` that names an imported module." Concern: If `IDENT` wins, the step 0 sentence must carry the whole burden, and a dev may still think a local variable can qualify a type.
- **PLT: A (`MODULE`).** Reasoning: The grammar already names roles, not lexemes: `TYPE_NAME` and `IDENT` are both identifiers (03_types.md:3163). The head of this form is a role that resolution fills with an imported module qualifier, so the grammar line should name that role. `IDENT` makes the new line read as the mirror of `TYPE_NAME "." IDENT "{"`, with no sign that resolution picks between them; min's own concern (a reader may think a local variable can qualify a type) shows `IDENT` needs a repair sentence. `MODULE` needs one definition line beside 03_types.md:3163 and implies no case rule. Concern: If `IDENT` wins, the grammar shows two dotted-brace lines that differ only in head role, and the choice between them lives only in the step 0 prose.
- **DevOps: A.** Reasoning: The head is a role name, like `TYPE_NAME`, which the grammar already uses without a lexer class behind it (03_types.md:3163). `MODULE` shows in the grammar, in diagnostics and in LSP hover docs that this line applies only when resolution picks the module. `IDENT` makes the new line mirror `TYPE_NAME "." IDENT "{"` with no sign that resolution chooses between them. One definition line beside 3163 closes the gap: "`MODULE` is an `IDENT` that names an imported module qualifier". Concern: If `IDENT` wins, the step 0 sentence carries the whole rule, and a tool or reader that sees only the grammar line cannot tell the two dotted-brace forms apart.
- **AI/ML: B.** Reasoning: The spec has no token class for a module name (03_types.md:3163), and `MODULE` or `MODULE_NAME` would teach a model a lexical or case rule that does not exist. `IDENT` adds no term to learn. The step 0 sentence must say the head resolves to an imported module; that one sentence also answers the concern that `IDENT` reads as "any identifier". Concern: If the step 0 sentence is weak or missing, a model may read `IDENT "." TYPE_NAME "{"` as allowing a local variable as the head.
- **Minimalism: B.** Reasoning: `IDENT` uses a token class that the grammar already has (03_types.md:3163). `MODULE` is a role name that needs a new definition line. `TYPE_NAME` has the same status today, but that is not a reason to add a second such name for one grammar line. The step 0 sentence states that the head must resolve to an imported module, so the grammar line needs no more. Concern: If `MODULE` wins, the spec carries one more defined term, and a reader may look for a lexical rule on module names that does not exist.

**Q2 writer decision.** The panel tied 3-3, so the spec writer chose the wording: `IDENT`. The reason: both sides agree that the step 0 sentence must say the head resolves to an imported module, and `IDENT` adds no defined term. The step 0 text says that the head must resolve to an imported module, and it says that letter case does not choose between the two forms. A good example, `geo.Point { x, .. }` in a match arm, shows that resolution picks the form. The grammar lines for the two forms sit side by side, with one sentence that names both as the shape `A.B { ... }`.

### Final Spec

```blink
import geo

fn px(p: geo.Point) -> Int {
    match p {
        geo.Point { x, .. } => x
    }
}

fn area(s: geo.Shape) -> Int {
    match s {
        geo.Shape.Circle { r } => r    // error[E1007]: import the type, write Shape.Circle
        _ => 0
    }
}
```

- `mod.Type { field_patterns }` is a struct pattern at every site where the bare `Type { .. }` is valid: match arm, nested, OR alternative, `let`, `for`, parameter. E0525, E0316 and E0319 apply unchanged. (6-0)
- The parser reads `A.B {` as one dotted-brace form. Resolution decides, not letter case. A type `A` in scope makes it `Type.Variant`. Else an imported module `A` makes it `mod.Type`. The type wins a clash. This is a new step 0 before E0507, E0547 and E0300. (6-0)
- The qualified spelling of a struct is `mod.Type`. The qualified spelling of a variant is `Type.Variant`. (6-0)
- `geo.Shape { .. }` on an enum gets the same diagnostic as the bare `Shape { .. }`, named by reference. A type that the module does not declare is E0507. An unknown module gets the existing error. (6-0)
- `mod.Type.Variant` and `mod.Type.Variant { .. }` in a pattern are E1007, with help to import the type. The ERROR_CATALOG text of E1007 is the §10.8 row. (6-0)
- Q1: the E1007 fix is machine-applicable only when the module is imported and the new import line is a pure addition: no binding named `Type`, no alias for the type, no selective import of that module to merge into. (5-1)
- Q2: the grammar head is `IDENT`; the step 0 text says that the head resolves to an imported module. (3-3, writer decision)
- Q3: when `A` is both a type in scope and an imported module, the diagnostic carries a note that names the module and the alias fix. The note does not appear when `A` is only a type. (5-1)
