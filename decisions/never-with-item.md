# A `with` Item of Type `Never` — Design Rationale

Spec §4.7 says a `with` item is a `Handler[E]` or a scoped value, and that any other type is E0839. It was silent on an item of type `Never`, such as `with panic("x") as v { }` or `with todo() { }`. The compiler refused a `Never` item without `as` (E0839) and accepted it with `as`, and the generated C then failed to compile ("void value not ignored as it ought to be"). The panel was asked whether a `Never` item is legal with `as`, without `as`, or never, and what the binder is if it is legal.

## Summary

| Q | Question | Result | Vote |
|---|----------|--------|------|
| Q1 | A `with` item of type `Never` | E0839, with or without `as`, at any place in a comma list | 4-2 (PLT, DevOps dissent); Phase C 4-2, no change in Phase D |
| Q2 | The `help:` text for E0839 on a `Never` item | "this item never finishes, so the body cannot run. Remove the `with`, or write the item as a statement." | Ranked transfer after Phase D (first choices E 2, D 1, F 1, G 1, H 1) |

### Panel Deliberation

Six panelists (systems, web/scripting, PLT, DevOps/tooling, AI/ML, minimalism) deliberated in independent-proposal → debate → vote rounds. Phase A and Phase B below are excerpts with attribution. Phase C and Phase D are verbatim.

#### Phase A — Independent proposals

- **Systems:** "A `with` item dispatches on its type: `Handler[E]` installs, `Scoped` calls `enter()`/`exit(ok)`. `Never` is a subtype of both, so the dispatch has no answer. `Never` implements neither `Scoped` nor `Closeable` (03_types.md:81, closed list), and `Never` has no values, so there is no `Handler` to install. Both typing rules fail, so E0839 already applies. The spec only needs to say so. `as` changes nothing (§4.7: "`as` never changes what a `with` item does"). A `Never` item without `as` is therefore an error, and so is one with `as`. The compiler today treats them differently. That is the defect." Systems also wrote: "Rejecting at typecheck means zero lowering and zero runtime cost, and the pipeline stays total."
- **Web/Scripting:** "A `with` item of type `Never` is never legal. `as` does not change this (§4.7: `as` never changes what an item does). E0839 fires in all forms. No new code. No new warning. The binder question does not arise." Web also wrote: "A JS/Python dev reads `with panic("x") as v` as a typo. Nobody writes it on purpose. An error teaches faster than a warning that people suppress."
- **PLT:** "A `with` item of type `Never` is legal. The item diverges while it is evaluated. No handler is installed, no `enter()` runs, no `exit()` runs, and the body is unreachable. `as` binds a name of type `Never`." PLT proposed a third table row: "`Never` | Evaluate the item. It does not finish, so no handler is installed, no value is entered and the body does not run. With `as`, the name has type `Never`."
- **DevOps:** "A `with` item of type `Never` is legal. `as` makes no difference. The item diverges before any handler is installed or `enter()` runs, so the body never runs. The binder, if any, has type `Never`." DevOps also wrote: "`with todo() { }` is a real editing state. A user stubs a block while the surrounding code builds."
- **AI/ML:** "A `with` item must pick a kind: install a handler, or enter a scoped value. `Never` is the bottom type, so it fits `Handler[E]` and `T: Scoped` equally. It chooses neither kind, so no rule in the table applies. The item is an error, whether or not `as` is present." AI/ML added: "The rule is specific to `with`. It is not a rule about operands of type `Never`."
- **Minimalism:** "A `with` item has one of two typing rules: it is a `Handler[E]`, or it is a scoped value `T: Scoped`. `Never` is a subtype of every type (03_types.md:63), but a subtype relation does not pick a handler effect `E`, and `Never` has no `Scoped` or `Closeable` impl (03_types.md:79-81, a closed list). So the item fits neither row, and the existing sentence "An item of any other type is a compile error (E0839)" already covers it." Minimalism added: "Rejecting is reversible. Accepting later is a compatible change. Accepting now, then rejecting, breaks code."

#### Phase B — Debate highlights

The moderator deduped Phase A into three options: Option 1 (E0839 for every `Never` item; sys, web, aiml, min), Option 2 (legal; plt, devops), and Option 3 (legal with `as` only, today's compiler; sys-2, a fallback its author opposes).

- **PLT:** "I concede part. aiml and min are right that subsumption alone does not choose a row, and `E` in `Handler[E]` is open. My rule must not lean on subsumption. It stands as an explicit third row that names `Never`." and "I withdraw the sentence "subsumption applies"."
- **DevOps:** "I concede to plt: a third table row is cleaner than my paragraph." DevOps also wrote: "min says rejecting "deletes a special case". It moves the special case: the typechecker must now name `Never` to reject it, while Option 2 needs no name in the typing rules, only a lowering." **(dissent)**
- **Web:** "I withdraw "not a `with` special case". The spec text should state the `with` rule only, and not claim a general principle."
- **Minimalism:** "Option 2 must then say what the body's effect row is, and whether the body is type-checked at all."
- **PLT:** "**Unresolved:** whether a body under a diverging item is still type-checked. I say yes."
- **Minimalism:** "My reversibility point stands: accept later is compatible, reject later breaks code."
- **All six:** Option 3 is rejected, because `as` must not change legality. `for x in panic("x")` (NotIterable) is a separate ticket. There is no W0700 in this ticket. A note on UnresolvedMethod when the receiver has type `Never` is a separate chore.
