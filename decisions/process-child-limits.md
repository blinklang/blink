# Child Process Limits and End Reporting — Design Rationale

**Question.** How does `std.process` bound a child by time, memory and process count, and how does the result say what ended the child?

**Answer.** `process.run` and `process.spawn` take one keyword, `limits: ChildLimits`, with the fields `timeout`, `grace`, `memory` and `processes`. `ProcessResult` loses `exit_code` and gains `end: ChildEnd`, which is `Exited(Int)`, `Signaled(Int)` or `Limit(LimitKind)`. A limit that ends a child is an `Ok` result. A limit that the host cannot enforce is `Err` with `ENOTSUP`, and no child starts. `memory` and `processes` work only under a delegated cgroup v2 on Linux. `success()` is true exactly for `Exited(0)`. `process.can_limit` asks which limits the host supports, and `signal_name` gives the name of a signal. A limited child does not outlive the program, except in one stated gap.

### Panel Deliberation

Six seats voted: Systems, Web/Scripting, PLT, DevOps/Tooling, AI/ML and Minimalism. The quotes below come from the seats' own replies. Where a quote has a "[...]", the quote skips text. Phase D ran for Q6 to Q9.

#### Phase A — Independent proposals

Each seat proposed alone. The quotes are short excerpts from the seats' own proposals.

- **Systems.** "So: one `limits:` record param, a wall-clock limit on every target, memory and tasks only where cgroup v2 can enforce them (ENOTSUP everywhere else, no silent fallback), no CPU limit for now, and a new `end` field that fixes the 137 ambiguity."
- **Web/Scripting.** "Effect rows stay the same: `Process.Spawn`. The runtime keeps the clock itself, and the caller does not sleep." And: "Memory and process caps are the 10% case, so they go in a record."
- **PLT.** "Make how the child ended a sum type, so each case carries only its own data." And: "The child started and ended, and the op did its job."
- **DevOps/Tooling.** "(R1) No silent downgrade. A limit the platform cannot enforce gives Err before a child starts." And: "(R2) The result names the cause."
- **AI/ML.** "Why one record and not four flat keywords: a `handler Process` must write every parameter (decisions/child-process-env.md). With four flat keywords, each mock `run` clause grows by four params that a test almost never reads."
- **Minimalism.** "Position: add ONE primitive (a bound on wait) and ONE missing fact (which signal ended the child). Reject memory / process-count / CPU limits from std.process."

The seats differed on whether memory and process count ship (Minimalism: no), on where the deadline lives, and on the shape of the result.

#### Phase B — Debate highlights

Phase B ran one round on nine open points (D1 to D9). Quotes from the seats' own text:

- **Limits (D1).** Minimalism: "blink test can run each child under `systemd-run --user --scope -p MemoryMax=.. -p TasksMax=..` [...] That keeps the policy in the tool that owns it, and keeps std.process honest on all four targets." Web/Scripting: "A wall-clock timeout already catches spin loops. RLIMIT_CPU is per process, not per tree, so `sh -c` defeats it." Systems: "Verdict: defer CPU."
- **Where the deadline lives (D2).** PLT: "A wait-with-timeout that does not kill is a different op with a different type (it needs `Option[ProcessResult]` [...]). It must not be a mode of `wait`." PLT: "a handler must write every parameter of an op. If each limit were its own keyword, every new limit would break every `handler Process`".
- **A child that nobody waits on (D2).** Systems: "A spawned child's deadline is checked while this program is in `wait` on that child. [...] A child that nobody waits for is not ended. The runtime keeps no hidden watchdog thread." DevOps/Tooling: "the runtime enforces it even if the program never calls wait (no reaper dependency, no leak)".
- **Kill reach (D3).** Web/Scripting: "`sh -c \"make test\"` with a timeout must just work." Systems: "setpgid plus kill(-pgid), reaches grandchildren but stops Ctrl-C from reaching the child, and a parent killed by Ctrl-C then leaves an orphan that nothing will ever time out." PLT: "`run`/`wait` returns by `wall + grace`, plus a small epsilon, even if a descendant keeps the pipe open."
- **Result shape (D5).** PLT: "it stores the same fact twice, and a mock can build `exit_code: 0, end: Signaled(9)`. Illegal states become representable". Web/Scripting: "Every mock that builds `ProcessResult { out, err_out, exit_code: 2 }` today still compiles". Minimalism: "needs no field: the caller knows, because wait returned ETIMEDOUT and the caller sent the kill."
- **Memory without a cgroup (D6).** Systems: "the parent must first move itself into a leaf (`<own>/blink-self`) before it can turn on memory+pids in subtree_control. That is a side effect the user can see in /proc/self/cgroup". Web/Scripting: "The spec allows a short overshoot before the end, because a poll is not a hard cap."
- **A process-count hit (D7).** PLT: "the type has no such variant, and none can be reported." DevOps/Tooling: "the deadline then ends a spinning bomb".
- **Asking for support (D8).** Systems: "The panel may prefer a field on ProcessError instead." Web/Scripting: "retries on `ENOTSUP`. That is explicit and greppable."


#### Phase C — Final vote

The AG block, Q1 to Q5 settled in Phase C. Q6 to Q9 went to Phase D. A seat marked "moved" held another position at the end of Phase B (the seat's own words in the ballot, or the Phase B digest). The text after each vote is the seat's reasoning from its ballot, whole.

##### AG. The agreed block — AG-yes (6-0)

The block holds the rules that all six B1 replies stated: effect rows do not change; `Ok` with the output read so far when a limit ends a child; ENOTSUP for a limit the host cannot enforce, EINVAL for a bad value, `grace` = 0 legal; one `limits: ChildLimits` keyword on `run` and `spawn` and none on `wait` or `exec`; no CPU limit; a limited child in its own process group, with a kill to the group or the cgroup; the return bound of timeout + grace + a small delay, with no wait for EOF; a clean exit in the grace period ends as `Limit(Timeout)`; memory and process count only on a delegated cgroup v2 (leaf move, swap 0); no non-exhaustive marker on the end type.

- **Systems** — AG-yes. "Every item matches what I argued or accepted in B1. That includes grace = 0 meaning SIGKILL at once, and memory.swap.max = 0 as part of `memory`."
- **Web/Scripting** — AG-yes. "Every item matches my B1 position or one I moved to. Allowing grace = 0 (SIGKILL at once) is fine: it is what Python and Go users expect from a timeout."
- **PLT** — AG-yes. "Every item matches what I argued or conceded in B1. It covers the return-time bound that does not wait for EOF, ENOTSUP in place of a silent fallback, no RLIMIT_AS, and the child that catches SIGTERM and exits in the grace period ending as `Limit(Timeout)`. `grace = 0` as SIGKILL at once is a clean edge with a total meaning, and a negative grace gives EINVAL as other bad input does."
- **DevOps/Tooling** — AG-yes. "Each item matches what I argued in B1. The no-silent-downgrade rule, the group kill and the pipe bound are what make an operator able to trust the result. Allowing grace = 0 (SIGKILL at once) is a sane value, and a negative grace giving EINVAL keeps it in line with S7."
- **AI/ML** — AG-yes. "Every item matches my B1 reply. Taken together they make each limit do what its name says on every host, or fail loud with ENOTSUP. That is the property learned code needs most. A grace of 0 meaning "SIGKILL at once" is the obvious reading, and it costs nothing to learn."
- **Minimalism** — AG-yes. "Every item matches my B1 position or is a consequence of it. Allowing grace = 0 and EINVAL for a negative grace follows the existing bad-input rule. The cgroup items apply only if Q1 ships caps, and if it does, ENOTSUP plus the stated leaf-move is the honest form."

##### Q1. Which limits ship in this ticket — WMT (5-1)

WMT: `timeout`, `memory`, the process count and `grace`. W: only `timeout` now (min).

- **Systems** — WMT. "The P0 driver is the fork bomb and the OOM. Only a cgroup in the runtime both enforces them and attributes them (memory.events). systemd-run from blink test also works only on Linux, and it makes the parent guess the cause from the exit. Deferring keeps the record shape but leaves the stated "why now" unsolved."
- **Web/Scripting** — WMT. "The P0 that motivates this ticket is the fork bomb and the OOM. A timeout alone leaves blink test shelling out to systemd-run for the part it needs most. The record shape lets each cap ship now and lets CPU come later as a defaulted field."
- **PLT** — WMT. "The ticket's "why now" is the fork bomb and the OOM, and W leaves both outside the language. The ENOTSUP rule gives memory and process count a total, honest meaning on every target, and one record keeps the handler surface at one param."
- **DevOps/Tooling** — WMT. "The P0 that motivates this ticket is the fork bomb and the OOM, not the hang. A timeout-only ship leaves blink test shelling out to systemd-run, which loses the reason a child died (the transient scope's Result= is gone when the scope exits). Memory and tasks are honest here because they are cgroup-only and give ENOTSUP everywhere else."
- **AI/ML** — WMT. "The fork bomb and the OOM are the ticket's stated "why now". A timeout alone leaves blink test needing systemd-run, which cannot be learned from the Blink spec and hides the reason a child died. Memory and tasks share one mechanism and one ENOTSUP rule, so shipping them adds one table row to learn, not a new concept."
- **Minimalism** — W. "devops is right that `systemd-run --scope` loses the reason, and attribution is the part the language cannot express otherwise. But look at where the cgroup path actually works. Under cgroup v2's "no internal processes" rule, the parent can only move into a leaf and enable memory+pids if it is the sole process in its cgroup. In a normal terminal session, blink shares the terminal's scope with the shell, so the call gives ENOTSUP there too, as it does in most Docker CI and on all of macOS. So the feature works mostly when someone already started blink in its own delegated unit, which is an external wrapper anyway. That deserves its own ticket with a real "where does this return Ok" table. Wall clock + the end sum ships now, is total on four targets, and the record makes caps a non-breaking add."

##### Q2. A spawned child whose deadline passes with nobody in `wait` — E (6-0)

E: the runtime ends it at its deadline whether or not anyone waits. WT: it ends only while this program is in `wait` on it (min in B1).

- **Systems** — E. "devops's runner with 8 children shows the flaw in my Phase A rule. A child nobody is waiting on runs past its limit, keeps its memory, and then reports a "2s" timeout for a child that ran 40s. One lazily started watcher thread, blocking in epoll or kqueue, costs nothing when idle and nothing at all in a program without deadlines. It only signals, using pidfd_send_signal on Linux so a reused PID is never hit. Reaping stays in wait."
- **Web/Scripting** — E. "A deadline that holds only while someone is in `wait` depends on wait order: a runner that waits on children in turn lets later children overrun. "The child dies at 2 s" must be true however the caller waits. The thread exists only once a child with a deadline is spawned, so the program pays for it only when it uses it."
- **PLT** — E. "A limit is a property of the child. If enforcement depends on whether an observer is in `wait`, the child's lifetime depends on the observer, and the type does not show that. A runtime timer runs no Blink code, so it is not observable concurrency in the language, and a program with no deadline pays nothing."
- **DevOps/Tooling** — E. "A deadline that is enforced only during `wait` lets a test runner that waits in order leave a hung child running for minutes. The record then still says "2s timeout", which is false. A child that nobody waits on would never end. The lazy watcher thread costs nothing for programs that set no deadline."
- **AI/ML** — E. "The model writes `spawn(.., limits)`, does other work, and believes the child is bounded. "A deadline counts only while you are inside `wait`" is a rule nobody guesses, and it fails silently. Only programs that set a deadline pay the cost of the thread."
- **Minimalism** — E (I move). "plt and devops convinced me. A limit that holds only while someone is in `wait` is a property of the observer, not the child. An unwaited fork bomb with a 2 s deadline would run forever, which defeats the one limit I want to ship. sys's cost bound settles my objection: one lazy thread, started only by the first spawn with a deadline, idle in epoll/kqueue, that only signals and never reaps. A program with no deadline pays nothing."

##### Q3. Grace period — GF (6-0)

GF: a field in the record, `grace: Duration = Duration.seconds(2)`. FX: a fixed 2 s (min in B1).

- **Systems** — GF. "As a record field with a default, it costs callers and handlers nothing. A test runner wants grace near 0 and a database child wants 10 s. min's "add it later" is true but buys nothing, since the field is free now."
- **Web/Scripting** — GF. "Inside the record, the field costs callers and mocks nothing. devops's example (a child that needs 10 s to flush) is a real case that a fixed value cannot serve."
- **PLT** — GF. "A defaulted field inside the record costs no decision on the common path and no handler change. The 10-second database flush devops cites is a real caller. Min is right that the field could also come later without a break, so this is a weak preference."
- **DevOps/Tooling** — GF. "A test runner wants a short grace and a build or database child wants a long one. A field with a default costs no handler a parameter and no caller a decision. min's "add it later" is true, but the field is free now and the need is known."
- **AI/ML** — GF. "A defaulted field adds no decision in the common case, and devops shows a real caller (a database flush) that needs more than 2 s. Adding it now keeps one record literal, not a later "grace exists since vX" split in training data."
- **Minimalism** — GF (I move). "sys named the concrete pair I asked for in B1: a test runner wants a short grace (even 0), and a build tool wants a long one. Inside the record it adds no handler parameter and no decision on the common path, so the YAGNI cost I objected to is near zero."

##### Q4. A limited child after this program exits — OL (5-1)

OL: a limited child does not outlive this program. 0: no such rule; the spec states the cost (min).

- **Systems** — OL. "This closes the hole I raised myself. With its own group, a limited child no longer gets the terminal's SIGINT. Without this rule, a Ctrl-C to the parent leaves a group that nothing ends, which is the leak the deadline was meant to stop. When a limited child is live, the runtime kills its group (or its cgroup) at exit, on a panic, and on a fatal SIGINT, SIGTERM or SIGHUP, then re-raises the signal so the exit status is unchanged. That makes the cost of the own group acceptable."
- **Web/Scripting** — OL. "We are taking Ctrl-C away from limited children (AG). So a runner that a user Ctrl-C's would leave its limited children running with no deadline enforcer: the worst DX outcome, and it fills the box with orphans after every interrupted `blink test`. Killing the limited groups on program exit (plus PDEATHSIG on Linux) puts back what the user expects from Ctrl-C."
- **PLT** — OL. "A limited child that outlives the program that set its bounds keeps no bound at all, so the limit's meaning stops at the parent's exit unless the runtime ends the child. Killing the group of each live limited child on any exit the runtime sees, plus a cgroup kill where one exists, makes "a limited child does not outlive this program" hold everywhere except the gap devops names. The spec can state that gap."
- **DevOps/Tooling** — OL. "Without this rule, Ctrl-C on a test runner leaves every limited child running in its own group with no deadline enforcer. That is the orphan sys warned about, and it is the most common way an operator stops a run. PDEATHSIG on Linux, the cgroup kill, and the group kill at exit close that path on every target except a SIGKILLed parent on macOS."
- **AI/ML** — OL. "AG puts a limited child in its own process group, so a Ctrl-C of `blink test` no longer reaches its tests. Without OL, every interrupted test run leaks orphans, and no model will guess that. OL repairs the cost AG creates, and leaves only the macOS-parent-SIGKILL gap, which the spec states."
- **Minimalism** — 0. "OL holds only on some targets. PDEATHSIG is Linux-only, and macOS SIGKILL of the parent still orphans. So it is a guarantee that holds on some targets, which is the kind of quiet portability gap this panel rejected for memory. PR_SET_PDEATHSIG also fires when the spawning THREAD dies, not the process, which is a known footgun once a runtime watcher thread exists (Q2). State the cost, ship no rule, and let the test-runner panel ask for one if it needs it."

##### Q5. Result shape — R (6-0)

R: replace `exit_code` with `end: ChildEnd`. K: keep `exit_code` and add the end field (web in B1).

- **Systems** — R. "In the grace-period case that AG fixes, a child exits 0 but the end is Limit(Timeout). A kept `exit_code` would then read 0, and the `!= 0` check it was kept for reads a killed child as success. Removing the field makes every old read a compile error, and an illegal state like `Signaled(9)` with code 0 cannot be built."
- **Web/Scripting** — R (moved to R in C). "I move. plt's grace case decides it. A child that exits 0 during grace either reports `exit_code` 0 (the check fails open) or reports a made-up 143 (the field no longer holds the exit code). My "not zero" rule was the second, a synthesized number. The op API is not built, so the break costs no user code today, and `r.success()` is as short as `r.exit_code == 0`."
- **PLT** — R. "In the grace case, the keep-`exit_code` designs either fail open (`exit_code` 0 for a timed-out child) or store a made-up number in a field named exit code. The sum removes that bad state, and with the field gone every old `r.exit_code` read becomes a compile error, so the migration is safe. If K wins, my second choice is aiml's form (no default on the end field, and an `exited` constructor)."
- **DevOps/Tooling** — R. "Removing the field makes every old `exit_code` read a compile error. A child that exits 0 during the grace period can no longer read as success. The sum maps one to one onto the §06 "exactly one of signal or exit_code" record. The op API is not implemented, so the break is free now."
- **AI/ML** — R. "One field, one fact. No mock can build `exit_code: 0` with `Signaled(9)`, and mocks are where AI-written tests live. §4.4.8 is not implemented, so the migration cost is now at its minimum. Every old `r.exit_code` read becomes a compile error with a fix, which teaches the rule in one hit."
- **Minimalism** — R. "One fact, one field. plt's and sys's grace-period case proves that keeping `exit_code` fails open: a child that exits 0 during grace reads as success. Removing the field turns every old read into a compile error, the safest migration, and no user code exists yet."

##### Q6. Helper methods on ProcessResult — S (6-0 after Phase D; 3-2-1 in Phase C)

S: `success()` only. SC: `success()` and `code() -> Int?`. 0: no helper.

- **Systems** — S. "`r.success()` is the common check and costs the same as the old `exit_code == 0`. `code() -> Int?` adds nothing that `match r.end` does not already give."
- **Web/Scripting** — SC. "With `exit_code` gone, the most common lines after `success()` are "print the exit code" and "pass the code through", and `r.code() ?? -1` beats a three-arm match for that. Rust has exactly `success()` + `code() -> Option`, so the pair is familiar."
- **PLT** — S. "`success()` is one total, unambiguous predicate (`Exited(0)`), and it is the most common read. `code() -> Int?` adds a second way to observe what a `match` already gives. Min's `==` with Eq also works, but costs every caller a longer spelling of the same check."
- **DevOps/Tooling** — SC. "`success()` covers the common check. `code() -> Int?` covers the next most common read, "print the exit code if there was one", without a three-arm match at every log line. Both are fail-closed by type."
- **AI/ML** — S. "`r.success()` keeps the most common check as short as `exit_code == 0` was, with one obvious spelling. `code() -> Int?` adds a second way to read Exited, and it invites `.code().unwrap_or(0) == 0`, a check that wrongly treats a killed child as success."
- **Minimalism** — 0. "`r.end == ChildEnd.Exited(0)` with Eq derived says exactly what it means and adds no surface. `success()` is a second spelling of one comparison. `code() -> Int?` is a second way to read the Exited payload, next to `match`. If the panel wants one helper, `success()` is the one I would not fight."

##### Q7. The process-count limit is hit — K (6-0 after Phase D; 4-2 in Phase C)

K: the runtime watches the cgroup's pids events, kills the cgroup, and the end is `Limit(Processes)`. N: the fork fails, the runtime does not kill, and the end type has no variant for it.

- **Systems** — K (returned to K in C). "I return to my Phase A rule after reading B1. Under N, a fork bomb, the very case in the ticket, spins N tasks at full CPU until the deadline and then reports Limit(Timeout). The ticket asks for "the result says which limit it hit", and N answers it wrong. The runtime acts and has kernel evidence (pids.events max), so attribution is exact by plt's own rule. The kernel already kills on the memory limit, so "a hit ends the tree" is now one rule for every limit. Watching pids.events costs one fd in the existing poll loop, not a timer."
- **Web/Scripting** — K. "One rule a user learns in a minute: hit any cap, the tree ends, and `end` names the cap. Under N, a fork bomb (the ticket's exact case) is reported as `Limit(Timeout)` after a full deadline, and the test runner tells the user the test hung. The runtime acts and has kernel evidence (`pids.events`), so attribution is exact."
- **PLT** — N. "`pids.max` is a cap. It refuses a fork, and the kernel's semantics do not end the child. Turning it into a kill makes a child that handles EAGAIN correctly die for correct behaviour, and that is a different limit under the same name. A spinning bomb still ends at the timeout, and the result truthfully reads `Limit(Timeout)`."
- **DevOps/Tooling** — K. "Under N, `tasks: N` with no timeout lets a fork bomb spin at the cap forever. That is exactly the hang this ticket exists to stop. With a timeout set, the record says `Limit(Timeout)` for what was really a fork bomb. plt's make -j back-off point is real, but the callers this ticket names (test runners, job queues) want the tripwire."
- **AI/ML** — K. "With K, every limit follows one rule: a hit ends the tree, and `end` names the limit. Under N, a fork bomb reads `Limit(Timeout)` or some random exit code, so the test runner reports the wrong reason for exactly the case this ticket exists for. sys's `make -j` back-off is real, but a task cap sized for a test or a job (hundreds to thousands) is not a throttle for builds. Throttling is a different feature."
- **Minimalism** — N. "pids.max refuses a fork. It does not end anything, and a child that handles EAGAIN (make -j) keeps working, which matches systemd TasksMax. Killing on a pids.events hit is a policy the caller did not ask for, and it adds a watcher fd per child. A spinning bomb still ends at the timeout, as `Limit(Timeout)`."

- **Web/Scripting** — Y. "SIGBUS is 7 on Linux and 10 on macOS, so user code cannot write this table portably. The §06 test-runner record needs the name. Without it, every runner hand-rolls a table and gets it wrong on one OS."
- **PLT** — 0. "The name of a signal is a Display concern of the end type. The runtime already knows the platform's table when it formats `SIG<name>` in Display. - **DevOps/Tooling** — Y. "The §06 record must carry "SIGBUS" by name, and the number is 7 on Linux and 10 on macOS. Only the runtime's platform table can map it, so a Blink program cannot write this portably. A pure function with no effect is the smallest form of that."
- **AI/ML** — 0. "The use case is printing why a child died, and ChildEnd's Display already gives `SIG<name>` from the runtime's table. - **Minimalism** — 0. "The need is real (SIGBUS is 7 on Linux, 10 on macOS), but ChildEnd's Display can render `SIG<name>` per the §06 runner rule, which covers the runner. A standalone name function is a separate small API for the runner panel to request."

#### Phase D — Round 2

Phase D took Q6 to Q9. Each seat replied to the strongest point against its Phase C vote and then voted again. The reply and the concern are the seat's own words, whole. "Changed" marks a vote that differs from the seat's Phase C vote.

##### Q6 — S (6-0)

- **Systems** — S (kept S). Reply: "Reply to web ("print the exit code / pass the code through"): For printing, `"{r.end}"` already gives `exited with code 2` or `ended by signal SIGKILL`. Without `code()`, the pass-through is a match that names the non-Exited case, so the mapping is visible at the call site." Concern: "Pass-through code (a wrapper that exits with the child's code) needs an example in the spec, so users do not invent the 128+n folklore again."
- **Web/Scripting** — S (changed from SC). Reply: "Reply to aiml ("`code()` invites `.code() ?? 0 == 0`, which treats a killed child as success"): this beats my point. ### Final Spec

```blink
let lim = ChildLimits { timeout: Some(Duration.seconds(30)), memory: Some(512 * 1024 * 1024) }
let r = process.run("sh", ["-c", "make test"], limits: lim)?
match r.end {
    Exited(c) => io.println("exit {c}")
    Signaled(n) => io.println("signal {signal_name(n)}")
    Limit(_) => io.println("{r.end}")
}
```

- One keyword, `limits: ChildLimits`, on `run` and `spawn`. `wait` and `exec` take none. No effect row changes.
- Fields: `timeout`, `grace` (default 2 s, 0 allowed), `memory`, `processes`. No CPU limit.
- A limit that ends a child gives `Ok` with the output read so far. `run` and `wait` return by timeout + grace + a short delay and do not wait for EOF.
- Bad values give `EINVAL`. A limit the host cannot enforce gives `ENOTSUP`. No child starts in either case.
- A limited child has its own process group. A terminal Ctrl-C does not reach it. The kill goes to the group or the cgroup.
- `memory` and `processes` need a delegated cgroup v2 on Linux. The program moves into a leaf cgroup. `memory` sets swap to 0. A fork refused by `processes` ends the tree.
- One watcher starts at the first deadline. It only signals. A limited child does not outlive the program, except for the stated macOS gap.
- `ProcessResult.end` replaces `exit_code`. `success()` is true exactly for `Exited(0)`. There is no `code()`.
- `process.can_limit(which)` is a mockable `Process.Spawn` op. It is advice, cached for the life of the program, and it never touches a cgroup.
- `signal_name(n)` is pure and total: `"SIG<n>"` for an unknown number, as §8.10.5 says. `Display` of `ChildEnd` calls it.

### Implementation notes

- The runtime watcher thread starts lazily, at the first deadline. If it cannot start, `spawn` returns `Err` (DevOps/Tooling). It signals and never reaps.
- The cgroup path: the leaf move, `memory.max`, `memory.swap.max` = 0, `pids.max`, `pids.events` and `cgroup.kill`.
- `PR_SET_PDEATHSIG` fires when the forking thread exits, not the process. Limited children fork from a long-lived thread (PLT, AI/ML, Systems, Minimalism).
- The Darwin watcher kill and the reap share a per-child lock, so a recycled pid is never signalled (Systems).
- Limited children die before the exit code of the program is returned (DevOps/Tooling).
- The support op and `run` share one cached check (DevOps/Tooling, Systems).
- Add an `ENOTSUP` Errno constant (std names them `ERR_*`, to avoid C macro names) and the constants `SIGSEGV`, `SIGBUS`, `SIGABRT` and `SIGXCPU`.
- The `r.exit_code` help line on `NoSuchField` (E0525).
- `scripts/capped.sh` already passes `Delegate=yes`, so the gate's children can use the caps (DevOps/Tooling asked for it).
