# Type of the Name in the Ptr Write Fix — Design Rationale

### Panel Deliberation

Six panelists (systems, web/scripting, PLT, DevOps/tooling, AI/ML, minimalism) deliberated
in independent-proposal → debate → vote rounds. Phase D ran two steps: a focused debate (D1) and a silent re-vote (D2) on Q2 and Q3.

**The gap.** §2.22 said the non-inert `Ptr` write fix is `let v = rhs`, then `p.f.write(v)`, with no type on the `let`. For `p.iov_len = 18446744073709551615 - 1` (field `U64`) the applied fix gave `IntLiteralOutOfRange`, because the literal took the default type `Int`. `place = rhs` gives `rhs` the type of the place as its expected type; a `let` has no such type.

**Reading gaps.** The spec does not say whether an `@ffi.struct` may take type parameters; all six seats named this against Q5. The spec declared no `PollFd` for the §2.22 sample. A later check found that §9.1.3 declares `Pollfd` (lower-case `f`, with `events: I16`) for `poll.h`; the sample keeps the name `PollFd` that the ruling names and declares it in one line.

#### Phase A — Independent proposals

All six seats proposed that the `let` always carries the type of the field. Excerpts:

- **Systems:** "For a non-inert `rhs`, the fix binds the name WITH the field type: ... Rule text (replaces the clause at :3083): \"binds `rhs` to a new name on the line before, with the type of the field, and then writes the name: `let v: T = rhs` and `p.f.write(v)`.\"" "The fix must be equivalent to the plain struct assignment `s.u = rhs`, which already gives the literal its expected type (fact 3). Only the typed `let` keeps the meaning." "The compiler must not offer a fix that does not compile."
- **Web/Scripting:** "The new name carries the field type, when the file can spell it." "A fix that does not compile when applied is worse than no fix. A JS or Python dev clicks the quick-fix and trusts it." "The fix never adds an import and never guesses a qualified path. The file may not import the module at all, so `inner.Inner` can fail as well." (Phase A: help only when any part of the type is not in scope.)
- **PLT:** "Typing rule. `place = rhs` checks `rhs` against the type `T` of the place (checking mode). A bare `let v = rhs` has no expected type, so it synthesizes. The two forms type `rhs` differently. A fix must keep the typing of the code it replaces, as it keeps the order of evaluation." "An unsound or non-compiling fix is worse than no machine fix."
- **DevOps:** "Spelling: 1. The name as written in the field declaration, if it resolves at the fix site ... 2. Else the qualified form (`inner.Inner`), if the module is imported at the file. 3. Else no autofix." "A fix that does not compile is worse than no fix." "The CLI and the LSP should share one function so the text is the same." Each spelling case "gets a golden test".
- **AI/ML:** "Any other `rhs` ...: the machine-applicable fix binds `rhs` to a new name on the line before, with the type of the field ... When neither works, the fix is help only, and the help shows the type in the qualified form of its home module." "One rule (type always; help only when it cannot be spelled) is easier to learn from the spec and to predict."
- **Minimalism:** "The new name gets the type of the field. No new syntax, no new analysis, no new decision point." "Deciding whether `rhs` depends on its expected type needs inference at the diagnostic site. That is a new analysis for a help line. One rule that always writes the type is smaller than a rule with a test." Sample type: "`I16` (the `short` of C `pollfd`)."

All six also agreed that the open `write` argument-check bug is separate. Sys: "the typed fix is correct before and after." Plt: "The ticket for the `write` bug should also give the argument of `write` its expected type `T` (checking mode)."

#### Phase B — Debate highlights

Round 1 ran once. All six ended at "STATUS: stable, ready to vote". Excerpts:

- **Web/Scripting** moved on V1: "Five seats say to use it when the module is imported at the line. I agree. The condition is the same one I wanted: the fix must compile when applied."
- **Minimalism** moved the other way on V1 **(dissent)**: "Printing the qualified form needs a second resolve check, and the facts do not show that the check passes in that case. That is one more case in the fix code, one more golden test, and a way to print a fix that does not compile."
- **PLT**, V1: "The rule is: the compiler offers a spelling only if it resolves the spelling at the fix line with the same name lookup the checker uses." V4: "I wrote `u32` in my Phase A. That is wrong: Blink spells it `U32`. I withdraw it." V3: "An alias in the declaration prints as the alias if the alias resolves, else as its target if that resolves."
- **PLT**, generic receivers: "the typed `let` is correct only if the fix names `T` from the declaration of the field, not from the receiver after substitution. For `Ptr[Wrapper[Int]]` with field `x: A`, `T` is the substituted type."
- **DevOps**: "The tests must also assert the fix compiles after it is applied (apply-and-recompile), for every golden."
- **Web/Scripting**: "I want it written in the spec as a rule, with the reason: the `let` has no expected type from `write`, so only the annotation keeps the meaning of the original line."
- **AI/ML** and **DevOps** on V2: both rejected PLT's "type left out" help. AI/ML: "a type left out brings back the ticket bug when the user copies the lines." DevOps: "plt's "type left out" gives a typeless `let`, which is the fault in the ticket. Reject plt's form."

The moderator's ballot took five questions to Phase C and listed the points all six agreed on: the typed `let`, `T` is the declared field type, no added import, `p.x = n + 1` into `I8` reports `cannot assign Int to I8` at the `let`, the `write` bug is separate, one shared function for the CLI and the LSP, and a golden per spelling case with apply-and-recompile.

#### Phase C — Final vote

Votes, reasoning and concerns are copied from each seat's own Phase C file.

- **Q1: A type name not in scope whose module name resolves at the line** (5-1, Minimalism dissent). Options: A print the qualified form `let i: inner.Inner = mk()` after the same resolve check; B help only, print a fix only when the bare spelling resolves.
  - **Systems:** A — "The check is one name lookup, and the checker already does it. A qualified spelling that resolves compiles to the same C symbol and has no runtime cost, so the user gets a fix that runs in one more case. The \"never print a fix that does not compile\" rule is the same rule that governs the bare name, so this adds no new decision point." Concern: "If the resolve check and the checker's lookup drift apart (for example, with import aliases), the tool prints a fix that does not compile."
  - **Web/Scripting:** A — "A JS or Python dev who clicks a quick-fix expects it to work. If `import inner` is present, `inner.Inner` resolves, and the resolve check already proves the fix compiles. That gives a working fix in one more common case, and the cost is one lookup that the bare-name path already needs." Concern: "A file that imports the module only through a selective import or an alias may fail the qualified lookup in a way the golden tests do not cover, so the fix drops to help only without the user seeing why."
  - **PLT:** A — "The offer rule is one test: the spelling resolves at the fix line by the checker's own lookup. `inner.Inner` passes that test when `inner` is an imported module name, so the fix compiles and keeps the typing of the original line. A selected name and a qualified name differ only in the lookup result, so one rule covers both. Option B drops a sound fix and gives no gain in soundness." Concern: "The qualified lookup must use the same code as the checker, or the fix and the checker will disagree on some import form (alias, selective import)."
  - **DevOps:** A — "The fix passes one test: the spelling resolves at the line by the checker's own lookup. `inner.Inner` passes that test when `import inner` is present, so the user gets a fix that compiles and the quick-fix does not drop to help only for a common case. The CLI and the LSP share the function, so the extra branch costs one golden test, and apply-and-recompile proves it." Concern: "If the resolve check and the checker's lookup drift apart (for example an aliased or selective import), the tool prints a qualified fix that does not compile."
  - **AI/ML:** A — "The qualified fix is one more compiling fix for the same rule: print a spelling only if it resolves at the line. An AI that applies the fix by rote gets code that compiles, with no second edit to check. The extra case costs one lookup, and the resolve check is already needed for the bare name." Concern: "Option A adds a spelling branch that must stay in step with the checker's lookup, and a mismatch prints a fix that does not compile."
  - **Minimalism:** *(dissent)* B — "The facts show the bare spelling works and the fix never needs the qualified one to be correct. The qualified form is a second resolve path, a second golden test, and a second way to print a fix that fails to compile (for example under a selective or aliased import). Help only is complete and already exists as a tier. If tickets show the qualified fix is common, add it then." Concern: "A will make the fix code carry two spelling paths, and each path is a place where the printed text can drift from what the checker resolves."

- **Q2: The help text when no spelling resolves** (Phase C 3-2-1: A 3, B 2, C 1; see Phase D). Options: A two lines with the home-qualified type plus a note that the file must import `inner` or select `Inner` first, a private type with no public path gets the type in words; B no spelling printed that does not resolve, a note names the field and its type in words; C two lines with a placeholder type `let i: <type of Outer.i> = mk()` plus a note.
  - **Systems:** A — "A help line with a concrete, qualified type is code a user or an AI can apply once the import exists. The note says the file must import `inner` or select `Inner` first, so the text is not offered as a ready fix. A private type with no public path gets the type in words, because no valid spelling exists." Concern: "A user may paste the two lines before adding the import and get ImportNotSelected, which is the failure plt warns about."
  - **Web/Scripting:** A — "The user must be able to copy the help and finish the job. Two lines with a real, home-qualified type, plus a note that says to import `inner` or select `Inner` first, is concrete and works once the import exists. A placeholder like `<type of Outer.i>` makes a JS dev look the type up. Words only is right for a private type with no public path." Concern: "A user may paste the qualified line before adding the import and get `ImportNotSelected` or an unknown-module error, so the note about the import must come first and be easy to see."
  - **PLT:** B — "A help is code the user copies. A spelling that does not resolve at the line is wrong code, so the help must not print it. A note that names the field, its declared type in words, and the declaring module gives the user what they need and no false program text. A placeholder (C) is not code either, but it puts a non-Blink token in a code span." Concern: "A note in words is less direct than two lines of code, so users may copy the two-line form and leave out the type, which re-creates the untyped `let`."
  - **DevOps:** B — "A user and an AI copy help text, so help must not print a spelling that does not resolve at the line. Naming the field and its type in words (\"the field `i` has type `Inner`, declared in `inner`\") gives the user all facts and prints no code that fails with ImportNotSelected. A placeholder (C) is not code and gets pasted; the qualified form (A) fails when pasted." Concern: "The words-only note is less direct than a code line, so some users must write the `let` type themselves."
  - **AI/ML:** A — "An AI can apply two lines with a real type, and they are correct once the import exists. A placeholder (C) needs a lookup step and may get pasted as code. Words only (B) gives the AI the least to act on. The note that names the import or the selected name keeps the printed text from reading as a fix that works now." Concern: "If the note is easy to skip, a user or an AI pastes the qualified spelling before adding the import, and gets a compile error at the line."
  - **Minimalism:** C — "Help must not print an unresolvable name as if it were valid code, and it must not drop the type (that is the ticket bug). A placeholder plus a note naming the field and its declaring module adds no new fact the compiler lacks and cannot be pasted as working code by mistake." Concern: "A's `inner.Inner` text will be copied by users and AI tools as code, and it fails to compile until the import exists."

- **Q3: Which spelling of `T` when the declaration and the checker's form differ (an alias)** (Phase C A 4, B 2; see Phase D). Options: A the type as written in the field declaration; B the checker's printed form, an alias prints as the alias if it resolves, else as its target if that resolves.
  - **Systems:** B — "A spelling as written in the field declaration resolves in the declaring module's scope, not at the fix line. The checker's printed form with a resolve check on each name, and an alias-to-target fallback, handles that case. An alias and its target are one type with one C layout, so either spelling is sound and costs the same." Concern: "The checker's printed form may be longer or less familiar than the name the user wrote."
  - **Web/Scripting:** A — "The user wrote the declared name and knows it. An alias prints as the alias, not as a target the user never typed. This is the least surprising text in a fix." Concern: "If the alias is not in scope at the fix line, the rule falls back to the resolve check and the user may see a different spelling from the one in the field declaration."
  - **PLT:** B — "Both spellings name the same type, so soundness does not decide it; the resolve check does. The declared spelling is relative to the scope of the declaring module and may not resolve in the user's file at all. The checker's form, with the alias-then-target order, always has a defined result and gives a working fix in more cases." Concern: "Printing the target of an alias can show a name the user never wrote, and a later change to the alias will not move the fix with it."
  - **DevOps:** A — "Use the name as written in the field declaration: the user knows it and can search for it, and it matches the rest of the file's text. Both forms are the same type, but the declared name gives stable text in the diagnostic and the LSP edit. The resolve check from Q1 still runs on it, and an unresolved alias goes to Q1/Q2 as any other name." Concern: "A declared alias that does not resolve at the fix line forces the help-only path even though its target would resolve."
  - **AI/ML:** A — "The type as written in the declaration is the name the user and the spec text show, so it is the most learnable form. It is one rule with no second form to predict. The resolve check from the agreed list still runs on every name in it." Concern: "A declared alias may not resolve at the fix line while its target does, so some fixes fall back to help only where B would print a fix."
  - **Minimalism:** A — "The declared spelling is one rule with no printing of the checker's internal form. The user wrote that name and knows it. The resolve check still applies to every name in it." Concern: "B lets an alias print as its target, which the user never wrote, and the printed type then differs from the field declaration."

- **Q4: The §2.22 sample** (5-1, Minimalism dissent). Options: A `I16` and a one-line `@ffi.struct` declaration of `PollFd`; B `U32` with a declaration; C `I16`, no added declaration.
  - **Systems:** A — "`I16` matches the C `short events` of `pollfd`, which is what an FFI sample should show. A narrow signed type also shows why the annotation matters. The sample must declare `PollFd`, or it cites a type that does not exist." Concern: "The added `@ffi.struct` line makes the sample longer than the rest of §2.22."
  - **Web/Scripting:** A — "`I16` matches the C `short` of `pollfd.events`, and a small signed type shows why the annotation matters. A sample that cites an undeclared `PollFd` makes readers search for it. One `@ffi.struct` line makes the sample self-contained." Concern: "The added declaration makes the sample longer, and a later change to FFI struct syntax then has one more place to update."
  - **PLT:** A — "The sample must cite a type that exists. `I16` matches C `pollfd.events` and is not `Int`, so it shows why the annotation matters. A one-line `@ffi.struct` declaration makes `Ptr[PollFd]` and the field type check against real text. I withdraw `U32` as my pick; the type is not a typing question." Concern: "The added declaration must match the layout rules of `@ffi.struct`, or the sample itself fails to compile."
  - **DevOps:** A — "A sample that cites a type the spec never declares cannot be tested as a golden and an AI cannot check it. A one-line `@ffi.struct PollFd` with `events: I16` makes the sample self-contained and shows a type that is not `Int`. The cost is one line of spec text." Concern: "The added declaration may need a matching `@ffi.struct` syntax check, so the sample can go stale if the struct rules change."
  - **AI/ML:** A — "The sample is the text an AI learns the rule from. Type `I16` is real and not `Int`, and a one-line `@ffi.struct` declaration of `PollFd` makes the sample self-contained, so a reader sees where `T` comes from. A sample that cites an undeclared type teaches a reader to guess." Concern: "The added declaration must match the `@ffi.struct` syntax of the spec exactly, or the sample teaches wrong syntax."
  - **Minimalism:** *(dissent)* C — "The sample needs a real type that is not `Int`; `I16` is the C `short` of `pollfd.events`. A new `@ffi.struct` declaration in the sample adds spec text to fix a gap that this decision does not own. If the missing `PollFd` matters, it is a separate chore." Concern: "A leaves the sample citing a type the spec never declares, so a reader cannot see where `I16` comes from."

- **Q5: Generic receivers** (5-1, Minimalism dissent). Options: A `T` is "the type of the field at that `Ptr` type" (after substitution); B no such clause.
  - **Systems:** A — "After monomorphization, the field has one concrete type at a given `Ptr` type, and `write` takes that type. `T` must be that substituted type, or the fix writes a type that is not in the C struct. One clause states it and costs nothing at run time." Concern: "The spec does not yet say that `@ffi.struct` may take type parameters, so the clause may describe a case that cannot occur."
  - **Web/Scripting:** A — "One clause, \"the type of the field at that `Ptr` type\", is exact for any receiver and costs no extra learning for the 90% case of non-generic structs. It stops the fix from printing an unsubstituted parameter like `A`." Concern: "The clause suggests that `@ffi.struct` may take type parameters, which the spec does not say, so it may read as a promise the language has not made."
  - **PLT:** A — "For `Ptr[Wrapper[Int]]` with field `x: A`, the declared `A` is not a type at the call site. The rule must say `T` is the type of the field at that `Ptr` type, after substitution, or the fix prints a type variable. One clause removes the gap, whether or not generic structs exist today." Concern: "The spec does not say that an `@ffi.struct` may take type parameters, so this clause may state a rule for a case the language does not allow."
  - **DevOps:** A — "The fix prints the type of the field at the receiver's `Ptr` type, after substitution, because that is the type `write` takes. Printing the declared `A` would give an unbound name in the `let`. One clause removes the doubt, and the resolve check applies to the substituted names." Concern: "The spec does not say whether an `@ffi.struct` may take type parameters, so this clause may describe a case that cannot exist yet."
  - **AI/ML:** A — "One clause, \"the type of the field at that `Ptr` type\", fixes what `T` means after substitution. Without it, a reader or an AI must guess between the declared and the substituted type. The clause is short and costs nothing when no generic struct exists." Concern: "The spec does not say that an `@ffi.struct` may take type parameters, so the clause may suggest a feature that does not exist."
  - **Minimalism:** *(dissent)* B — "The spec does not say whether an `@ffi.struct` takes type parameters. A clause about substitution in a generic receiver writes a rule for a feature that may not exist. \"The type of the field\" already reads correctly for any receiver, and the compiler uses the field type at that `Ptr` type without the spec saying so." Concern: "If generic `@ffi.struct` is allowed later, the spec will have no stated rule for the fix, and the first bug will decide it."

### Final Spec

Written to sections/02_syntax.md §2.22 *Writes that are not to a place*, ERROR_CATALOG.md (the `NotAPlace` row), and llms-full.md.

- The non-inert `Ptr` write fix writes `let v: T = rhs`, then `p.f.write(v)`. `T` is the type of the field at that `Ptr` type, not the inferred type of `rhs`. The `let` has no expected type from `write`, so only the annotation keeps the meaning of the original line.
- A spelling of `T` prints only if every name in it, generic arguments included, resolves at the fix line to the same type by the checker's lookup. The fix never adds an import.
- Order: the checker's form (an alias prints as the alias if it resolves, else as its target if that resolves); a bare name that does not resolve but whose module does prints as `inner.Inner`; if no spelling resolves, help only: a note names the import to add, then the two help lines with the home-qualified type; a private type with no public path gets the type in words.
- `p.x = n + 1` into an `I8` field reports `cannot assign Int to I8` at the `let`.
- The sample adds `@ffi.struct type PollFd { fd: I32, events: I16, revents: I16 }` and shows `let events: I16 = next_events()`.
- The inert fix and the `op=` help do not change. No spec text names the open `write` argument-check bug; its fix must give the argument of `write` the expected type `T`.

### Open points

- The spec does not say whether an `@ffi.struct` may take type parameters. The Q5 clause "the type of the field at that `Ptr` type" holds for any receiver, but all six seats flag it as a candidate for a separate spec question.
- Implementation notes (not spec text): one shared function for the CLI and the LSP; a golden for each case (builtin, selected, qualified only, unresolvable, generic with an unresolved name, alias that resolves, alias that falls back to its target, selective and aliased imports, a shadowing name); each golden applies the fix and recompiles.
