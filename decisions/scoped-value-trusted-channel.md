# Scoped-Value Lints and the Audit Channel — Design Rationale

**Gap:** §5.5 lets `@trusted(audit: K)` suppress W0610 `ScopedValueWithoutWith`, and W0611 `ScopedValueEnteredTwice` follows it. The §9.1 audit-gated list holds only W0800 and W0310. Both lints can also be set under `[lints]`, which E0837 refuses for audit-gated names. The two lints were therefore neither audit-gated nor ordinary lints. Do they keep the `@trusted(audit: K)` channel? The §9.1 membership criterion decides: "only when silently suppressing it would destroy a record the language promises exists".

**Options on the table:** (A) ordinary lints: `@allow(Name)` per fn, `[lints]` per project, `@trusted(audit: K)` does not reach them, and they stay off the §9.1 list. (B) put both on the §9.1 audit-gated list, so `@allow` and `[lints]` are refused with E0837. Five more questions came out of Phase B: the closure rule in §9.1 (Q2), the pointer in §5.5 (Q3), the note when a lint fires inside a `@trusted` fn (Q4), the help-note wording (Q5) and the LSP quick fix (Q6).

### Panel Deliberation

Six panelists (systems, web/scripting, PLT, DevOps/tooling, AI/ML, minimalism) deliberated
in independent-proposal → debate → vote rounds. All text below is quoted from the panelists. Cuts are marked "…". Dissent is marked **(dissent)**.

#### Phase A — Independent proposals

All six proposed A first. Each one who listed B said they would vote against it.

- **Systems:** "**Position:** Take W0610 and W0611 off the `@trusted` channel. Both become plain warnings, reached by `@allow` and `[lints]` like any other lint." … "That test asks whether silent suppression destroys a record the language promises exists. Nowhere does the language promise a record of manual resource handling." … "What it guards against is a leaked fd or socket. That is a resource bug, not a memory-safety hole. The GC owns memory, so a missed `close()` costs a handle, never a dangling pointer." … "Every edit to a pool function makes its pin stale. The author then reruns `blink audit pin` with no new claim to check. That is busywork, and it trains people to re-pin without reading the claim." Systems also raised a concern outside the ticket: "For a `BlockHandler` that wraps a foreign handle, a second `exit()` calls `sqlite3_close` twice on one pointer. In C that is a double free, reached from safe code."
- **Web/Scripting:** "**Proposal 1 (primary): W0610 and W0611 become ordinary lints. `@allow` is the per-function channel, `[lints]` is the project channel, and `@trusted(audit: K)` does not reach them.**" … "A JS/Python dev who sees `@trusted` reads it as "unsafe/FFI-adjacent, a reviewer must look at this". Using it for "my pool returns a connection" weakens that signal. Within a year people will write `@trusted` without thinking, and that hurts W0800 and W0310 too." … "Today the codes sit on the @trusted channel and are also reachable from `[lints]`, so they are neither audit-gated nor ordinary lints. Pick one. I vote for Proposal 1." On B: "**Proposal 3 (fallback, if the panel keeps the channel):** … I oppose this, because that claim does not hold up for code that changes often and a flow lint cannot check it."
- **PLT:** "I propose that **W0610 and W0611 leave the `@trusted` channel. Both become plain warnings under `@allow` and `[lints]`.**" … "**Nothing reads the claim.** … "I manage this lifetime by hand" backs no other code. The type system, the effect system and codegen never depend on it. A record that nothing reads is a comment." … "**One annotation, one meaning.** §7's `@trusted` row says the annotation "records a claim the compiler assumes". The compiler assumes nothing from a W0610 suppression." PLT also proposed the closure rule: "Add this to §9.1: "`@trusted(audit: K)` acts only on the diagnostics in the list above (and on the FFI/`Ptr` duties §9 assigns it). It never suppresses a diagnostic outside the list. To add a diagnostic to the channel, it must meet the membership criterion.""
- **DevOps:** "**Position:** take W0610 `ScopedValueWithoutWith` off the `@trusted` channel, and take W0611 `ScopedValueEnteredTwice` off with it. Both become ordinary lints, suppressed with `@allow` and set with `[lints]`. Neither joins the §9.1 list." … "**The channels already disagree.** §5.5 says `[lints]` controls W0610. §9.1 says audit-gated names are refused in `[lints]` (E0837). Under P1, W0610 follows the §4.16.8 rules with no exceptions." DevOps also proposed the note for Q4: "If a function has `@trusted(audit: K)` and W0610 or W0611 fires inside it, add this note: … This is a note, not a new code." and "The `@allow` quick fix in the LSP is offered second and is never machine-applicable".
- **AI/ML:** "**Proposal 1 (main): take W0610 and W0611 off the `@trusted` channel. Suppress them with `@allow` only.**" … "For W0610, the language makes no such promise. A pool that closes connections by hand gives a reviewer nothing to check against an outside fact. It is a leak lint, and a leak lint is a lint an author can find noisy." … "After this change there is one rule a model can learn from §9.1 alone: "`@trusted(audit: K)` = FFI, plus the closed list in §9.1. Everything else = `@allow`."" AI/ML also proposed the §5.5 line: "**Proposal 2 (small, same ticket): state the closed list in §5.5.** One line under W0610/W0611: "Not audit-gated (§9.1)." A model that reads only §5 should not have to infer channel membership from the absence of a row elsewhere."
- **Minimalism:** "**Rule.** `ScopedValueWithoutWith` (W0610) and `ScopedValueEnteredTwice` (W0611) become ordinary lints" … "**Why, against the criterion.** … No section promises a record for manual resource management. W0610 reports a likely mistake, a leak. It does not force a record. The §9.1 text names this exact case: "A diagnostic an author merely finds noisy does not qualify."" On B: "**Proposal M2 (rejected, listed for completeness):** … This fails the gate on its face. It makes `@allow(ScopedValueWithoutWith)` an E0837, which forces an `audits.toml` record and a pin onto every pool author." On a hard gate: "If teams need a lint that a local `@allow` cannot override, that is a general `[lints]` feature (for example `"deny"`), and it gets its own ticket."

#### Phase B — Debate highlights

The moderator grouped the proposals into A, B, and five variations: V1 (PLT's closure rule), V2 (AI/ML's line in §5.5), V3 (what happens when a lint fires inside a `@trusted` fn), V4 (help-note wording) and V5 (follow-up tickets). All six ended round 1 "STABLE".

- **A against B.** Every panelist held A. **PLT:** "B would assert a record that the incomplete flow analysis cannot back: a returned value is never reported, and a callee is never followed." **Minimalism:** "No one has argued that W0610/W0611 pass the §9.1 gate, and B fails it."
- **V1, the closure rule.** **Web/Scripting:** "One condition: the clause about FFI and Ptr duties must point to §9.1.1. It must not restate those duties, because §9.1 says "stated once"." **Minimalism:** "write "the FFI/`Ptr` duties" as "its §9.1.1 region role". Then the open ticket that splits that role out has one cross-reference to edit, not a list to keep in step." **DevOps:** "Among diagnostics, `@trusted(audit: K)` suppresses only those on this list." **PLT:** "HOLD. The moderator's V3 fact supports it: `@trusted` has two jobs, suppressing audit-gated diagnostics and opening a Ptr region."
- **V2, a line in §5.5.** **AI/ML:** "If the panel thinks it is redundant, I accept merging it into the §5.5 suppression sentence: "`@trusted(audit: K)` does not suppress it (§9.1)."" **Minimalism:** "I oppose it, but softly. … If the panel wants V2, I will not block it."
- **V3, a lint inside a `@trusted` fn.** Web first proposed an error: "the result is the usual "@trusted suppresses nothing here" error." The moderator stated the facts: no such diagnostic exists, and a `@trusted` fn body is also an FFI region where `Ptr[T]` is allowed. **Web/Scripting:** "I move to devops's note. The moderator's facts make my version wrong." **DevOps:** "A "@trusted suppresses nothing here" error would fire on correct code that uses Ptr and has a W0610 by chance. That is a false positive, and it pushes users to remove an annotation they need. My note attaches only to a W0610 or W0611 that already fires, so it cannot be a false positive, and it needs no new code." **Minimalism:** "A new error code with a wrong premise costs more than this ticket can justify." **AI/ML:** "It also covers my out-of-scope flag, so I withdraw that flag."
- **V4, help-note wording.** PLT, Minimalism and Systems first used "suppress with @allow(ScopedValueWithoutWith) for manual resource management". **PLT:** "I MOVE to the aiml/web/devops wording … It states the condition under which the suppression is right, so it does not teach a blanket suppression." **Systems:** "It names the one case where the suppression is right, so it does not offer `@allow` as the default answer." **DevOps** moved the other way, to the shorter form, and kept an add-on: "in the LSP, the `@allow` quick fix comes after the `with` fix and is never machine-applicable."
- **V5, follow-up tickets.** All six asked for the three tickets. **Systems:** "a scoped type that wraps a foreign handle must have an `exit()`/`close()` that is safe to run twice. W0611 is not a proof, so a missed double `exit()` on a C handle is a double free reachable from safe code." **PLT:** "FILE it, as a bug, not friction." **Web/Scripting** on the `"deny"` level: "I am sceptical, because it adds one more concept to every lint." **Minimalism:** "YAGNI until then." **DevOps:** "It must define what `@allow` does under "deny": refuse it with a named error (my lean)".

#### Phase C — Final vote

Each voter was a freshly spawned panelist who voted alone from the Phase B digest. Votes by letter: Systems A R M NOTE C YES; Web/Scripting A R M NOTE C YES; PLT A R M NOTE C YES; DevOps A R M NOTE C YES; AI/ML A R M NOTE C YES; Minimalism A R N NOTE C YES.

A missed `close()` leaks a handle, not memory, so silent suppression destroys nothing the language promises." Concern: "a team that sets `W0610 = "error"` can be bypassed by any `@allow`.   - **Web/Scripting:** A — "Silencing W0610/W0611 destroys no promised record, so they fail the §9.1 test. `@allow` is what every Java, Rust or Python dev reaches for with a resource-leak lint, so it costs one line and needs no audit ritual."   - **PLT:** A — "Nothing in the type system, the effect system or codegen reads the claim "I manage this lifetime by hand". So silently suppressing W0610/W0611 destroys no promised record, and they fail the §9.1 criterion." Concern: "The double `exit()` hole could stay open behind a lint that authors can silence. ### Final Spec

```blink
@allow(ScopedValueWithoutWith)
fn checkout(pool: Pool) -> Connection ! IO {
    let conn = pool.take()
    pool.track(conn)
    conn
}
```

- **Q1 (6-0):** W0610 and W0611 are ordinary lints. They are warnings by default. `[lints]` sets them per project. `@allow(Name)` suppresses them per fn (§4.16.8; an fn-level `@allow` overrides `[lints]`). `@trusted(audit: K)` does not suppress them. They are not on the §9.1 audit-gated list. The clause "including `ScopedValueWithoutWith` (§5)" leaves §9.1. The §5.5 text, the ERROR_CATALOG rows and the W0611 `Cleanup` example name `@allow`.
- **Q2 (6-0):** §9.1 gains a closed-list rule: "`@trusted(audit: K)` acts only on the diagnostics in the list above (and its §9.1.1 region role). It never suppresses a diagnostic outside the list. To add a diagnostic to the channel, it must meet the membership criterion."
- **Q3 (5-1, Minimalism dissent: N):** §5.5 says "`@trusted(audit: K)` does not suppress it (§9.1)." for each lint, in the suppression sentence.
- **Q4 (6-0):** When the lint fires inside a fn that carries `@trusted`, the diagnostic gets one added note: `@trusted` does not suppress `ScopedValueWithoutWith`; use `@allow(ScopedValueWithoutWith)`. W0611 has the same note with `ScopedValueEnteredTwice`. There is no new code. The note shows only when the lint fires and the enclosing fn carries `@trusted`.
- **Q5 (6-0):** The help note for W0610 reads `note: if this function manages the lifetime by hand, add `@allow(ScopedValueWithoutWith)``. The note for W0611 reads `note: if running `exit()` more than once is intended, add `@allow(ScopedValueEnteredTwice)``. The `with` fix stays first.
- **Q6 (6-0):** The LSP offers the `with` fix first and the `@allow` fix second. The `@allow` fix is never machine-applicable (§8.6).

### Follow-ups

- A wrapper over a foreign handle must have an `exit()` or `close()` that is safe to run twice. Without it, a second `exit()` is a double free reachable from safe code.
- Whether W0611 should be an error by default.
- A general `deny` level in `[lints]` that `@allow` cannot override, for every lint.
