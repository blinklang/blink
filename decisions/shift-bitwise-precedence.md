# Shift and Bitwise Operator Precedence — Design Rationale

The ticket asked where the shifts `<<` `>>` and the bitwise operators `|` `^` `&` sit in the precedence order. The §2.19 table had no rows for `|` `^` `&` `<<` `>>` `~`. The parser put shifts above `+`, so `x << n + 1` printed 5 and `1 + 2 << 3` printed 17 (C gives 24). §3.2 said bitwise binds lower than comparison and "matches C", and it cited W0700. W0700 is UnreachableCode in the catalog; W0702 is BitwisePrecedence.

### Panel Deliberation

Six panelists (systems, web/scripting, PLT, DevOps/tooling, AI/ML, minimalism) deliberated in independent-proposal → debate → vote rounds.

Constraints given to the panel (decided earlier, not reopened): bitwise operations are operators that desugar to sealed traits and take integer types only; the shift amount is `U32`; there is no truthiness, so `&` `|` `^` on `Bool` is a type error; comparisons do not chain; `blink fmt` drops redundant parentheses; the `??` associativity mismatch is a separate bug.

Facts surfaced to the panel by the moderator:

- **F1:** `x << n + 1` with x=1, n=2 prints 5. `1 + 2 << 3` prints 17 (C gives 24).
- **F2:** W0702 fires when a `&` `|` `^` node has a direct comparison child. The AST does not record parentheses, so `(a == 0) & (b == 0)` also gets W0702, and that expression is also a type error (`bitwise & requires integer operand, got Bool`). Under the old parse, `flags & 0x0F == 0` is `flags & (0x0F == 0)`: Int & Bool, also a type error.
- **F3:** a sweep of src/, lib/, examples/ and tests/ for an unparenthesized mix of two bitwise operators, a bitwise or shift operator with arithmetic, or a bitwise operator with a comparison found only the two formatter fixtures `tests/fmt/{input,expected}_operator_parens_follow_parser_precedence.bl` (`x | y & 3`, `x << 1 + 2`, `x << 1 < y`). A regex sweep is a lower bound, not proof.
- **F4 (house rule):** spec text in sections/ states language rules, not implementation (AST layout, parser internals).

#### Phase A — Independent proposals

All six rejected the old order (shifts above `+`). All six put unary `~` in the unary row with `-` and `!`. All six retired W0702 as a standalone warning. They differed on the shift level, on the bitwise levels against comparison, and on whether a mix is an error.

- **Systems:** "Blink's current order, with shifts above `+`, is not C, Rust, Java, JS, Python, or Go. It matches no language, so it should change." Sys proposed "put `<<` and `>>` below `+` and `-`, and above comparison." and "when an operand of `<<` or `>>` is a bare arithmetic expression (`+ - * / %`), or when a shift is a bare operand of arithmetic, the compiler gives an error, not a warning." Sys kept the C order among the bitwise operators: "keep the order `&` > `^` > `|`." On the comparison pair: "With no truthiness, every unparenthesized mix of the two (`a & b == c`) is a type error. So the C order buys nothing there, and the S1 hint is the cheapest way to reduce the friction."
- **Web/Scripting:** "Put shifts below `+`/`-`, the way C, JS, Python and Rust all do. Put `&`, `^` and `|` above comparison, the way Python, Rust and Swift do, not below it as C does." "So each reading either gives the result the writer wanted or fails to compile. It never gives a wrong number quietly." Web added a paren warning for a shift mixed with `+`/`-`: "Add a lint that warns when a `<<` or `>>` node has an unparenthesized `+` or `-` child, or the reverse."
- **PLT:** "A precedence rule whose only output is a type error is a dead rule." "The sound fix is to make precedence a **partial order**, as Carbon and Fortress do: if neither operator is ranked above the other, the mix is a grammar error." "This is an **error**, not a warning: giving a meaning plus a warning is weaker than giving no meaning." PLT also proposed "`<<` and `>>` do not associate." and let arithmetic, bitwise and shift expressions be bare comparison operands.
- **DevOps:** "`|`, `^`, `&` and the shift pair `<< >>` each form a separate level. They are not ordered against arithmetic, comparison, equality, or each other." The proposed error was named `MixedOperatorPrecedence`. "The LSP offers both rewrites as code actions, but neither is marked as a safe auto-fix: the tool cannot know which one you meant." "Mark W0702 as retired in the catalog and do not reuse the number."
- **AI/ML:** "Every pair is split somewhere in the training data." "Put a binary operator from one family directly under a binary operator from another family, with no parens, and the compiler gives a **parse error**, not a warning." "Agents in edit-compile loops fix errors that come with a fix-it on the first try. They often ignore warnings, and they never see a wrong result that compiles cleanly."
- **Minimalism:** "The fewest new rules come from copying one well-known table exactly, and C is the table §3.2 already claims to match." "W0702 is dead weight. Delete it." Min's fallback was a parse error for a shift mixed with `+ -`. "Either option must delete W0702 as a standalone warning."

#### Phase B — Debate highlights

The moderator merged the six proposals into sub-questions Q1–Q7 (shift vs arithmetic; bitwise vs comparison; two different bitwise operators; bitwise vs arithmetic; the W0702 diagnostic; the formatter; how the compiler sees written parentheses). One round was enough: all six replied `STABLE: yes`.

- **Sys moved to family isolation.** "Go puts `&` at the `*` level and `|` and `^` at the `+` level. So `a & b + c` and `a | b ^ c` give different values in Go and in C, and a total order on those pairs keeps a silent misread for one group of readers. I now back family isolation (AI/ML A / DevOps D1), with PLT's well-typed reading for comparison."
- **Web moved from a warning to an error.** "I moved. Sys, PLT, DevOps and AI/ML made a case I can't wave away: for each pair, *some* language a dev or model came from reads it the other way." "Nobody finds a silent 5-instead-of-8 in five seconds." Web held the line on one pair: "This is the one place I hold the line, and the type system is the reason."
- **Min moved on Q1, Q3 and Q4.** "Sys and AI/ML met the burden of proof" Min then folded Q1 and Q4 into one sentence: "`& | ^ << >>` never mix with `+ - * / %` without parentheses." Min kept shift vs bitwise ordered: "I reject DevOps D1's extension to shift vs bitwise. Every language binds `<<` tighter than `|`, so `(d << 24) | (d << 16)` already reads one way everywhere."
- **PLT, AI/ML and Sys crossed on Q2.** PLT: "I moved from **2B to 2C**." "2B makes comparison the one place where a bitwise expression mixes without parentheses, so it is an exception to the family rule" AI/ML went the other way: "**Q2: moved from 2C to 2B (bitwise above comparison, Web A / PLT P1).**" with a condition for the formatter: "So `blink fmt` must keep, or add, parens around a bitwise or shift operand of a comparison." Sys: "**Q2 — moved from 2A to 2B; 2C is my second choice.**"
- **DevOps held 2C and moved on shift vs comparison.** "Under 2C, fmt keeps `(flags & 0x0F) == 0`, which reads the same in every language." "**One move from D1: a shift may be a bare operand of a comparison.**" "Every language in the AI/ML table binds shift tighter than comparison, so the error prevents no misread."
- **Collapse.** "PLT P1, DevOps D1 and AI/ML A are one design: shift and bitwise expressions do not mix with other binary operators unless you add parentheses." Q7 left the vote: all six said how the compiler sees parentheses is an implementation matter. DevOps: "Under the house rule, sections/ says only "mixing these operators requires parentheses"."

#### Phase C — Vote

Each panelist voted alone on V1–V9. Options were taken from the round 1 replies. V2 and V6 went to Phase D.

- **V1: a shift (`<<` `>>`) mixed with any of `+ - * / %` without parentheses is a parse error; the same shift group chains left (`a << 1 >> 2` is legal)** (6-0)
  - **Systems:** A — "`1 << n - 1` and `x << n + 1` change the shift amount without a word. The shift guard then turns that into either a wrong mask or a panic far from the cause. C, Go and Swift each give these lines a different value, so a parse error is the only rule under which a ported or generated line cannot compile to a value its author did not mean. A same-group left chain is unambiguous in every language, so it can stay legal." Concern: "hash and CRC code ported from C gets a burst of errors, though each one is mechanical to fix."
  - **Web/Scripting:** A — "For a JS or Python dev, an error with both groupings in the help line costs five seconds. A silent 5 where they expected 8 costs an afternoon. Go splits from C on `*` as well as `+`, so the whole of `+ - * / %` belongs in the rule, which also makes it one sentence to learn. `a << 1 >> 2` reads left to right in every language, so letting it chain adds no risk." Concern: "hash and varint code gets a little noisier (`(h << 5) + h`), and a dev porting from C might find that petty."
  - **PLT:** A — "Languages disagree on how a shift ranks against arithmetic (C and Rust put it below `+`; Go puts it at the `*` level; Swift puts it above), so no total order is principled. Parens remove that meaning only where it is ambiguous. A same-group left chain is unambiguous in every language." Concern: "Hash code that ports C idioms gets more parens, and authors may see that as noise."
  - **DevOps:** A — "The error covers every place where Go and C disagree, including `a << 2 * 3`. One diagnostic stops silent wrong values for code ported from any of these languages. fmt needs no special case to keep the parens, because parens between unordered groups are never redundant." Concern: "Users may see the error on hash and packing code that is correct in C and think it is noise, unless the help line shows the C grouping first."
  - **AI/ML:** A — "C, Rust and Python put shifts below `+`. Go puts them at the `*` level and Swift above it. So a model writing `x << n + 1` brings one of three readings. Any precedence rule gives a silent wrong value to some of those models, and an error with a fix-it costs one compile round. Same-shift chains are left-assoc in C, Rust and Go, so allowing them adds no risk." Concern: "models trained on C will hit this error often at first, in hash code (`h << 5 + h`), until Blink code with explicit parens is a large share of their training data."
  - **Minimalism:** A — "Go and Swift disagree with C on where shifts sit, so `x << n + 1` with `U32` operands silently gives a wrong value. No type rule can catch that, so here a new rule is justified. The same shift group chains left because every language agrees on that chain." Concern: "someone may later extend "parse error" to same-operator shift chains, which would add noise and no safety."

- **V2: bitwise (`& ^ |`) vs comparison and equality: 2A bitwise below comparison (C), 2B bitwise above comparison, 2C the mix is a parse error** (2B 3 (Sys, Web, AI/ML), 2C 2 (PLT, DevOps), 2A 1 (Min); sent to Phase D)
  - **Systems:** 2B — "under C order the only parse of `x & MASK != 0` is `Int & Bool`, so the rule can only produce a type error. Under 2B the common systems test means its one well-typed reading. A C-trained writer who means `a & (b == c)` gets a type error, never a wrong value. The vote must state that it replaces the §3.2 sentence "binds lower than comparison, matches C"." Concern: "if 2C wins instead, the most common bit test in systems code needs parens on every use, for no gain in safety."
  - **Web/Scripting:** 2B — "The C parse of `flags & 0x0F == 0` can never type-check, so 2B has no silent misread. A C/JS reading does not compile, and every reading that compiles is the one the writer meant. That makes this the most common bitwise line in real code, and under 2B it just works, as in Python and Rust. 2A keeps a rule whose only output is a TypeError, so the docs must explain "why does Blink do this?" forever." Concern: "if 2C wins instead, we make users add parens to a line that has exactly one legal meaning, and that will read as the compiler being pedantic."
  - **PLT:** 2C — "Under 2A every parse of the mix is ill-typed, so the precedence rule is dead. 2B gives the mix a meaning only through an exception to the group rule. 2C keeps the grammar uniform: a bitwise or shift operand mixes only with the logical and flow levels. It also hardens §3.2's existing "requires explicit parentheses" wording." Concern: "If 2B wins, the grammar has one irregular edge, and readers from C will still stop and wonder whether `flags & 0x0F == 0` compiles."
  - **DevOps:** 2C — "Under 2C, fmt prints `(flags & 0x0F) == 0`, which reads the same in every language. The parse error names `&` and `==`, not a Bool the user did not knowingly write. It also keeps the decided §3.2 text, which says the compiler requires explicit parentheses here." Concern: "If 2B wins, a C reader who reviews `flags & 0x0F == 0` misreads it, even though the compiler does not."
  - **AI/ML:** 2B — "Every C-order parse of a bitwise-vs-comparison mix is Int-vs-Bool, so it never type-checks. 2B therefore gives no writer from any language a silent wrong value. It accepts the Python/Rust form and the parenthesized form, and both are correct. 2C rejects a line that only had one correct reading, which wastes a compile round and adds a decision point." Concern: "a reader from C or JS may misread `flags & 0x0F == 0` in Blink source. They cannot get a wrong value, but they may lose time. V3=B limits this."
  - **Minimalism:** 2A — "The C reading of `flags & 0x0F == 0` never typechecks, so the misreading is already an error. 2A closes the footgun with zero new grammar rules and keeps the decided §3.2 text. 2C restates a rule the type system already enforces." Concern: "if 2C wins, the spec carries two rules for one mistake, and implementers must make sure the parse error fires before any confusing TypeError."

- **V3: only if 2B wins V2: B, fmt keeps (or adds) parentheses around a bitwise or shift operand of a comparison** (5-1, Sys dissent)
  - **Systems:** *(dissent)* A — "under 2B, the C reading of `flags & 0x0F == 0` cannot type-check, so dropping the parens cannot hide a wrong value. A formatter exception adds a rule with no safety gain, and fmt stays simplest when it drops only redundant parens." Concern: "a C reader reviewing fmt output may stop and doubt the bare form, though the compiler settles that doubt."
  - **Web/Scripting:** B — "JS is the largest group of devs we target, and JS uses C order. A JS dev who reads `flags & 0x0F == 0` in formatted code may parse it in their head as `flags & (0x0F == 0)`, even though the compiler does not. Prettier keeps parens around mixed bitwise operators for this reason. Letting the source be legal but printing it in the form every reader agrees on costs nothing at runtime and helps the person who reads it." Concern: "it adds a "keep these parens" exception to fmt, and the exception must stay in sync with the grammar."
  - **PLT:** B — "If 2B wins, keeping the parens makes printed code read the same to C readers and to Rust or Python readers. A formatter should not print a form that one large group of readers will misread." Concern: "This is a formatter rule that keeps parens the grammar calls redundant. That makes fmt's output depend on more than precedence."
  - **DevOps:** B — "If 2B wins, fmt must keep the parens. Otherwise the formatter prints the exact line the ticket note flags as easy for a C reader to misread. A formatter rule that adds parens costs one golden test and protects the review surface." Concern: "A keep-parens rule in fmt is a special case that the grammar does not enforce, so it can drift from the parser."
  - **AI/ML:** B — "Blink output becomes training data. If fmt prints a bare `flags & 0x0F == 0` across the corpus, it teaches models a line that is a bug in C and JS. Keeping the parens costs 2 tokens and makes the line read the same in every language." Concern: "fmt gets one exception to "drop redundant parens", and the exception must be stated precisely so the idempotency checks stay simple."
  - **Minimalism:** B — "Under 2B, a formatter that drops the parens in `(flags & 0x0F) == 0` turns clear code into the exact line a C reader misreads. A tool must never make code less clear." Concern: "B adds a formatter exception, which is one more rule for the 2B option to carry."

- **V4: a shift as a bare operand of a comparison (`x << 1 < y`) is legal and means `(x << 1) < y`** (5-1, PLT dissent)
  - **Systems:** A — "C, Rust, Go, Swift, Python and JS all bind a shift tighter than comparison, so `x << 1 < y` has one meaning everywhere. An error here would remove no misread." Concern: "none of substance. Every language agrees on this pair."
  - **Web/Scripting:** A — "Every mainstream language (C, JS, Python, Rust, Go, Swift) binds a shift tighter than `<`, so `x << 1 < y` has one reading across all of them. An error there would be noise, and noise teaches devs to stop reading errors." Concern: "none of note. If V3 B wins, fmt should treat a shift operand of a comparison the same way, for consistency."
  - **PLT:** *(dissent)* B — "For consistency with V2 and V7, the shift group is unordered against comparison as well. One rule ("shift and bitwise groups mix only with `|| && ?? |>`") is easier to state and to learn than a list of exceptions. Cross-language agreement on this pair is real, but uniformity costs only two characters." Concern: "`x << 1 < y` is unambiguous in practice, so this paren is the one most likely to feel arbitrary."
  - **DevOps:** A — "Every language in the AI/ML table binds a shift tighter than comparison, so an error here would prevent no misread. A diagnostic that fires on code nobody misreads teaches users and agents to ignore that error class." Concern: "The spec must state the exception clearly, or users will expect the same freedom for `&` under `==`."
  - **AI/ML:** A — "C, Rust, Python, Go and Swift all bind a shift tighter than `<`. The other reading (`x << (1 < y)`) shifts by a Bool, so it is ill-typed anyway. There is no split to protect against, so an error would only cost tokens and a compile round." Concern: "none of note; under V3=B, fmt should print `(x << 1) < y` as well, for the same training-data reason."
  - **Minimalism:** A — "C, Rust, Go, Swift, Python and JS all bind a shift tighter than a comparison, so `x << 1 < y` has one reading everywhere. An error here would be pure noise." Concern: "a later push for "uniform family isolation" may make this an error with no safety gain."

- **V5: two different bitwise operators (`a | b ^ c`, `x | y & 3`) are a parse error; the same operator chains left** (6-0)
  - **Systems:** A — "Go puts `|` and `^` at the same level, so `a | b ^ c` means `(a | b) ^ c` in Go and `a | (b ^ c)` in C. Clang already warns on `&` inside `|`. The corpus has no unparenthesized mixes, so the cost is zero." Concern: "bit-packing code needs a few more parens than C programmers type by habit."
  - **Web/Scripting:** A — "Go puts `^` and `|` at one level, so `a | b ^ c` splits across languages, and most Python/JS devs don't know `&` > `^` > `|` by heart. "Different bitwise operators need parens; the same one chains" is one rule. `a | b | c` stays clean for the common flags case." Concern: "code with many flags that mixes `&` and `|` grows extra parens, but that code is rare and is clearer with them."
  - **PLT:** A — "Go puts `^` and `|` on one level, so in Go `a | b ^ c` means `(a | b) ^ c`, but in C it means `a | (b ^ c)`. All the operands are integers, so no type error catches the misread. A same-operator chain is associative and safe." Concern: "`x | y & 3`, where `&` above `|` is universal, still needs parens, and some readers will call that pedantic."
  - **DevOps:** A — "Go puts `|` and `^` on one level, so `a | b ^ c` groups differently in Go and C. One rule, "different bitwise operators need parens", is easier to explain in one help line than a three-level order." Concern: "Someone may file a friction ticket for `x | y & 3`, because C, Rust and Go agree on that pair."
  - **AI/ML:** A — "Go puts `^` and `|` at one level, so `a | b ^ c` means `(a | b) ^ c` in Go and `a | (b ^ c)` in C. "Different bitwise operators need parens" is one rule with no exceptions, and the corpus has zero unparenthesized mixes, so it costs nothing." Concern: "flag code like `x | y & MASK` that a model copies from C becomes an error, which costs one round per occurrence."
  - **Minimalism:** A — "`a | b ^ c` reads `(a|b)^c` in Go and `a|(b^c)` in C, both typecheck, and the corpus has zero mixes, so requiring parens costs nothing. The same operator chains left." Concern: "this also forces parens on `x | y & 3`, where every language agrees, which is a small amount of noise for a simpler rule."

- **V6: shift vs bitwise (`d << 24 | d << 16`): A shift binds tighter than `& ^ |`, B parse error** (B 4 (Sys, PLT, DevOps, AI/ML), A 2 (Web, Min); sent to Phase D)
  - **Systems:** B — "Go puts `<<` and `&` both at the `*` level, so `a & b << c` means `(a & b) << c` in Go and `a & (b << c)` in C. With one uniform rule ("different groups need parens"), nobody has to learn which pairs are safe. The corpus already writes `(d << 24) | (d << 16)`." Concern: "`|` vs shift agrees in every language, so B costs parens on a pair that is not ambiguous."
  - **Web/Scripting:** A — "C, JS, Python, Rust, Go and Swift all bind a shift tighter than `& ^ |`, so `d << 24 | d << 16` has one reading everywhere. It is also the most common byte-packing idiom in the corpus, which copies it straight from C and Rust. An error here would make the 90% case pay for a misread that no one makes." Concern: "it adds one ordered edge to an otherwise unordered family, so the 2.19 table and its footnote must state it plainly."
  - **PLT:** B — "In Go `<<` and `&` share the `*` level, so `a & b << c` means `(a & b) << c`; in C it means `a & (b << c)`. All the operands are integers, so the split is silent. Separate groups match the uniform rule." Concern: "`(d << 24) | (d << 16)` byte-packing code gets heavier. The corpus already writes it that way, though."
  - **DevOps:** B — "Go puts `<<` and `&` on the same level, so `a & b << 2` is `(a & b) << 2` in Go and `a & (b << 2)` in C. A rule that orders shifts against `|` and `^` but not `&` would need an exception in the spec and in the error text. Every shift-and-bitwise mix in the corpus, including sha256.bl, already uses parens." Concern: "`(d << 24) | (d << 16)` chains in byte-packing code get longer. But every language agrees on shift vs `|`, so some users will see those parens as noise."
  - **AI/ML:** B — "The split is real. In Go, `&` and `<<` share the `*` level, so `a & b << c` means `(a & b) << c`, while C and Rust read `a & (b << c)`. Keeping V5–V7 as one rule ("bitwise and shift groups do not mix with each other or with arithmetic") gives a model one sentence to learn, where V6=A would need an exception. The corpus already writes `(d << 24) | (d << 16)`, as in sha256.bl." Concern: "byte-packing code gets more parens, so it costs 2 tokens per term, and models trained on C will hit it until they adapt."
  - **Minimalism:** A — "Every mainstream language binds `<<` tighter than `& ^ |`, and `(d << 24) | (d << 16)` is the most common bit-packing line. Since no reader misreads it, an error would buy nothing." Concern: "if B wins, hash and packing code grows parens that no reader needs, and people learn to ignore the errors."

- **V7: bitwise vs arithmetic (`a & b + c`, `h * 31 ^ x`) is a parse error** (6-0)
  - **Systems:** A — "`a & b + c` means `(a & b) + c` in Go and `a & (b + c)` in C, a silent split. `h * 31 ^ x` costs two parens." Concern: "none beyond the paren count."
  - **Web/Scripting:** A — "Go puts `&` at the `*` level and `|`/`^` at the `+` level, so `a & b + c` and `h * 31 ^ x` split silently between C and Go. This is the same family rule as V1, so devs learn one sentence: bitwise and shift operators do not mix bare with arithmetic." Concern: "hash code (`h * 31 ^ x`) is a common copy-paste from Java/JS and will now need parens. The error's help line must make that fix obvious."
  - **PLT:** A — "In Go `&` sits at the `*` level, so `a & b + c` means `(a & b) + c`; in C it means `a & (b + c)`. Both readings type-check. This is the worst silent split in the space." Concern: "None in my domain beyond the extra parens."
  - **DevOps:** A — "Go puts `&` at the `*` level, so `a & b + c` differs between Go and C. The sweep found no unparenthesized mix in the corpus, so the error costs nothing to adopt." Concern: "None in my domain beyond the cost of the extra parens."
  - **AI/ML:** A — "In C, `a & b + c` means `a & (b + c)`; in Go it means `(a & b) + c`. Both type-check, so the wrong reading gives a silent wrong value. That is the worst case for generated code." Concern: "hash loops (`h * 31 ^ x`) need parens; this is a small token cost."
  - **Minimalism:** A — "`a & b + c` reads `(a&b)+c` in Go and `a&(b+c)` in C/Rust, and both typecheck, so the wrong value is silent. This is the same reasoning as V1 and the same rule: "`& | ^ << >>` never mix with `+ - * / %` without parentheses"." Concern: "none beyond a little extra typing in hash code."

- **V8: diagnostics package: one named parse error `MixedOperatorPrecedence`; the help line shows both groupings; the LSP offers both rewrites, neither marked safe to auto-apply; W0702 BitwisePrecedence is retired and its number is never reused; the TypeError for `&` `|` `^` on `Bool` operands suggests `&&` or `||`** (5-1, Minimalism dissent)
  - **Systems:** A — "one named error whose help line shows both groupings is the cheapest correction for a person or an edit-compile agent. Neither rewrite is marked safe to auto-apply because the tool cannot know which one was meant. Retiring W0702 without reusing its number keeps old references unambiguous." Concern: "the `&&`/`||` suggestion on a Bool `&` must not fire where the operands have effects that a short-circuit would skip, without saying so."
  - **Web/Scripting:** A — "One named error with both rewrites shown is the best DX we can give: no warning to ignore, no confusing `requires integer operand, got Bool` as the first thing a newcomer sees. Pointing `(a == 0) & (b == 0)` to `&&` catches the real mistake a Python dev makes (`&` where they meant `and`). Retiring W0702 without reusing its number keeps old search results and docs from pointing at the wrong thing." Concern: "if LSP auto-fix marks a rewrite as safe by mistake, it can silently pick the wrong grouping. "Neither safe" must be tested."
  - **PLT:** A — "One parse-level error replaces a warning that could only fire alongside an error. It needs no AST change, because the parser sees the parens. Retiring the number keeps the catalog unambiguous. Suggesting `&&`/`||` for Bool operands is the right fix-it, because a Bool operand there almost always means the author wanted logical and/or." Concern: "The LSP's two rewrites must list both groupings in a fixed order, or tools will treat the first as the default."
  - **DevOps:** A — "One error name with both groupings in the help line lets an agent fix the line in one step. Neither rewrite is marked safe to apply, because the tool cannot know which one the user meant. Retiring W0702 without reusing its number keeps old CI logs and docs unambiguous. The `&&`/`||` hint covers the one case the parse error leaves, `(a == 0) & (b == 0)`." Concern: "The catalog and §3.2 must both change in the same commit, or users will see a spec that cites a dead code."
  - **AI/ML:** A — "A model fixes an error that names both groupings in one turn. A bare TypeError about `Bool` takes extra reasoning steps. ### Final Spec

```blink
fn low_clear(flags: U32) -> Bool {
    flags & 0x0F == 0              // (flags & 0x0F) == 0; fmt prints the parens
}

fn pack(d: U32) -> U32 {
    (d << 24) | (d << 16)          // parens required
}

let a = x << 1 >> 2                // same group chains left
let b = x | y | z
let c = x << n + 1                 // error[MixedOperatorPrecedence]
```

- Partial order: comparison and equality < five integer-operator groups (arithmetic with `* / %` above `+ -`; `<< >>`; `&`; `^`; `|`) < unary `-` `!` `~` < postfix.
- The five groups have no order among themselves. Mixing two of them without parentheses is `MixedOperatorPrecedence` (E1127). The same group chains left.
- Any integer group may be a bare operand of a comparison or equality.
- `blink fmt` prints parentheses around a bitwise or shift operand of a comparison or equality.
- The help line shows both groupings. The LSP offers both rewrites; neither is machine-applicable.
- W0702 `BitwisePrecedence` is retired. Its number is never reused.
- `&` `|` `^` on `Bool` is a `TypeError` whose help suggests `&&` or `||`.
- Spec: §2.19, §3.2. Catalog: E1127 added, W0702 retired.
