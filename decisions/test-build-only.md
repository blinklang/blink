# Which Builds Contain Test Blocks — Design Rationale

### Panel Deliberation

Six panelists (systems, web/scripting, PLT, DevOps/tooling, AI/ML, minimalism) deliberated
in independent-proposal → debate → vote rounds.

The question: `sections/02_syntax.md` said "Tests are stripped from release builds. They exist only when compiled with `blink test`." (also in the `@tags` text and the §2.20 summary list). No section defines "release build". The CLI has `--release`, `--debug` and a plain mode. Three readings of the ticket: (a) strip only under `--release`; (b) strip in every build that is not a `blink test` build; (c) strip unless `--debug`. All agree that `--release` strips and that `blink test` keeps. The readings are the ticket author's, not a panel option list.

Facts at the start (gen1 at main): plain `blink build` and `blink build --debug` kept the test symbols and `./bin --test` ran the tests. `blink build --release` kept none, and `./bin --test` ran `main` and exited 0. `blink check`, `blink build` and `blink build --release` all rejected a type error in a test body. `blink test` built each file with `--debug`. The §2.20 `?` text said test bodies are checked "in both `blink check` and `blink test`" and said nothing on `blink build`.

#### Phase A — Independent proposals

- **Systems:** "A program has two build kinds: a *test build* and a *normal build*. Only `blink test` makes a test build. A test build keeps test bodies, names, tags and the runner. Every normal build strips all of them. Normal builds are plain `blink build`, `blink run`, `--debug` and `--release`. `--debug` and `--release` change optimization level and assertions. They never change which items the program contains. This is reading (b) of the ticket." Proposed text for the Syntax line: "Test blocks exist only in a test build, which only `blink test` produces. Every other build (`blink build`, `blink run`, with any optimization or debug option) contains no test body, name, tag or runner. A normal binary gives `--test` no special meaning." On the cost: "About 7 tests and the scripts `corpus_one.sh`, `run_fmt_semantic.sh`, `test_fmt_semantic.sh` build with plain `blink build` and run `--test-json`. They must change. ... Do not weaken the rule to avoid it."
- **Web/Scripting:** "Rule: a test block (body, name, tags, runner support) is compiled only when the build is made by `blink test`. `blink build`, `blink run`, `blink build --debug` and `blink build --release` all strip it. No other build has tests." On a built binary: "A stripped binary has no test runner and reserves no flag. `./myapp --test` passes `--test` to the user's `main` like any other argument. This matters for the web case: a CLI app that has its own `--test` option (a connectivity check, for example) must work." Proposed text: "Tests exist only in the program that `blink test` builds. Every other build (`blink build`, `blink run`) omits test bodies, names and tags. A built program does not reserve any command-line flag for tests."
- **PLT:** "Elaboration: every test block is parsed and type-checked in every compilation (`blink check`, `blink build`, `blink run`, `blink test`). This is already decided. Code generation: a test block (body, name, tags, runner entry) reaches the binary only in a test build. A test build is the build `blink test` makes. No other command makes one, whatever its optimization or debug flags." Proposed text: "Tests are type-checked in every build. Their code exists only in the test build that `blink test` makes. Every other build leaves it out." Hazard recorded: "A script that runs `./bin --test` on a plain build will run `main` and report success without running any test. Silent false green is the worst failure for a gate."
- **DevOps:** "A test block (body, name, tags, runner support) exists in a binary only when the build is made for `blink test`. Every other build strips it: plain `blink build`, `blink run`, `--debug`, `--release`." Proposed a runtime rule: "a binary built without tests that gets `--test`, `--test-json`, `--test-filter` or `--test-tags` prints to stderr `error: this binary was built without tests; run \`blink test\`` and exits 2". Proposed text: "Test blocks are compiled only by `blink test`. `blink build` and `blink run` omit them, and the resulting binary has no test runner (§8.10)." Wanted "`blink build --tests` (public, listed in `--help`) rather than a hidden flag. A hidden flag that the repo's own scripts depend on is an undocumented API."
- **AI/ML:** "Rule: a test block, its name, its tags and the runner support are present only in the program that `blink test` builds. `blink build`, `blink run`, and every flag combination (`--debug`, `--release`, `--target`) strip them. `blink check` still type-checks them (already decided)." Proposed text: "Tests exist only in the program that `blink test` builds. Every other build removes them: `blink build` and `blink run`, with any flag." On `--test`: "the runner is stripped, so the flag is no longer special. The program sees `--test` as an ordinary argument. The spec should say that the binary has no test runner." On decision points: "One rule with one trigger (\"is this `blink test`?\") has no branch on flags."
- **Minimalism:** "Test blocks (bodies, names, tags, runner support) are compiled into a program only when `blink test` builds it. Every other build omits them: `blink build`, `blink run`, `blink build --debug`, `blink build --release`, and any future mode. There is no \"release build\" in the spec, so there is nothing to define." Proposed text: "Test blocks exist only in programs that `blink test` builds. No other build contains them." On `--test`: "A normal binary has no test runner, so `--test` is an ordinary program argument that `main` may read. This removes a reserved argument from every user program, which is a gain."

#### Phase B — Debate highlights

All six stated, in Phase A, that tests exist only in the build that `blink test` makes (reading (b)) and that the spec names no `--release` or `--debug` for this rule. Each seat then stated its position on five variations: V1 a normal binary given `--test`, V2 how a script gets a test binary, V3 whether the spec names the start flags, V4 the wording, V5 other points. Key shifts, in the seats' words:

- **DevOps (V1, moved):** "I change my position. In Phase A I wanted exit 2 and an error. Five seats show the cost: that makes `--test`, `--test-json`, `--test-filter` and `--test-tags` reserved words in every user program. A user CLI with its own `--test` flag (web's connectivity-check case) would break. I judge a reserved argument worse than a silent false green, because I can handle the false green in tooling (see below). I withdraw the exit-2 rule."
- **DevOps (V2, moved):** "I wanted a public `blink build --tests`. A public flag gives models and users a second way to run tests (aiml), and it adds language-adjacent surface that min asks us not to add. I accept a hidden build flag, with two conditions: it appears in contributor docs (docs/build/), and `blink build --help` hides it."
- **DevOps (V3, moved):** "Not in the spec. With V1 settled there is no user-visible rule to state. The start flags are a `blink test` internal."
- **Systems (V3, moved a little):** "The spec does not name `--test`, `--test-json`, `--test-filter` or `--test-tags`. I wrote \"gives `--test` no special meaning\" in Phase A. web's \"reserves no flag\" says the same without naming a flag the spec otherwise leaves to `blink test`. I take web's phrasing."
- **PLT (V3, moved):** "I side with web and min. The spec says only that `blink test` builds a binary that holds the tests. I drop my Phase A phrase \"starts its tests on request\" as too close to naming a protocol."
- **PLT (V1):** "I accept devops's concern (false green) as real, but fix it at the gate: `blink test` is the only supported way to run tests, and the repo scripts and the 7 tests move to it."
- **Web (V1):** "That risk lives in repo scripts, not in user programs, and the migration removes it: after the change no script calls `--test-json` on a plain build. A ratchet or a corpus check that fails when a script does so is the right guard. I do not add a language rule for it."
- **Web (V4, moved toward PLT):** "I move toward plt: add that test bodies are type-checked in every build. The Facts section shows `blink build` already does this, and it is consistent with the \"already decided\" rule."
- **AI/ML (V4, moved):** "I change my wording to take two parts from others. From plt: say tests are type-checked in every build. From web: say a built program reserves no flag for tests."
- **Systems (V4):** "plt's \"type-checked in every build\" matches the fact that `blink build --release` already rejects a bad test body. It costs compile time only, no runtime."
- **Minimalism (V4, dissent on the clause):** "I do not add plt's \"type-checked in every build\" sentence to this rule. It is a separate fact (and today only holds from the shared check pass). If the panel wants it, it should be its own line in the vote, not in this sentence." **(dissent)**
- **Minimalism (V1, V2):** "A user CLI with its own `--test` option must work." and "Hidden means not in `--help`, not in `blink llms`, not in the spec. The repo documents it in docs/build/, not in sections/."
- **Minimalism (V5, term):** "The term \"test build\": I prefer \"programs that `blink test` builds\". It needs no new term. Not a blocker." Four seats (sys, plt, devops, aiml) supported the term "test build".
- **Minimalism (for the vote):** "fallbacks plt-2 and web-2 (strip only under `--release`) should not be options. Their own authors oppose them."
- **PLT (profiles):** "If the spec later defines build profiles, it does so in §8.14 and states that profiles do not change which declarations exist."

Result of Phase B: the "Agreed" points below stood at 6-0. The seats ended on three open points: Q1, Q2 and Q3 of Phase C.

##### Agreed by all six by the end of Phase B (not voted)

- Test blocks (bodies, names, tags, runner support) exist only in the program that `blink test` builds. `blink build` and `blink run` omit them, with any option (`--debug`, `--release`, `--target`). (Ticket reading (b).)
- The spec does not name `--release`, `--debug` or any build profile, now or in §8.14. (If profiles are ever specified, that panel states that they do not change which declarations exist; no text now.)
- A normal binary has no test runner. `--test` and the like are ordinary arguments for `main`. (devops withdrew the exit-2 rule.)
- The spec does not name the test binary's start flags (`--test`, `--test-json`, `--test-filter`, `--test-tags`); they are a `blink test` internal. §8.10 output and exit codes stay as decided.
- No public `blink build --tests`. The build step of `blink test` uses an internal flag that is not in the spec, not in `blink build --help` and not in `blink llms`. (devops withdrew the public flag.)
- §8.10 gets one sentence that `blink test` builds each file with its tests.
- Implementation, not spec: the obj cache and the per-module entry-unit key carry the build kind; the repo scripts and about 7 tests move to `blink test` or the internal flag; the migration checks that no script still runs `--test-json` on a normal build.
- Fallbacks plt-2 and web-2 (strip only under `--release`) are not options; their own authors oppose them.

#### Phase C — Final vote

Each seat voted alone. Votes are verbatim (**Reasoning**, then **Concern**: what could go wrong with the option the seat expected to win).

- **Q1: The type-check clause** — Option A: state that test blocks are type-checked in every build, and change the §2.20 `?` sentence to say "in every build" in place of "both `blink check` and `blink test`". Option B: leave it out of this change. (5-1, Minimalism dissent)
  - **Systems:** A — "Type-checking costs compile time only and adds nothing to the binary, so it is free at run time. Without the clause, \"every other build omits tests\" can be read as \"the compiler skips them\". Then a test body with a type error would pass `blink build` and fail only in `blink test`. One rule for elaboration in every build also keeps the build kinds equal in everything but the emitted code." Concern: "The clause makes the spec promise a front-end behaviour that a later fast build path (skip check on unused items) could not drop without a spec change."
  - **Web/Scripting:** A — "A JS/TS dev knows that `tsc` checks code that a bundler later drops. The same dev will be confused if `blink build` skips the check on test blocks. The compiler already type-checks them in every build, so the spec only records a fact. The fix to the §2.20 `?` sentence (\"in every build\" in place of \"both `blink check` and `blink test`\") removes a line that is wrong by omission." Concern: "The clause makes a promise that holds only while every build path shares the check pass, so a future fast build mode could break it without anyone seeing the spec line."
  - **PLT:** A — "Elaboration and code generation are separate phases. \"Every other build omits tests\" names only the second. Without the clause, a reader can take omission to mean no elaboration, which contradicts the `@skip` decision (a skipped test keeps a type-checked body). The clause also matches what `blink build` and `blink build --release` do today. The §2.20 `?` sentence must change from \"both `blink check` and `blink test`\" to \"every build\", or the spec contradicts itself. Min is right that this is a separate fact. It is separate from the strip rule, but both rules govern the same construct, and one sentence in the same place keeps them from drifting." Concern: "The clause makes type-checking of test bodies a spec guarantee for every build, so a future \"fast build\" that skips test elaboration needs a spec change."
  - **DevOps:** A — "The diagnostic surface decides this. A test body with a type error fails `blink build` today, and a user must be able to find that rule in the spec. If the spec says only that other builds omit tests, a tool author can read that as \"no elaboration\", and an LSP or `blink build` could then drop the error. min is right that this is a separate fact, but it is a one-phrase fix to a sentence that is already wrong (\"both `blink check` and `blink test`\"), so the cost is small." Concern: "The clause makes `blink build` compile time depend on test bodies, and a later optimization that skips elaboration of tests in normal builds would need a spec change."
  - **AI/ML:** A — "A model that reads only \"every other build omits them\" can infer that omitted code is not checked, and then write a test body with a type error that a plain `blink build` rejects. One clause, \"type-checked in every build\", removes that guess. It costs a few tokens and adds no decision point. Today's §2.20 text names only `blink check` and `blink test`, which leaves `blink build` undefined, so the fix is also needed for correctness." Concern: "If the clause is not stated, a model may learn that a stripped test body is free to be wrong, and the error will surface only in a later `blink check` run."
  - **Minimalism:** *(dissent)* B — "The ticket asks which builds contain tests. Where the type checker runs is another fact, and §2.20 and the `@skip` decision already cover it. Adding it to this sentence mixes two rules in one line, and the check today runs from the shared check pass, so the text could go stale if that pass moves. If the panel wants the clause, it should be its own change." Concern: "With B, a reader can take \"omitted\" to mean \"not elaborated\", and a later compiler change could stop type-checking test bodies in `blink build` without breaking any spec line."

- **Q2: A sentence that a built program reserves no command-line flag for tests** — Option A: state it in §2.20. Option B: no sentence; the strip rule implies it. (5-1, Minimalism dissent)
  - **Systems:** A — "A normal binary has no runner and does no argv scan at start-up. That is a zero-cost property and the spec should state it, so no one adds an argv scan to `main` later. The sentence also tells script authors that `./bin --test` runs `main`, not tests." Concern: "The sentence fixes a promise on all future runtimes, and a later diagnostic for a mistaken `--test` (which devops wanted) would need a spec change."
  - **Web/Scripting:** A — "Many CLIs have their own `--test` option (a connectivity check, a dry run). A user who reads §2.20 looks there for the answer. One sentence (\"a built program reserves no command-line flag for tests\") settles it. Without it, a user can fairly guess that the old runner flag still exists." Concern: "The sentence is a promise about every future build, so a later runner feature that wants an argv hook must break it or find another channel."
  - **PLT:** A — "Under the rule, a normal binary has no runner, so `--test` is an ordinary argument. That is a property user programs depend on. A program that owns a `--test` option composes with the toolchain only if the spec promises it. The implication from \"a normal build has no tests\" is sound, but it holds only while the runner stays out of normal builds. The sentence fixes the interface so that a later change cannot reserve a name in every program without a spec change." Concern: "The sentence guarantees a negative about the runtime, and a future start-up hook (for example a coverage or trace flag in a normal build) must then avoid the same argv space."
  - **DevOps:** A — "I withdrew my exit-2 rule because it reserves four flag names in every user program. The sentence is the written form of that decision. Without it, a later tool change could add a \"built without tests\" error on `--test` and break user CLIs that own the flag. Users and tool authors look in the spec for this rule." Concern: "A script that runs `./bin --test` on a normal build still gets a silent false green, and the spec sentence makes that behavior permanent."
  - **AI/ML:** A — "Models write CLI programs with `--test` options (connectivity checks, dry runs). If the spec is silent, a model cannot tell whether `--test` is reserved, and the old behavior (a runner in plain builds) is in its training signal from this repo. One sentence settles this at the place where a model looks for it. It also records that a normal binary has no test runner, so the false-green hazard is written down." Concern: "The sentence makes a guarantee about argv that the compiler must keep for good, and a script that runs `./bin --test` on a normal build still gets a silent false green."
  - **Minimalism:** *(dissent)* B — "The rule \"no other build contains tests\" already implies it: with no runner, `--test` is an ordinary argument. A second sentence states the same thing again, and every restated consequence is one more line to keep in sync. The spec stays shorter if it says what is present and not what is absent." Concern: "Without the sentence, a later change could add a runner flag to normal binaries and break no spec line."

- **Q3: A defined term** — Option A: define "test build" once in §2.20 (the build that `blink test` makes) and reuse it in §8.10 and the `@tags` line. Option B: no new term; write "the program that `blink test` builds" in each place. (Phase C: A 4 — sys, plt, devops, aiml; B 2 — web, min. Final after Phase D: 5-1, Minimalism dissent.)
  - **Systems:** A — "The rule has two cases, test build and normal build, and one short term names the first case in all three places (§2.20, §8.10, `@tags`). \"The program that `blink test` builds\" is longer and repeats in each line. The term also gives the cache-key chore a name for the build kind." Concern: "A defined term can make a reader look for a flag or mode that selects it, when only `blink test` makes it."
  - **Web/Scripting:** B — "\"The program that `blink test` builds\" is plain and a reader needs no glossary. A new term \"test build\" invites the question of what a \"normal build\" is, and then someone asks for a `--test-build` flag. The phrase is used in three places only, so repeating it costs little." Concern: "The long phrase will drift into three different wordings across §2.20, §8.10 and the `@tags` line, and a reader will wonder if they name different things."
  - **PLT:** A — "Two build kinds make one total predicate: \"is this the test build?\" A name for the case lets §2.20, §8.10 and the `@tags` line refer to one definition and not restate \"the program that `blink test` builds\" in three places. The term adds no syntax and no mode name. It states the semantic fact (a different set of entry points), not a flag." Concern: "A defined term invites readers to look for a \"normal build\" counterpart and for a command that makes a test build, and the spec must keep saying that only `blink test` makes one."
  - **DevOps:** A — "Error messages, `--help` text and the LSP need one short name for this build kind. \"Test build\" is two words, and the spec can then reuse it in §8.10 and the `@tags` line without a long phrase each time. The term is also what a diagnostic can say (\"this item exists only in a test build\")." Concern: "A defined term can drift from the tool: if the internal flag gains a second user (for example a public `--tests` later), \"the build that `blink test` makes\" stops being the whole definition."
  - **AI/ML:** A — "\"Test build\" is two short words, defined once and reused in §2.20, §8.10 and the `@tags` line. A fixed term gives a model one string to match across sections, where the phrase \"the program that `blink test` builds\" appears in three slightly different forms. The term adds one name but removes repeated long phrases, so the token cost is lower over the whole spec. I pair it with the plain \"normal build\" for the opposite case." Concern: "A defined term suggests a mode that a user can select, and a model may then look for a flag to make a test build outside `blink test`."
  - **Minimalism:** B — "\"The program that `blink test` builds\" is short and needs no definition. A new term adds a name to learn and a place to define it. It would also invite a matching term, \"normal build\", and then a rule for each." Concern: "The long phrase is repeated in §2.20, the `@tags` line and §8.10, and the three copies may drift apart in wording."

#### Phase D — Round 2 (Q3 only)

Q1 and Q2 stood. Q3 split 4-2 in Phase C, so the panel ran a focused debate and a second silent vote.

##### D1 — Debate highlights

- **Systems:** "The risk is real, but the plain phrase does not remove it. \"The program that `blink test` builds\" also tells a reader that a second kind of program exists. The reader then asks the same question about the other kind. The term does not add that question. It only gives the answer a name. The term fixes the risk if the definition says who makes it. I propose the definition sentence in §2.20 states the maker in the same breath: \"A test build is the build that `blink test` makes. No other command makes one.\"" "I do not need \"normal build\" as a second defined term. The spec can say \"every other build\" and leave that case unnamed."
- **PLT:** "The risk comes from a term that sounds like a mode. It does not come from a defined term as such. The definition removes it if it ties the term to the command and nothing else." "devops's Concern (a later public flag) holds under both options. Under B the phrase \"the program that `blink test` builds\" also stops being the whole definition. Under A the amendment touches one definition. Under B it touches three lines."
- **DevOps:** "The flag risk is the same under both options. ... The term does not create that question. The ballot already fixes the answer: the build step uses an internal flag, not in the spec, not in `--help`, not in `blink llms`." "A defined term gives one string to grep and one string for a diagnostic."
- **AI/ML:** "The flag question comes from the rule, not from the name. What the name changes is drift. ... A model that sees three wordings may take them as three rules, and that is a worse failure than a flag guess." Conditions: "Define the term as \"the build that `blink test` makes. No other command makes one.\" Do not define \"normal build\". Say \"every other build\". ... Do not name a flag, a mode or a profile in the definition."
- **Web/Scripting (moved B to A):** "That fear is real, but the four A voters list the same risk in their own Concerns, and it is a risk of how we write the definition, not of the term. \"Test build\" is a name JS, Go and Rust devs already know from `go test`, `cargo test` and Jest. It does not add a mode to learn. The drift risk is certain to happen. The flag question is a risk that we can control with the wording." "I change Q3 from B to A, on two conditions for the text: 1. §2.20 defines the term once, in one plain sentence: a test build is the program that `blink test` builds. It says that no flag or other command makes one. 2. The spec does not define or use \"normal build\". The other builds are \"every other build\"."
- **Minimalism** *(dissent)*: "The drift risk is real, but a term is not the only fix. The spec can use the same words in all three places, and the three places are the three lines already named in the ballot. A review of those lines catches drift. This costs nothing in the language." "The diagnostic argument does not hold for the spec. A compiler message may say \"test build\" without the spec defining the term. Tooling vocabulary and spec vocabulary can differ." "I concede that A is a small cost. It is one definition, and the vote is 4-2 against my seat. If A wins, I ask that the definition say only \"the build that `blink test` makes\", with no mention of a mode, a flag or a \"normal build\"."

### Final Spec

```blink
fn add(a: Int, b: Int) -> Int {
    a + b
}

fn main() {
    io.println("{add(1, 2)}")
}

test "add works" {
    assert_eq(add(1, 2), 3)
}
```

`blink test` builds this file as a test build and runs `add works`. `blink build` and `blink run` make a program that has no `add works` test. All of them reject a test body that has a type error.

```blink
fn main() {
    let argv = env.args()
    if argv.contains("--test") {
        io.println("connection ok")
    }
}
```

`./app --test` runs `main`, and `env.args()` holds `--test`.

- A **test build** is the build that `blink test` makes. No other command makes one.
- Test bodies, test names, tags and the test runner exist only in a test build. Every other build, with any option, omits them.
- `blink check` and every build type-check test blocks, also a block that the build omits.
- A built program reserves no command-line flag for tests.
- The spec names no build profile and no start flag of the test binary. `blink test` reaches its build step through an internal flag that is not in the spec, `--help` or `blink llms`.
- `@tags` exist only in a test build, with the test bodies. §8.10 says that `blink test` builds each file as a test build.
- A test build of a file with no test blocks follows §8.10 as before.
