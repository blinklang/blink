# Test Runner Limits — Design Rationale

**Question.** How does `blink test` bound each test binary by time, memory and process count, and how does the report say which limit ended it?

**Answer.** `blink test` runs each test binary with a wall-clock timeout of 10 minutes, on by default on every host. `--timeout`, `--memory` and `--processes` change the limits. `none` turns a limit off, and `0` is an error. `--memory` and `--processes` are off by default and need a delegated cgroup v2. A limit that someone asks for and the host cannot apply stops the run before any build, with exit code `2`. A limit end is an `aborted` file with exactly one of `signal`, `exit_code` and `limit`. `limit` is `"timeout"`, `"memory"` or `"processes"`, and the line has one matching key: `limit_ms`, `limit_bytes` or `limit_count`. `blink.toml` has a `[test]` table with the key `timeout` only. The human output adds a `help:` line that names the flag.

### Panel Deliberation

Six seats voted: Systems, Web/Scripting, PLT, DevOps/Tooling, AI/ML and Minimalism. The quotes below come from the seats' own replies. Where a quote has a "[...]", the quote skips text. Phase D ran for Q8 only.

#### Phase A — Independent proposals

Each seat proposed alone. The quotes are short excerpts from the seats' own proposals, on flags, defaults, JSON keys and human lines.

- **Systems.** "Do something. A runner with no deadline has a liveness bug: one `while true { }` blocks the run forever." Its table: "timeout | 600 s (wall clock, per child) | every host (process group + timer)", "memory | 2 GiB, swap 0 | Linux with a delegated cgroup v2", "processes | 1024 | Linux with a delegated cgroup v2". And: "Why 1024 and not the gate's 256: the pids controller counts threads."
- **Web/Scripting.** "[...] do something, but keep the 90% case to one rule a JS/Python developer gets in 5 minutes: \"blink test kills a test file that runs longer than 10 minutes, and tells you so.\" The timeout is on by default on every platform. Memory and process count are opt-in, because a default that gives ENOTSUP in every normal terminal (and on all macOS) is a default that does not exist for most users." And: "`[test]` becomes a closed table: an unknown key is W1002 with the nearest-key help, same as `[package]`."
- **PLT.** "[...] the runner must report a limit end as a separate case, not as a signal." And: "the flag, the toml key and the NDJSON `limit` value all use the `ChildLimits` field name. [...] Then there is one word in four places: `ChildLimits.processes`, `--processes`, `[test] processes`, `\"limit\": \"processes\"`."
- **DevOps/Tooling.** "The wall-clock timeout is on by default on every host. The memory cap and the process-count cap are off by default and opt-in. If you ask for one and the host cannot enforce it, you get an error. A limit end is still `aborted`, with a third discriminator key `limit` next to `signal` and `exit_code`, so the file line mirrors `ChildEnd` one-to-one."
- **AI/ML.** "[...] do something, on by default. An agent runs bare `blink test` in a tool call that has its own wall-clock cap (often 2 to 10 min). A hung test kills that tool call with no NDJSON at all, so the agent gets nothing to act on. A runner timeout turns \"no output\" into one `file` line that names the hung test."
- **Minimalism.** "[...] limit time only. Time works on every host and solves the problem nobody plans for (a hang). Memory and process limits give ENOTSUP in a normal terminal session, so as a default they break every local run." And: "The only surface is `--timeout <dur>`. [...] There is no blink.toml key and no env var, so there is no precedence rule."

The seats differed on whether memory and process count ship, on whether they default on where the host supports them, on whether `blink.toml` carries them, on whether build workers get limits, and on the key for the cap value.

#### Phase B — Debate highlights

Phase B ran one round on a block that all six seats shared (the AG block) and on nine open points. All six seats agreed to the AG block. Quotes from the seats' own text:

- **Memory and process count (Q1).** Systems changed from AUTO (on where the host supports it) to OPT (off until asked): "The 2026-10-25 incident came from this repo's gate, and min is right that a repo chore fixes it". AI/ML changed from AUTO to OPT: "In practice AUTO is off on every dev laptop, because the terminal shell shares the cgroup." Minimalism **(dissent)** kept M0: "In a normal terminal session, AUTO does nothing: memory and process limits give ENOTSUP there, so they are off." Against M0, DevOps/Tooling: "an outside cap covers the whole run, not each file. When it fires, the kernel picks a victim and the line reads `signal: \"SIGKILL\"` with no reason. That is the ticket's third complaint unchanged."
- **A limit asked for and not applied (Q2).** Systems changed from SPLIT to STRICT: "SPLIT's \"the toml value runs without the limit, plus a warning\" is the fallback that std.process forbids, just moved one layer up." Web/Scripting changed from SPLIT to STRICT: "a toml value that runs \"where supported\" is AUTO with user-picked numbers."
- **The `[test]` table (Q3).** Systems, Web/Scripting, PLT, DevOps/Tooling and AI/ML voted for a table. Minimalism moved to a table with one key: "I move to FT, with `timeout` as the only `[test]` key." AI/ML proposed the split: "`[test]` takes only `timeout`, the one limit that works on every host. Memory and processes are flags only, because they depend on the host."
- **Turning a limit off (Q4).** Web/Scripting changed from Z (`0` turns it off) to N: "devops's `memory 0` = \"zero bytes\" settles it: one off word for three knobs beats a go habit for one." PLT: "One off-spelling for all three keys must be one that cannot be read as a value."
- **The cap value on a `file` line (Q5).** Systems changed from VI (one `limit_value` key) to VK: "in VI, `limit_value`'s unit depends on a sibling key, which a typed consumer must branch on." DevOps/Tooling changed from VI to VK: "With `limit_ms`, `limit_bytes` or `limit_count`, exactly one is present, and its name tells its unit, as `duration_ms` already does." Minimalism **(dissent)** kept V0: "The value is the same for every file in a run, so a key on each `file` line repeats one fact N times."
- **A record of the limits in force (Q6).** Systems changed from LR to L0: "Under OPT + STRICT no limit is \"asked for but not applied\", and LR existed only to report that." Web/Scripting changed from LF to LR in Phase B. PLT **(dissent)** kept LR: "[...] a reader of the NDJSON then sees the caps without the command line."
- **Limits on build workers (Q7).** Web/Scripting changed to B0: "a toml knob that only `blink test` builds obey is folklore, and a hung compiler hangs `blink build` too". DevOps/Tooling changed from BS to B0: "A compiler hang is a toolchain bug, and a limit that only `blink test` builds obey, while `blink build` ignores it, is the folklore aiml names." Systems **(dissent)** kept BS: "a hung blinkc or cc blocks the run forever: the same liveness bug as a hung test."
- **A `help:` line (Q8).** Web/Scripting, DevOps/Tooling and AI/ML argued for it. Minimalism and PLT argued against: "A help line copies flag and key spellings into a second place that must change when they change." PLT and AI/ML noted that an early example said "0 turns it off", which is wrong when `0` is an error.
- **Names (Q9).** The seats dropped the `-limit` suffix. PLT: "With `-limit` on the flag and not on the toml key, one setting has two names." DevOps/Tooling: "`--timeout` is already the bare word, not `--timeout-limit`, so `--memory` and `--processes` match it."

#### Phase C — Final vote

Each seat voted on the AG block (eight items that all seats signed in Phase B) and on Q1, Q3, Q5, Q6, Q7 and Q8. The quotes are the seats' own vote replies. A seat that changed its position says so in its own words.

##### AG block (6-0)

Concern: "when the STRICT start-up error is outside the test outcomes, the writer must change the §8.10.5 text "no other non-zero exit code" in plain words, so that no reader finds a contradiction."
- **Web/Scripting: AG-yes.** Reasoning: "Every item gives a JS/Python developer one rule each: hangs end after 10m, `none` turns a limit off, a limit you ask for is applied or the run does not start. Concern: "Under STRICT, the start-up error must name the flag or key and the host fact in one line, or it becomes the top search result for this feature."
- **PLT: AG-yes.** Reasoning: "I agree with every item in the block. The `limit` discriminator follows `ChildEnd` one to one. STRICT plus `none`-is-off means every limit someone asked for is either applied or refused, never dropped without notice. Using one word in four places keeps the flag, the key, the record value and the std.process field from drifting apart." Concern: "the writer must state the §8.10.5 change from "exactly one of two keys" to "one of three", because consumers that rely on the old rule break."
- **DevOps/Tooling: AG-yes.** Reasoning: "I signed every item in B1. Together the block fixes the MVCE hang, and nothing in it varies by host." Concern: ""an outside kill stays `signal: "SIGKILL"`" leaves the gate-OOM case with no reason given unless the repo also routes `task test` through a per-file cap. The chore min names should be filed with this ticket."
- **AI/ML: AG-yes.** Reasoning: "Every item gives an agent a single rule with no host-dependent branch. There is one discriminator on `aborted`, one spelling to turn a limit off, one word per limit in all four places, and a limit that you asked for either applies or stops the run. A model can read every item from the spec alone, on its first try." Concern: "some consumers now assume `aborted` carries `signal` or `exit_code`, and they will see neither. The writer must state that break plainly in §8.10.5."
- **Minimalism: AG-yes.** Reasoning: "Every item matches my B1 reply. A 10m timeout that is on by default fixes the hang, which no one plans for. `none` is consistent with "a duration needs a unit". STRICT keeps the std.process rule that there is no silent fallback. One word in four places means a user learns one name." Concern: "the "exactly one of" set now has three keys, so a consumer that looks only for `signal` or `exit_code` finds neither, and the writer must say this plainly."

##### Q1. Memory and process count in this version (OPT 5-1)

- **Systems: OPT.** Reasoning: "min is right that a repo chore fixes our gate. But a user's own `blink test` has no `capped.sh`, and only the runner can put a cap on each binary and name the file that hit it (devops). The cost is small: the runtime already has the mechanism, and the runner passes a ChildLimits value through." Concern: "users will find out that memory and processes give ENOTSUP in a normal Linux terminal, so the error text must say what to do (a delegated cgroup), not only what is missing."
- **Web/Scripting: OPT.** Reasoning: "Only the runner can cap each binary and write `limit: "memory"` on the right file. A user outside this repo has no capped.sh, so M0 gives them only systemd-run folklore. Off by default keeps a laptop and CI running the same command the same way." Concern: "Users who do not know about the flag get no protection against a runaway test, so the docs must show the flag next to the timeout default."
- **PLT: OPT.** Reasoning: "only the runner can cap one binary and write `limit: "memory"` on the right `file` line (devops). An outside cap, the M0 route, leaves the ticket's "SIGKILL, no reason" complaint unchanged. Off by default keeps one meaning per command on every host." Concern: "the 2026-10-25 kind of incident stays unprotected unless the repo adds the flags to its own `task test` call, so that chore must be filed."
- **DevOps/Tooling: OPT.** Reasoning: "only the runner can cap each binary and write `limit: "memory"` / `"processes"` on the file that hit the cap. An outside cap kills a victim the kernel picks and reports a bare SIGKILL, the ticket's third complaint. Off by default keeps the same command meaning the same thing on every host. The repo's gate opts in with one flag." Concern: "a terminal user on a plain Linux session still has no fork-bomb protection by default. The docs must say so and name `systemd-run --user --scope -p Delegate=yes` as the way to get it."
- **AI/ML: OPT.** Reasoning: "Only the runner can kill one binary at its cap and write `limit: "memory"` on the `file` line of the right file. A per-child wrapper in the repo gives a reason only on stderr, in the repo's own format, so an agent has no NDJSON to act on. Off by default keeps `blink test` the same on every host." Concern: "users who never pass the flags still have no guard against a fork bomb outside the gate."
- **Minimalism: M0.** Reasoning: "Memory and process limits give ENOTSUP in a normal terminal session, so as an opt-in they serve only users who can already cap the run with systemd-run, a container or CI limits. The incident that opened the ticket is a repo chore: route the children of `task test` through `scripts/capped.sh --child`. OPT adds two flags, two `limit` values and a start-up error path for that small group. devops is correct that only the runner can name the file that hit the limit. That is a good reason to add the limits later, when a user outside this repo asks." Concern: "under OPT, the size format (units, `none`) and the STRICT start-up error are new surface that every later `[test]` or `blink build` limit must copy, so the writer must spell them out exactly once."

##### Q3. The `[test]` table (T1 5-1)

- **Systems: T1 (changed from T3).** Reasoning: "Under OPT, a toml `memory` key only adds a cap that no default needs, and the place that wants a cap is CI, which can pass a flag. aiml's point decides it for me: with T1 no checked-in file can stop a macOS contributor's run, and STRICT then applies only to what a person typed on this host. The timeout is the key that a project must be able to raise, so it alone goes in `[test]`." Concern: "a user who writes `[test] memory = "2G"` gets only the warning W1002 and no cap, so the W1002 help must say that `--memory` is a flag only."
- **Web/Scripting: T1 (I move from T3).** Reasoning: "aiml is right, and it is my Phase A concern again. Under STRICT, a checked-in `memory = "2G"` locks every macOS contributor out of bare `blink test`. That is the first Stack Overflow question this feature would make. With T1, `[test] timeout` serves the slow-test repo, and caps go in the CI script, the only place where they always apply." Concern: "A `memory` key is W1002 under T1, so the W1002 help must say "use --memory" and not offer only a nearest key."
- **PLT: T3.** Reasoning: "under T1, a `memory = "2G"` line in `[test]` is W1002. The toolchain reads the section without the key and runs with no cap, so a cap the user asked for is dropped with only a warning. That is the silent fallback that STRICT was voted to forbid, moved to a new place. Under T3 the key means one thing everywhere: it is applied, or the run fails and says why. The macOS lockout is the project's choice to make, as sys says." Concern: "if T3 wins, the STRICT error on a toml value must name the key with its span, so the macOS user sees at once which checked-in line to move to CI."
- **DevOps/Tooling: T1 (I move from T3).** Reasoning: "aiml's point turns my own B1 argument into a rule. If caps on CI only belong in the CI script, then a `[test] memory` key exists only to lock out a macOS or terminal contributor under STRICT. `timeout` is the one value that must be in toml, so that a bare `blink test` passes on a project with a valid slow file. A Linux-only project that wants caps puts them in the Taskfile or CI script, where they apply to the host that has the cgroup." Concern: "a `memory` key in `[test]` gets only W1002 (a warning), so a user who wrote it may think a cap is on. The W1002 note should say that memory and processes are flag-only."
- **AI/ML: T1.** Reasoning: "`timeout` is the one limit that works on every host. Putting it in the repo lets a bare `blink test` (from an agent or from CI) pass a suite that is slow for a valid reason. A `memory` value checked into the toml either locks out every macOS and terminal contributor (under STRICT) or invites a per-host exception. Flags only for host-dependent caps makes "put it in the CI script" the only path." Concern: "if T3 wins, a project that adds `memory = "2G"` breaks `blink test` for every contributor who is not on a delegated cgroup. The error must name the CI-script remedy."
- **Minimalism: T1.** Reasoning: "The `[test]` section exists so that a bare `blink test` passes for a project whose tests are slow for a good reason (aiml's point). That point applies only to the timeout. A memory key checked into toml stops every macOS or plain-terminal contributor under STRICT, so the only safe place for one is the CI script. T1 makes that the only path, not just advice. A smaller closed table also leaves less to check." Concern: "if T3 wins, one `memory = "2G"` line stops every run on macOS, and the error must name the toml span and tell the user to move the cap to the CI flags."

##### Q5. The cap value on a limit `file` line (VK 5-1)

- **Systems: VK.** Reasoning: "The agent reading a killed file's line needs the value on that line to decide between "raise the limit" and "find the leak". It may never see a `run` line, or may read one file's lines out of the stream. Each key has one unit, so a typed consumer never branches on a sibling key. VN gives the same data; min's point that the value repeats is true but cheap, since it appears only on aborted lines." Concern: "if LR also wins, the writer must keep the key names of the two consistent, or a consumer learns two spellings for one value."
- **Web/Scripting: VK.** Reasoning: "One unit per key, so a consumer never reads `limit` to learn how to read the number. The `file` line stands alone in a CI log and needs no lookup in another record. VN is the same behavior with other names, and I accept it if it wins." Concern: "Three optional keys, of which a line has exactly one, is a shape that a typed consumer must model as a union. The writer must state "exactly one, matching `limit`"."
- **PLT: VK (I move from VN).** Reasoning: "VK and VN behave the same: one key per unit, and the name gives the unit. Four seats chose VK, and its shared `limit_*` prefix reads as the payload of `limit`. VN's only advantage was matching the LR key names, and that matters only if LR wins." Concern: "when VK and LR both ship, the same cap has two names (`limit_ms` on the `file` line and `timeout_ms` in the `run` limits object). The writer should state how they map, or align the names."
- **DevOps/Tooling: VK.** Reasoning: "the reader of a CI log or an agent often did not set the value. The default, toml or a flag did, and the reader needs the number to choose between "raise it" and "find the leak". VK gives each key one unit, as `duration_ms` does, so no consumer branches on the kind to read a number. min's "repeats one fact N times" costs a few bytes, and only on lines that show a limit end." Concern: "if the std.process count word changes, `limit_count` stays generic, which is fine, but the writer must not invent a fourth `limit_*` key for it."
- **AI/ML: VK.** Reasoning: "The key name gives the unit, so the agent needs no table of units by kind. The value sits on the line the agent acts on. Without it, the agent must rebuild precedence (flag > toml > default) to choose between "raise the cap" and "fix the hang". Against V0: repeating one fact on a rare line costs nothing, while a lookup costs a decision." Concern: "VK and VN act the same, so whichever wins, the writer must keep the key names fixed and never let them depend on the kind."
- **Minimalism: V0.** Reasoning: "The cap is one fact per run, and a key on every limit `file` line repeats it. The human line already prints the value. If the stream must carry it, LR carries it once. Of the per-line options, VK is better than VN because no key's unit depends on the kind." Concern: "if VK wins and LR also wins, the stream holds the same number in two shapes (`limit_ms` and `timeout_ms`), and the two can drift apart."

##### Q6. A record of the limits in force (L0 5-1)

- **Systems: L0.** Reasoning: "Under OPT + STRICT, the limits in force are the limits asked for, and VK puts the value on the line that hit it. devops's CI question ("was the cap on?") gets its answer from the killed file's line. If CI kills the whole `blink test`, LR's `run` line does not exist either." Concern: "none of substance; if LR wins, use the VK unit names in it."
- **Web/Scripting: L0 (I move from LR).** Reasoning: "Under OPT + STRICT, no limit is asked for and then not applied (sys). VK already puts the value on each limit end, where a reader looks when a file dies. A `limits` object on the `run` line repeats facts the caller set, and as devops notes it is missing when CI kills the whole run." Concern: "A reader of a green run cannot tell from NDJSON alone whether the timeout was on, but nobody asks that of a green run."
- **PLT: LR.** Reasoning: "the 10m default, the toml and the flag combine through precedence. A reader of the NDJSON (a CI log, an agent) does not see the command line, so one object on the existing `run` line answers "was the cap on, and at what value" for files that ended without a limit too. VK answers it only for files that hit one. LF adds a record kind for the same facts." Concern: "if L0 wins, a consumer cannot tell "no memory cap" from "memory cap set and not hit" in the stream."
- **DevOps/Tooling: L0 (I move from LR).** Reasoning: "under OPT + STRICT + T1, the limits in force are what the flags, `[test] timeout` and one documented default say, and no host drops a requested cap. VK puts the cap on every line where it matters. LR was there to report "asked for but not applied", and that case no longer exists. That is sys's and aiml's point, and I accept it." Concern: "with L0, a run killed from outside gives no record of whether a runner memory cap was on. A reader must infer it from the missing `limit` key, which is weak, but acceptable for MVP."
- **AI/ML: L0.** Reasoning: "Under OPT, STRICT and T1, the limits in force follow only from the command line, `[test] timeout` and one documented default. No host decides anything, so a record of the limits only repeats input the agent can already see. The cap value an agent needs comes with each limit end (Q5)." Concern: "devops's case of a whole run killed by CI before any `file` line is real. The reply there is the per-binary timeout, not a record of the limits."
- **Minimalism: L0.** Reasoning: "sys has it right. Under OPT and STRICT, a limit is never "asked for but not applied", and that was the case LR was for. The values in force are the default, the toml or the flag, all visible to the caller. devops' question "was the cap on?" has its answer in the `limit` key of the file that hit it." Concern: "if LR wins, `null` must mean only "off" and never "unknown", or a reader cannot tell a limit that was off from one that was not reported."

##### Q7. Limits on build workers (B0 5-1)

- **Systems: BS.** Reasoning: "A build worker is a child of `blink test`. A hung blinkc, or a cc stuck on a pathological generated file, blocks the run forever, which is the same liveness bug this ticket fixes for test binaries. The fix is the same ChildLimits value on one more spawn, and `build_failed` with an `error` diagnostic already exists to report it. `error`, not `ice`, because the runner cannot tell a hang from a slow vendored compile." Concern: "if B0 wins (likely), `blink test` still has a path that never returns, so the follow-up ticket for build-step limits must be filed now and linked to this one, not left as a note."
- **Web/Scripting: B0.** Reasoning: "A toml or flag limit that only `blink test` builds obey is folklore (aiml), and a hung compiler also hangs `blink build`. The fix belongs to both commands together. I keep asking for the follow-up ticket." Concern: "Until that ticket lands, a hung build worker still blocks `blink test` forever, and the user cannot tell it apart from a hung test."
- **PLT: B0.** Reasoning: "the seats do not agree on the severity of a build-limit end (`ice` vs `error`), so the behavior is not settled. If one `timeout` key governed both build workers and test binaries, it would have two meanings and two outcomes. A separate ticket that covers `blink build` and `blink test` together is the right place." Concern: "a hung `blinkc` or `cc` still blocks `blink test` forever until that follow-up ticket lands, so it must be filed now."
- **DevOps/Tooling: B0.** Reasoning: "build limits need their own call on severity (`error` vs `ice`), and they should cover `blink build` and `blink run` too, not only the builds `blink test` starts. That belongs in its own ticket, which I ask the team to file now. The incident was a test binary, not a build." Concern: "sys is right that B0 leaves a known path where a hung blinkc or cc can hang the run forever. The follow-up ticket must not sit in the backlog."
- **AI/ML: B0.** Reasoning: "Build limits need their own severity ruling (a vendored native dependency makes a long compile legitimate), and they must hold for `blink build` and `blink run` as well. A knob that only `blink test` builds obey is folklore. A follow-up ticket for build-step limits across the three commands is the right place." Concern: "until that ticket lands, a hung `blinkc` or `cc` still blocks `blink test` forever with no output."
- **Minimalism: B0.** Reasoning: "A hung compiler is a toolchain bug. A user cap hides it, and a cap can kill valid long native builds. The seats that wanted build limits did not agree on the shape of a build-limit end (`ice` or `error`). A follow-up ticket that covers `blink build` and `blink test` together is the right scope." Concern: "until that follow-up lands, a hung `blinkc` or `cc` still blocks `blink test` forever, with no `running` to name it."

##### Q8. A `help:` line under a limit end (H, 4-2 in this phase)

- **Systems: H.** Reasoning: "An agent or a new user acts on the help line, and its cost is small. min's point (a second place to update) is real but is a doc-consistency check, not a design cost." Concern: "under T1 the help line for memory and processes must name only the flag, never a toml key."
- **Web/Scripting: H.** Reasoning: ""How do I change it" is the first question after "timed out". jest answers it in the message, and that is why its timeout question has one answer. The text is human output only, so NDJSON consumers do not see it." Concern: "min's drift point is real. The writer should generate the help text from the same names as --help, or a test must pin it."
- **PLT: H0.** Reasoning: "the limit-end line already names the cause and the value. A help line copies flag and key spellings into a second place that must change when they change (min). Low stakes." Concern: "if H wins, the text must use `none` (never `0`), and under STRICT it must not suggest a key that this host cannot apply."
- **DevOps/Tooling: H.** Reasoning: "the help line prints only on a limit end, and it answers the next question a human or agent asks: which knob, and how to turn it off. Without it they guess `--timeout=0`, `--test-timeout` or an env var, and each wrong guess costs one more run. rustc and cargo set this style, and the NDJSON line stays free of it." Concern: "min's point stands. The help text is a second copy of the flag and key names, so the writer must derive it from the same table as the flag list, and under T1 it names only `--memory` / `--processes` for those limits."
- **AI/ML: H.** Reasoning: "The line prints only on a limit end, and it answers the agent's next question (what is the flag or key called) with no round trip. Without it, the agent tries `--timeout=0`, `--test-timeout` or an env var, and each wrong guess is one more call. The help text must say `none`, and under T1 it names only the flags for memory and processes." Concern: "min is right that the spellings now live in two places. The writer should derive the help text from the same table as the flags, so the two cannot drift."

### Final Spec

```sh
blink test                                  # each test binary: 10m timeout, no memory or process limit
blink test --timeout 30m --memory 2G --processes 1024
blink test --timeout none                   # turn the timeout off
```

```toml
[test]
timeout = "30m"
```

```json
{"record": "file", "file": "tests/test_hang.bl", "outcome": "aborted", "limit": "timeout", "limit_ms": 600000, "running": "hangs", "summary": {"total": 0, "passed": 0, "failed": 0, "panicked": 0, "skipped": 0, "duration_ms": 602004}}
```

```
ABORTED tests/test_hang.bl
  timed out after 10m in test "hangs"
  help: raise it with --timeout <duration> or [test] timeout in blink.toml; none turns it off
```

- A 10-minute wall-clock timeout covers each test binary on every host. There is no flag for the grace period, no environment variable and no per-test limit.
- `--memory` and `--processes` are off by default. A plain terminal session has neither.
- `none` turns a limit off. `0` is an error with `help: use none to turn the limit off`. A duration or a size with no unit is an error.
- A limit that someone asks for, and that the host cannot apply, stops the run before any build. The exit code is `2`, and the run writes no `file` line.
- A limit end is `aborted` with exactly one of `signal`, `exit_code` and `limit`. `limit` is `"timeout"`, `"memory"` or `"processes"`. The line has the one matching key of `limit_ms`, `limit_bytes` and `limit_count`, and no `signal` key.
- A child that exits with code `0` in the grace period is `limit: "timeout"`. The `test` lines written before the end stay and count.
- A kill from outside the runner stays `signal: "SIGKILL"`.
- `blink.toml` has a closed `[test]` table with the key `timeout`. A `memory` or `processes` key there is W1002, and its help names the flag.
- The precedence is flag, then `[test]`, then the default.
- The `run` line does not record the limits in force. Build steps have no limits.
- The human output has a `help:` line under a limit end. It uses `none`, never `0`, and it names a `[test]` key only for the timeout.
- `blink test` sends SIGTERM to its children when it receives SIGINT or SIGTERM.

### Dissents

- **Q1, Minimalism (M0).** Leave `--memory` and `--processes` out, and route the children of the repo's own test task through the existing per-child cap.
- **Q3, PLT (T3).** Under T1, `memory = "2G"` in `[test]` is only a warning, and the run has no cap.
- **Q5, Minimalism (V0).** The line carries no value key.
- **Q6, PLT (LR).** A reader of the NDJSON cannot tell "no memory cap" from "cap set and not hit".
- **Q7, Systems (BS).** A hung `blinkc` or `cc` blocks the run forever.

### Implementation notes

- Runner: pass `ChildLimits` to each test-binary spawn, map `ChildEnd.Limit` to `limit` and its `limit_*` key, and make one `can_limit` check before any build.
- CLI flags `--timeout`, `--memory` and `--processes`, with a duration parser and a size parser: `none`, a unit required, `0` an error. Sizes use powers of 1024.
- `blink.toml`: a closed `[test]` table with `timeout`. W1002 for any other key, with the `--memory` / `--processes` help for those two keys. An error for a toml value carries the span of the value.
- Human output: the limit-end line and the `help:` line, taken from the flag table. A test pins the help text to the flag table (AI/ML).
- Usage errors exit with code `2` and write text on standard error, also with `--json`.
- Follow-up requested by Systems, Web/Scripting and DevOps/Tooling: limits on build steps for `blink build`, `blink run` and `blink test` together.
- Repo chore requested by Minimalism and DevOps/Tooling: the repo's own test task passes `--memory 2G --processes 1024`, or routes its children through the per-child cap.
