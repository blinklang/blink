# @trusted and FFI: Not an Effect, a Recorded Claim — Design Rationale

**Gap:** Spec §9.1 says `@trusted` means a human audited the FFI binding, including that its effects are accurate. It never says whether callers of a `@trusted` fn are free of FFI. §4.3 defines no `FFI` effect, yet `! FFI` appears on 114 `@ffi` decls in lib/std, and E0500 skips any effect named `FFI`. 212 FFI call sites fail E0500 without that skip. The user (BDFL) ruled that a human-only audit tag makes no sense for a language meant for AI development.

**Options on the table:** (1) a `@trusted` fn body discharges FFI, and callers see only its declared row. (2) No discharge: lib wrappers declare `! FFI` and it propagates. (3) Redefine `@trusted` itself.

### Panel Deliberation

Six panelists (systems, web/scripting, PLT, DevOps/tooling, AI/ML, minimalism) deliberated
in independent-proposal → debate → vote rounds. All text below is quoted from the panelists. Cuts are marked "…". Dissent is marked **(dissent)**.

## Part 1 — Does @trusted discharge FFI?

#### Phase A — Independent proposals

Six panelists proposed "FFI is not an effect" as first choice. Excerpts from each:

- **Systems:** "FFI describes *how* code runs, not *what* it does. It belongs in the type rules that mark where `Ptr` is allowed (E0811), not in the effect row. In every option the hardware sees a direct C call, and none of them changes codegen." … "**`@trusted(audit: K)` changes meaning** from "a human reviewed this" to "an author, human or agent, makes a recorded claim that this signature and row match the foreign code"." … "**Spec gap I must flag:** an `@ffi` fn declared `! IO` is a direct C call, not a handler dispatch point. Installing an IO handler in a test does **not** intercept it." Fallback: "A > B >> (2)."
- **Web/Scripting:** "**Position:** "FFI" is not an effect. A JS or Python developer never asks whether a call reaches C. They ask whether it touches the disk, the network or the database. Make `@trusted` mean "this claim has an author and a record", not "a human looked at it"." Proposed text: "`@trusted(audit: K)` records that a named reviewer, human or agent, checked the binding against the foreign source: types match the header, the declared effect row is accurate, and the wrapper keeps memory safe. `K` must resolve to a findable record. The language does not care who wrote the record." Fallback: "A, then B. Never option (2)."
- **PLT:** "Today FFI does two jobs, and they need different typing rules: (a) Semantic effect ... (b) Trust status: 'unverified code ran here, its signature is assumed.' This is not a capability ... As an effect, (b) is a row element that licenses nothing. As something you can discharge, it is an effect cast." "A1: FFI is not an effect. An @ffi decl declares the foreign code's real §4.3 row, often empty. That row is the one assumed fact ... Writing `! FFI` is an error." On option 1: "Unsound as a channel. The audit key takes any string, and an agent writes it in one token, so this is unsafePerformIO with a tag on it." Invariant offered: "every effect row in Blink is either compiler-proven or is the row of an @ffi decl, recorded as an assumption under audit key K. No other row is assumed."
- **DevOps/Tooling:** "**Drop `FFI` as an effect name.** §4.3 never defines `FFI`, so `! FFI` names nothing. Any use of `! FFI` in a row is an error, and E0500 loses its blanket skip." "**Every `@ffi` decl states its real row, and the row must be explicit.** `@effects()` is how you write a pure binding. If you leave it out, the compiler still rejects the decl ("the compiler refuses to guess")." "**Being foreign becomes a tooling fact, not a type fact.** `blink audit` and the lockfile record each package's FFI bindings and audit IDs." Also: "The second error must NOT offer a machine-applicable fix. If `blink fix` rewrote 114 decls to `@effects()`, it would forge the very record the audit exists for." Add-on proposal: audit records that go stale.
- **AI/ML:** "drop FFI as an effect, make @trusted a signed claim not tied to who wrote it, and discharge nothing." "An AI would learn the reflex 'add `! FFI` until it compiles', and that reflex teaches it to ignore rows." "Option (1) gives one annotation two jobs ... An AI could hide `IO` behind @trusted and pass every check." "An @ffi binding declares what the foreign code does in real §4.3 effects, or declares it pure. `@effects()` ... is an explicit claim that the code is pure. It is not an omission."
- **Minimalism:** "The ticket asks whether @trusted discharges FFI. That assumes FFI is an effect. §4.3 defines no FFI effect." "An effect row is the fourth. It tells a caller nothing it can act on: you can't handle it, mock it or narrow it. Effects say what code does to the world. Foreignness is how the code is built." Proposed `@trusted` text: "`@trusted(audit: K)` records that the author (human or agent) claims the binding matches the foreign header, its effect row is accurate, and its memory use is safe. `K` names where that claim is recorded and checked." "Don't add `reviewer:` kinds, agent IDs or confidence levels." Fallback order "M2 > B"; option 1 "adds a second discharge mechanism next to handlers and `with`, and it is keyed on an audit tag ... Once that link exists, people will ask for @trusted to discharge IO too."

Fallbacks stated: B ("FFI is a real effect; a @trusted fn body discharges it") for Web, Systems, AI/ML. M2 ("keep FFI, plain transitivity") for Minimalism only. PLT and DevOps rejected both.

#### Phase B — Debate highlights

The moderator grouped the six proposals into one core option and eight variations (V1-V8). Every panelist ended the round "STABLE, READY TO VOTE".

- **V1, how a pure `@ffi` binding is written.** Four panelists moved to the explicit form.
  - **Systems:** "I switch to a mandatory explicit pure claim (DevOps and AI/ML are right). In C an empty row and a forgotten row look the same, and 'the compiler refuses to guess' (§9.1) already rules this."
  - **PLT:** "I change my position to the mandatory explicit form ... an omitted row and an empty row give the same typing judgement. But under A3 the row IS the assumption, and an assumption should be written, not inferred from silence."
  - **Minimalism:** "with 'no row = pure', migrating 114 `! FFI` decls by deleting the row silently claims purity 114 times."
  - **Web:** "I CHANGE my Phase A position and support an explicit pure claim (DevOps/AI-ML). Reason: an AI writes most of these bindings. 'Forgot the row' and 'it is pure' must look different."
  - **AI/ML:** "explicit marker. I hold this firmly. For an ordinary fn, 'no row' means the compiler proved the body pure. For an @ffi decl the compiler proves nothing, so 'no row' there would mean 'unchecked claim of pure'."
- **V2, what the `@trusted` record holds in the language.** All six: only `audit: K`.
  - **Systems:** "I drop header:/by: from the language. K names the record, and the header path and author go inside the record."
  - **AI/ML:** "A `by: "agent:claude-..."` field invites fabrication. An agent will fill in a plausible-looking ID, and nothing can check it."
  - **PLT:** "An argument the compiler does not check (`by:`, `header:`) is a comment with syntax around it."
- **V3, `Bytes.with_ptr` signature.** All six: `! _`. **Systems:** "My `! E` breaks §4.15 ... I withdraw it." **Minimalism:** "a fact, not a taste".
- **V4, accounting not routing.**
  - **Systems:** "The rule to state: 'A handler intercepts effect operations, not foreign calls. The row of an @ffi decl is a capability claim. If a foreign effect must be mockable, the wrapper performs it through the effect's operation.'"
  - **Web:** "YES, the spec must state it, and this is the strongest DX point in the round. The first Stack Overflow question will be: 'I installed an IO handler in my test, why does sqlite still hit disk?'"
  - **PLT:** "for foreign code the declared row is an upper bound on what the call may do, not a route for dispatch, so a handler does not intercept a direct foreign call".
- **V5, diagnostic for `! FFI`.**
  - **Minimalism:** "correction to my Phase A text. No unknown-effect diagnostic exists today, in spec or src (I grepped both). So there is nothing to reuse. Add ONE general code, `UnknownEffect` (Web's name), for any effect name not in §4.3 or user-declared. It also catches typos like `! Fs`. For `FFI` it adds a help line. Don't add an FFI-only code."
  - **DevOps:** "I prefer a dedicated code but won't block on it. The generic unknown-effect path suggests 'did you mean …?' typo fixes, which is the wrong advice here ... Hard requirement either way: no machine-applicable fix."
  - **AI/ML:** "the fix must NOT be machine-applicable ... The same rule should apply to every audit-gated diagnostic: no auto-fix may write a claim."
- **V6, follow-ups.** All six: separate tickets. **DevOps:** the lockfile / `blink audit --no-escalation` record of FFI use "replaces the supply-chain signal that removing `! FFI` takes away, so file it in the same batch." **Minimalism:** "Don't let it ride in on this vote."
- **V7, housekeeping.** **PLT:** "E0801 stays absolute." **Web:** fix the annotation table to say "fn (with @ffi), or any fn body that uses Ptr".
- **V8, invariant.** **Minimalism:** "It is one sentence that RESTRICTS: it forbids every future '@trusted hides a row' proposal, B included." **PLT:** "The trusted base becomes a finite list of (K, @ffi decl, row) triples that a tool can list without typechecking ... Coq's `Print Assumptions` works because the assumptions are only declarations, never bodies."
- **Rejecting B as a fallback.** **PLT:** "reject, and I will not take it as a fallback ... B needs an effect label that only an attribute can remove. Every row rule then needs a special case: unification, the subset check, and the HM row inference that just landed."
- **Interaction of V1 and V4.** **Web:** "Once FFI rows are real rows, users will expect them to behave like real rows, including mockability. Stating both rules together closes the gap."
- **Interaction of V1 and V5.** **Minimalism:** "V1 and V5 are the same question. Both prevent a record from being forged, by omission (V1) or by an auto-fix (V5)."
- **Migration test.** **DevOps:** "The 114-decl lib/std migration is the first real test of the redefined @trusted ... the work must not be a mechanical `! FFI` → `@effects()` sed ... Suggest this as an acceptance criterion on the implementation ticket."

#### Phase C — Final vote

- **Q1: Core model. A: FFI is not an effect; an @ffi decl's declared row is the claim, assumed under audit key K; callers see that row by normal transitivity. B: a @trusted fn body discharges FFI. M2: no skip; wrappers declare `! FFI` and it propagates.** (6-0 for A)
  - **Systems:** A — "Rows are erased, so all three options compile to the same direct C call. The only difference is what the row tells the reader. Under A the row says what the foreign code does (IO, DB, pure), so it is a real capability list. B adds a "discharge" that no runtime frame performs. M2 puts `! FFI` on every program through Str, List and Map, and pure trait impls become impossible." Concern: "an @ffi binding that is wrongly declared pure is an unproven lie that now flows into pure code; only the audit record and later tooling (stale-audit hash, libc lint) will catch it."
  - **Web/Scripting:** A — "Users reason about capabilities (disk, network, DB), not about whether a call reaches C. A foreign binding states its real row and callers inherit it by the same §4.5 rule they already know, so there is no new concept to learn. B adds a second discharge mechanism. M2 puts `! FFI` on every function that touches a List, and a row that sits on every function tells the reader nothing." Concern: "Users will expect a declared `! IO` on an @ffi decl to act like any other IO row, mocking included, unless Q4 passes alongside it."
  - **PLT:** A — "FFI as an effect mixes two kinds: a semantic capability and a trust postulate. Making it dischargeable (B) adds an effect cast that an annotation can trigger, and one row label then obeys different laws in unification, the subset check and HM row inference. Making it propagate (M2) is sound but adds no information, and it conflicts with the decided Display.fmt subset rule. A keeps rows purely semantic and puts every assumption in one place: the @ffi decl." Concern: "the migration could write empty rows on bindings that really do IO, which would turn the honest-row win into 114 unchecked false claims."
  - **DevOps/Tooling:** A — "An error under A names the real capability (`DB.Read`), so the fix is concrete. Hover, docs and `@capabilities` budgets stay meaningful. B needs a special case the LSP must explain ("why does this call add no effect?"). M2 puts `! FFI` on nearly every stdlib signature, so the row carries no signal." Concern: "once `! FFI` is gone, the supply-chain signal "this package now uses foreign code" lives only in tooling, so the lockfile / `blink audit --no-escalation` follow-up must actually ship."
  - **AI/ML:** A — "A keeps one effect rule (§4.5) with no FFI exception, so an agent learns it from the spec alone. The spec's own canonical wrappers (`open_database ! IO`, the §9.1.3 `read ! IO`) are already correct under A and wrong under M2, and agents copy canonical examples. B gives @trusted a second job (it would hide effects), and M2 puts a `! FFI` on almost every signature without telling the caller anything, which teaches agents to ignore rows." Concern: "a false purity claim on one @ffi decl spreads silently to every caller, so the audit record is the only check left."
  - **Minimalism:** A — "A removes one fake effect and one blanket skip, and it adds no rule. Callers use plain §4.5. B adds a second discharge mechanism keyed on an audit tag, and that surface stays forever. M2 adds noise everywhere and tells callers nothing they can act on." Concern: "during the lib/std migration, someone may put real effects into wrappers carelessly (for example `! IO` on everything "to be safe"), which makes the rows as useless as `! FFI` was."
- **Q2: Explicit pure claim. YES: an @ffi decl must carry an explicit row; a pure claim is spelled explicitly (spelling left to jnf0tt / @effects()); omitting the row on @ffi is an error. NO: omitted row on @ffi means pure.** (6-0 YES)
  - **Systems:** YES — "In C, an empty row and a forgotten row look the same, and §9.1 already says the compiler refuses to guess. A stated pure row is a claim the audit covers; an omission is not. The cost is a few characters per decl and zero at runtime." Concern: "if the spelling in jnf0tt ends up visually close to an omitted row, the distinction will exist in the grammar but disappear when people read the code."
  - **Web/Scripting:** YES — "An AI writes most bindings, and "forgot the row" must not read the same as "this is pure". An explicit claim is cheap to write and makes the audit record mean something. The spelling stays with jnf0tt." Concern: "If jnf0tt picks the `!` spelling, the explicit pure form must not be easy to confuse with an empty `!` row, or the rule is lost again."
  - **PLT:** YES — "Type theory gives the same judgement for an omitted row and an empty row. Under A, though, the row IS the postulate, and a postulate should be written, not inferred from silence. §9.1 already says "the compiler refuses to guess"." Concern: "the explicit spelling may get settled in jnf0tt after this ruling ships, which would leave a window where neither spelling is normative."
  - **DevOps/Tooling:** YES — "If an omitted row means pure, then an agent that forgets the row gets a pure binding silently. No diagnostic can tell an omission from a claim, and the existing §9.1 rule ("the compiler refuses to guess") exists for exactly this case. It also lets the audit inventory list "declared pure" bindings as their own category, which is where a lying row hides." Concern: "if jnf0tt picks a spelling where an explicit empty row looks the same as no row in the source, the rule loses its point."
  - **AI/ML:** YES — "on an ordinary fn, "no row" means the compiler proved it pure. On an @ffi decl the same text would mean an unchecked claim, and an agent cannot see which meaning applies. Most fns carry no row, so an agent leaves the row out by habit. Without this rule that habit forges a purity claim with no point where the agent chose to make it." Concern: "jnf0tt may choose an empty-row spelling that is easy to confuse with "no row", which undoes the benefit."
  - **Minimalism:** YES — "if "no row" means pure, deleting `! FFI` from 114 decls claims purity 114 times and nobody has to look at the C. A required explicit claim makes each migration a decision. This matches the §9.1 text "The compiler refuses to guess", so it keeps a rule and adds none." Concern: "jnf0tt may pick a second effect syntax (`@effects()` next to `!`), which leaves two ways to write one thing."
- **Q3: Diagnostic for `! FFI`. 3a: ONE general UnknownEffect code with an FFI-specific help line. 3b: a dedicated FFI-only code. Both: no machine-applicable fix.** (6-0 for 3a)
  - **Systems:** 3a — "No unknown-effect diagnostic exists today, so one is needed anyway for typos such as `! Io`. One general code with an FFI-specific help line covers both cases and keeps the catalog small. A code for a single retired name is catalog noise that stays forever. No machine-applicable fix, agreed: an autofix that writes a pure row would forge the audit claim." Concern: "the FFI help line must name the real choices (a real effect, or an explicit pure claim) so that an agent does not just delete `! FFI` and leave the row empty."
  - **Web/Scripting:** 3a — "Users learn one error for "that is not an effect". A help line that names FFI covers the migration case. A dedicated FFI-only code is one more code to learn and to explain, only to serve a spelling that should disappear after migration." Concern: "The FFI help line must say what to write instead (declare the real row or an explicit pure claim) without offering an autofix."
  - **PLT:** 3a — "Once FFI is not an effect, `! FFI` is one case of a general rule (an effect name that is not built-in or declared). A general rule deserves a general code. A code for one spelling would be surface with no typing rule behind it. The FFI-specific help line gives the targeted guidance, and no autofix may write the claim." Concern: "the help line could read as permission to write an empty row by default; it must tell the author to state the real effects, not suggest a row."
  - **DevOps/Tooling:** 3a — "No unknown-effect diagnostic exists today, so one general UnknownEffect code fills a real gap: typos in effect names need it as well. One code means one LSP code action path, one `blink explain` page and one place where the FFI help line lives. A dedicated FFI-only code would be a second code for a subset of the same mistake." Concern: "the FFI help line must not degrade into a generic "did you mean …?" suggestion, which would nudge an agent to write `! IO` without any review."
  - **AI/ML:** 3a — "one general UnknownEffect code also fills the real gap Min found: typos like `! Io` or `! Database` have no diagnostic today, and agents produce that kind of name often. One code with a targeted FFI help line is fewer codes to learn, and the help text carries the guidance. I strongly agree with the shared rule that no autofix may write a claim." Concern: "if the FFI help line gets folded into generic text, agents will "fix" the error by deleting the row instead of declaring the real one."
  - **Minimalism:** 3a — "one general code fills a real gap: no unknown-effect diagnostic exists today, and typos like `! Fs` need one too. An FFI-only code would be surface that dies once the migration ends. A help line carries the FFI-specific text at no cost. No autofix, because an autofix would write the claim." Concern: "the help line may grow into a long FFI essay. Keep it to one line and put the rest in `blink explain`."
- **Q4: Accounting-not-routing. YES: the row of an @ffi decl is a capability claim, a handler does not intercept a foreign call, and a foreign effect that must be mockable goes through a Blink effect operation in the wrapper (with §4.7 cross-ref).** (6-0 YES)
  - **Systems:** YES — "An @ffi fn declared `! Time` or `! Rand` is a direct C call. A test that installs a Time or Rand handler for determinism still gets the real clock or RNG, so the test is flaky with no visible cause. The spec must say that handlers intercept effect operations, not foreign calls. A foreign effect that must be mockable goes through the effect's operation in the wrapper, as io.print already does." Concern: "existing lib/std wrappers for Time, Rand or IO that call foreign code directly will silently escape test handlers until someone audits them against this rule."
  - **Web/Scripting:** YES — ""I installed an IO handler in my test, so why does sqlite still write to disk?" will be the first Stack Overflow question once FFI rows are real rows. One sentence plus the wrapper pattern answers it before anyone asks. Without it, A trades the "what is `! FFI`" confusion for a "why can't I mock it" confusion." Concern: "The wrapper pattern needs a short worked example in §4.7, or readers will not find it."
  - **PLT:** YES — "This is a real limit on how handlers compose. A reader who knows the handler semantics in §4.7 would expect every IO operation in scope to be intercepted, and a direct foreign call silently breaks that. Unstated limits are worse than stated ones. Sending mockable effects through a Blink effect operation in the wrapper restores uniform handler semantics where it matters." Concern: "authors may skip the wrapper-level effect operation and then find their tests do not intercept the call. The §4.7 cross-reference must be prominent."
  - **DevOps/Tooling:** YES — "The first user whose IO test handler fails to intercept a foreign call will file a bug unless the spec says this outright. It also gives the LSP a hover line ("declared row under audit K: capability accounting, not handler-routable"). The cross-ref to §4.7 tells people where mocking does work." Concern: "people will still expect interception, so the hover text and the explain page must state it, not only the spec."
  - **AI/ML:** YES — "an agent writing a test will install an IO handler and expect it to intercept a foreign call. The test then passes or fails for the wrong reason, and nothing in the language warns about it. Stating this once, with the "route through a Blink effect operation" pattern and the §4.7 cross-ref, gives the agent the correct pattern to copy." Concern: "if the sentence lives only in §9.1, agents reading §4.7 handler docs will not see it, so the cross-ref must go both ways."
  - **Minimalism:** YES — "it costs a few sentences and stops a wrong belief, that "an IO handler mocks sqlite", which an AI author would act on. It adds no mechanism. It only describes what the compiler already does. The pointer to a Blink effect operation in the wrapper shows the existing way to mock, so nobody needs to ask for a new one." Concern: "the same rule may end up written in both Q4's text and the Q5 invariant and later drift apart."
- **Q5: Invariant (PLT wording, near §4.5), plus Systems' "regions change Ptr rules only, never rows".** (6-0 YES; text settled in D2)
  - **Systems:** YES-with-amendment — "The invariant states what A is for: the only unproven rows sit on @ffi decls, under a key. The amendment closes the gap where a reader might take an FFI region to be a second place where rows are assumed. With it, a grep for @ffi decls lists every unproven claim in a program." Concern: ""upper bound" is a promise the compiler cannot check, so the spec must not let any optimisation or analysis rely on it being true."
  - **Web/Scripting:** YES — ""Rows are proven, except @ffi rows, which are recorded assumptions" is one sentence a learner can keep in their head. Placing it next to §4.5 means readers meet it where they learn effects." Concern: ""Upper bound" is jargon for scripting readers; give a one-line plain example (a pure claim on a call that writes a file is a false claim)."
  - **PLT:** YES-with-amendment — "The invariant states the soundness boundary of the effect system in one sentence, and it is the property future proposals must not break. The Sys sentence closes the obvious loophole (regions as row-erasure) explicitly." Concern: "future features such as an `unsafe`-style cast or an FFI callback-row rule could quietly violate it unless reviewers test new rules against this text."
  - **DevOps/Tooling:** YES — "This gives tooling one rule with no special cases: every row is either proven or assumed under K. `blink audit` and the LSP can show the two kinds of row apart from that rule alone." Concern: ""upper bound" is unchecked by design, so a row that is too narrow is a silent lie that only an audit can catch."
  - **AI/ML:** YES — "it states the trust base in one sentence an agent can check any row against. "Upper bound" is the right shape: the claim may over-declare, never under-declare. Sys's "regions change Ptr rules only, never rows" closes the one remaining misreading, namely that an @trusted body or ffi.scope changes effects." Concern: "none of substance. Only that later features (e.g. effect polymorphism in v2) must amend this sentence rather than quietly break it."
  - **Minimalism:** YES-with-amendment — "this rule blocks additions. It forbids every later "@trusted hides a row" proposal, B included. Rules that block surface are the cheapest rules a language can have." Amendment: "state handler non-interception in ONE place. Keep it in the invariant, and have the Q4 text refer to it, not repeat it." Concern: ""upper bound" may be read as letting the compiler or tools infer narrower rows, which nobody proposed."
- **Q6: @trusted definition wording. Min draft, or AMEND.** (6-0 AMEND; six different texts submitted, text settled in D1)
  - **Systems:** AMEND — "Min's draft says "foreign header", but many lib/std bindings target runtime symbols with no public header (`blink_arena_bytes_used`), so "foreign declaration" is the accurate term. "Recorded and checked" suggests something checks the claim; nothing does, which breaks PLT criterion (i)." Concern: ""must resolve to one" needs a defined resolution mechanism (a file, a registry); without one it is a promise with no enforcement."
  - **Web/Scripting:** AMEND — "Min's "recorded and checked" suggests something checks the claim, which it does not, and readers will believe it. The amendment states PLT's three criteria in plain words: it is a claim, K finds the record, and authorship does not matter." Concern: ""Can be found by K" is a promise only tooling can keep, so the spec must not suggest the compiler enforces it."
  - **PLT:** AMEND — "Min's draft says the claim is "recorded and checked", but nothing in the language checks it. A spec must not imply a proof obligation it does not discharge. The amendment meets all three criteria: it is an assumption, K resolves to a record, and nothing is promised about the author." Concern: ""must name a record" has no enforcement mechanism yet, so until `blink audit` resolves keys it is a promise the toolchain cannot check either."
  - **DevOps/Tooling:** AMEND — "Min's "recorded and checked" implies that something checks the claim. Nothing in the compiler does, and a user reading "checked" will over-trust it. My text meets all three of PLT's criteria, and it names the tool that makes K findable." Concern: "until the stale-audit follow-up lands, a K can outlive the binding it describes without any warning."
  - **AI/ML:** AMEND — "Min's "recorded and checked" reads as "the language checks it". Agents take such words at face value and will treat @trusted as a proof. That violates PLT criterion (i)." Concern: "a wording that suggests verification leads agents to stamp @trusted as a way to satisfy the compiler, not as a claim they are accountable for."
  - **Minimalism:** AMEND — "my draft said "recorded and checked". "Checked" promises a review the language cannot see, which fails PLT criterion (i)." Concern: ""must name a record" has no enforcement today. If no tool ever resolves K, the word "must" is empty."
- **Q7: Bundle. V2: `@trusted` takes `audit: K` only; drop reviewer:/date: from the §9.1 example. V3: `with_ptr` uses `! _`. V7: E0801 stays absolute, the compiler's pub-when-@trusted exception goes, lib/std pub bindings are fixed, annotation table fixed.** (6-0 YES)
  - **Systems:** YES — "V2 keeps the language surface to `audit: K`; header and author belong in the record, where tooling can read them. V3 `! _` is the only form §4.15 allows in v1, and it keeps with_ptr free of any effect of its own. V7 makes lib/std obey the rule it imposes on users: a pub @ffi binding is a raw pointer API leaking past the safe wrapper." Concern: "making the lib/std @ffi bindings private may expose wrappers that do not exist yet (e.g. callers of `sqlite_errmsg` outside db_sqlite), so the migration is larger than a change to pub."
  - **Web/Scripting:** YES — "`audit: K` alone means fewer keys for an LLM to invent. Fixing the §9.1 example stops readers copying `reviewer:` and `date:`. `! _` is the only v1 syntax, and learners copy stdlib signatures. E0801 without exceptions, plus a fixed annotation table, removes a place where the spec contradicts itself, and that contradiction produces wrong generated code." Concern: "Making the lib/std pub bindings private may break users who call `sqlite_errmsg` directly today, so the release notes must name it."
  - **PLT:** YES — "V2: an argument the compiler does not check is a comment with syntax around it. ## Part 2 — What is an audit record, and how does K resolve?

The question: D1 says "`K` must name a record of that claim. The language promises that the record exists, not who wrote it." Nothing defined what a record is, where it lives, what it holds, or what checks it, or when. Facts the moderator checked: nothing in spec or src resolved K against anything. E0836's `blink explain` text says "The identifier is free-form". The compiler's W0310 help (src/typecheck.bl:4928) prints only "add @trusted(audit: \"AUDIT-ID\") to suppress". The §9.1 table still said "A human checked ...".

#### Phase A — Independent proposals

Shared by all six: a record is a table keyed K in one TOML file at the package root. `claim` is required and non-empty. The compiler resolves K at `blink check` / `blink build` (and LSP). Source stays `@trusted(audit: K)` only. Excerpts:

- **Systems (S1):** "In `audits.toml`, next to `blink.toml`, with one table per K. One file, not a directory, so a team can protect it with whatever review gate it already uses (CODEOWNERS, a required reviewer)." Pin: "The whole body is NOT hashed. Otherwise every unrelated edit would make the record stale." "A lie is still possible, but it is written down where reviewers look and it expires when the code changes. That is what §9.1 promises."
- **Web/Scripting (W1):** "A table in `audit.toml` at the package root, next to `blink.toml`. The table name is K. It has one required field, `claim`: a non-empty string that says what was checked and why it is safe." "Agents run `build` and `check`, not `audit`. A check that lives only in a tool they never run does not exist for them." "The parameterized fix is now cheaper than the shortcut, and that is the goal."
- **PLT (P):** "A claim is only sound if it is bound to the thing it is about. Today K is a free string, so `@trusted(audit: "x")` is a postulate about nothing." A record names its subject and pins it with a fingerprint. "Parameterizing (`{table}`) becomes strictly cheaper than auditing, which is the ordering we want: the right fix is the cheap one."
- **DevOps/Tooling (R1):** "An entry in `audits.toml` at the package root (lib/std has its own). The key is K." Pins are per site. "Every check runs at compile time (`check`, `build`, LSP), because a check that only runs in CI is one an agent never sees." "No `help:` line ever offers `@trusted`. The audit channel shows up only as a `note:` after a record already exists, plus the `blink explain` page."
- **AI/ML (R1):** "A record is one table in `audit.toml` at the package root." Pin is "a hash of each covered fn's signature, row and fmt-normalized body." "A stale record suppresses nothing. The gated diagnostic (W0800/W0310) fires again with `note: record DB-001 is stale: find changed after it was pinned`." "No scheme makes lying expensive for an agent. What R1 buys: **Visibility** … **Expiry**. "Silence once, forever" was the real shortcut, and R1 removes it."
- **Minimalism (M-A):** "No mechanism makes a lie expensive to write. An agent that will fake a K will also fake a record. What a language can do is make the claim visible: put it where a project can gate it, separate from the code it excuses. So the record should be as small as possible. Its value is WHERE it lives, not what it holds." Fields: `fn` list and `claim`, no hash.

### Final Spec

An `@ffi` decl states its real row. `FFI` is not an effect. The pure claim is written, not left out. The `@effects` spelling is left to the `@effects` implementation ticket. The safe wrapper is an ordinary fn. A caller sees the row by normal transitivity.

```blink
@ffi("sqlite3", "sqlite3_errmsg")
@trusted(audit: "DB-003")
@effects(DB)
fn sqlite_errmsg_ffi(handle: Sqlite3) -> Str {}

pub fn last_error(db: Database) -> Str ! DB {
    sqlite_errmsg_ffi(db.handle)
}
```

`audits.toml`, at the package root, next to `blink.toml`. The compiler resolves `"DB-003"` here at `blink check`, `blink build` and in the LSP. A pin maps a fn path to an AST hash of the fn's signature, row and body. The panel voted the schema shape (a non-empty `claim` plus per-fn pins, closed); the spec (§9.1 *Audit Records*) fixes the spelling below.

```toml
[DB-003]
claim = "Signature matches sqlite3.h 3.46. sqlite3_errmsg returns a borrowed const char*; it is copied into a Str before the next sqlite call. The row is DB."
pins = { "std.db_sqlite.sqlite_errmsg_ffi" = "ast1:9f2c41d07a3e" }
```

**Locked design points**

- **Q1 (6-0, A):** FFI is not an effect. An `@ffi` decl's declared row is an assumed claim under audit key K. Callers see that row by normal §4.5 transitivity. Nothing is discharged. Writing `! FFI` is an error (E0538 UnknownEffect) and the E0500 blanket skip is deleted.
- **Q2 (6-0, YES):** An explicit pure claim. Omitting the row on an `@ffi` decl is an error (E0802 FfiNoEffects). The spelling is left to the `@effects` implementation ticket.
- **Q3 (6-0, 3a):** One general `UnknownEffect` code (E0538) for any effect name not built-in or declared, with an FFI help line. No machine-applicable fix: no tool or autofix may write a claim.
- **Q4 (6-0, YES):** The row of an `@ffi` decl is capability accounting, not routing. A handler does not intercept a foreign call. A foreign effect that must be mockable goes through a Blink effect operation in the wrapper. Per D3, the rule is stated once, in the invariant (§4.5). §9.1 and §4.7 refer to it.
- **Q5 (6-0, YES; text settled in D2):** the invariant, in D2's final text below.
- **Q6 (6-0, AMEND; text settled in D1):** the `@trusted` definition, in D1's final text below.
- **Q7 (6-0, YES):** `@trusted` takes `audit: K` only. The §9.1 example drops `reviewer:` and `date:`. `Bytes.with_ptr` becomes `fn with_ptr[R](self: Bytes, body: fn(Ptr[U8]) -> R ! _) -> R ! _`. E0801 stays absolute: the compiler's pub-when-`@trusted` exception goes, lib/std `pub` bindings are fixed, and the annotation table (07:2308) is fixed.
- **D1 (round 2: T-PLT 5-1, Systems dissent for T-AIML), final text:** "`@trusted(audit: K)` records a claim, by an author who may be human or agent, that the binding matches the foreign code: its types, its effect row and its memory use. The compiler assumes the claim; it does not prove it. `K` must name a record of that claim. The language promises that the record exists, not who wrote it."
- **D2 (round 1 3-3; round 2 I-MIN 6-0), final text:** "Every effect row in Blink is either compiler-proven (including discharge by handler or `with`) or is the declared row of an @ffi decl, assumed under audit key K. An assumed row is an upper bound on the foreign call's behaviour; handlers do not intercept foreign calls. FFI regions change Ptr rules only, never rows." In the spec, "FFI regions" is a cross-reference to the E0811 list, which stays the single source of the region list.
- **D3 (6-0, YES):** Handler non-interception is stated in one place, the invariant.
- **R1 (6-0):** The record file is `audits.toml`, one per package, at the package root. lib/std has its own. A dependency ships its own. K resolves only against the package that holds the annotated fn.
- **R2 (6-0 in Phase D, after 3-3 in Phase C):** (c). A record pins each fn it covers with an AST hash of the signature, row and body. For an `@ffi` decl the body is empty, so the pin is the signature and row. Conditions: formatting and comments never stale a pin. The spec says a guard in a caller is outside the pin. Spec examples show small audited fns that hold their own guard.
- **R3 (6-0):** A pin that no longer matches lapses. The original W0800 or W0310 fires again with a note that names K and says why. There is no new code.
- **R4 (6-0):** On an audit-gated diagnostic the real fix comes first. `@trusted` comes second, not machine-applicable, names the record file, and is worded as recording a review, not "to suppress". This ruling fixes the help at src/typecheck.bl:4928 and the "A human checked" rows in the §9.1 table, and replaces the E0836 explain text ("free-form").
- **R5a (6-0):** The diagnostic for a K with no record, or an empty `claim`, is `AuditRecordNotFound`, allocated as E0829 (E0838, E0839 and E0840 are taken).
- **R5b (6-0):** A K that exists with a non-empty claim but has no pin for this fn is not an error. The suppression lapses, as in R3.
- **R6a (6-0):** `blink audit pin K [fn]` writes hashes only, never the claim. It refuses when K has no record or an empty claim.
- **R6b (6-0):** Bulk re-pin is forbidden. A bulk command may list stale records, never re-pin them.
- **R7 (6-0 in Phase D, after 3-3 in Phase C):** Closed schema. An unknown key is an error (E0830 AuditRecordUnknownKey) that names the allowed keys and gives a did-you-mean. `[K.meta]` was withdrawn. It can be added later without breaking any file.
- **R8 (6-0):** The K rule applies to every `@trusted(audit: K)` now, including ScopedValueWithoutWith. Whether ScopedValueWithoutWith keeps the channel goes to a separate ticket.
- **Follow-ups, not in this ruling:** splitting the Ptr-region job of `@trusted` from the record job (it reopens the mint-boundary decision), the lockfile hash of each dependency's `audits.toml` for `blink audit --no-escalation`, and whether ScopedValueWithoutWith keeps `@trusted` suppression.
- **Acceptance criterion for the implementation ticket (DevOps):** the 114-decl lib/std migration must not be a mechanical `! FFI` → `@effects()` rewrite. Each row is a decision.
