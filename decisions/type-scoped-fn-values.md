# Type-Scoped Functions as Fn Values — Design Rationale

§3.4 *A generic function named as a value* lets a generic function's name stand wherever a function value is expected, and *A payload variant named as a value* does the same for a variant. Neither covers a type-scoped function, `fn T.name` (§2.12.3), or a builtin such as `Duration.ms`. The payload-variant panel left it out of scope on purpose. This ruling answers the question: is `T.name` with no argument list a function value, and under which typing rule?

Before the ruling, the compiler stopped with an internal error on `let f = Duration.ms`, on `let h: fn() -> Int = Int.default` and on a trait `W.make`. `[1, 2].map(Duration.ms)` gave E0301 on the binding with the note "the empty construction here has no element type", a note that names neither the reference nor the rule. A user `fn Meters.of` did not parse yet. That parser gap is a separate implementation item and not part of this ruling.

Already decided and not reopened: a generic function named as a value (6-0); opaque types and type-scoped declarations (6-0: no receiver, one `T.` namespace, E1016 and E0522, `(Trait for T).name()` is a callee head only); no inherent methods; every variant qualified.

### Panel Deliberation

Six panelists (systems, web/scripting, PLT, DevOps/tooling, AI/ML, minimalism) deliberated
in independent-proposal → debate → vote rounds.

#### Phase A — Independent proposals

Each seat proposed alone. All six put the same rule first: `T.name` with no argument list is a function value under the §3.4 rule. The excerpts below are the seats' own text.

- **Systems:** "**Ruling.** A type-scoped fn, a trait associated fn reached as `T.name`, and the same reached through a type parameter are function values when written with no argument list. They follow the §3.4 rule for a generic function's name: the expected type is a source of type information, and the binders are solved by unifying against it. A binder the expected type does not fix is `error[CannotInferType]` (E0301) at the reference. No new rule." On the clash: "Two trait impls that give `T` one name is E0522 at the reference, exactly as for a call. Help: one line per owner. A bare `(Trait for T).name` is an error (§3c.4 *Only a callee head*), so the help must not print it as a value. It prints the closure the user can paste: `fn(n) { (Alpha for Widget).make(n) }`." Sys also proposed: "Add an error code (new) `ImplQualifiedNotCalled`, help: \"call it, or wrap it in a closure\"."
- **Web/Scripting:** "**Ruling.** `T.name` with no argument list, where `name` is a type-scoped fn or an associated fn (no `self`) in the `T.` namespace, is a function value. It has the declared signature as its type. It follows the §3.4 rule with no new rule: the expected type solves the binders; binders that nothing fixes give E0301 at the reference." Web also wrote: "A JS/Python dev writes `.map(Number)`, `.map(str)`, `.map(Duration.from_ms)` without thinking. If `Duration.ms(100)` works and `.map(Duration.ms)` does not, that is a Stack Overflow question every week." Web's fallback, "web-2: not a value; wrap in a closure", was not preferred.
- **PLT:** "**Position.** A reference `T.name` with no argument list, where `name` is a function in the `T.` namespace, is a function value. Its type is the declaration's type with its binders solved by the expected type. This is the §3.4 rule. It adds no new rule, so §3.4 only needs to list the forms it covers." PLT also proposed an amendment: "I propose `(Trait for T).name` with no call is a fn value of the same type. `(Alpha for Widget)` alone stays an error."
- **DevOps:** "**Ruling.** `T.name` with no argument list is a function value for every function the `T.` namespace holds: a type-scoped fn, a trait associated fn, and either one reached through a type parameter. It has the type of its declaration with `self` absent: `fn(P1, ..., Pn) -> R`. The expected type solves the binders by the rule in §3.4 *A generic function named as a value*. No new rule and no new error code." On the clash: "The spec should say that the help prints the closure when the reference has no call."
- **AI/ML:** "**Rule:** a name in the `T.` namespace, written with no argument list and no brackets, is a function value wherever a function value is expected. This holds for a type-scoped function, a trait associated function, and a function reached through a type parameter. The §3.4 rule governs it with no change[.] ... There is no second rule." And: "One uniform rule means one thing to learn. Variants, free functions and `T.name` all behave the same."
- **Minimalism:** "**min-1: One sentence in §3.4, no new rule, no carve-out.** `T.name` with no argument list is a function value whenever `T.name` names a function. This covers a type-scoped fn and a trait associated fn alike. The typing rule is the §3.4 rule already approved for a generic function's name. Nothing is added to the language."

#### Phase B — Debate highlights

The moderator's digest listed what all six proposals state, then seven variations (V1 to V7). Each seat replied once. The excerpts show the position shifts.

**V1. `(Trait for T).name` with no call.** Five seats kept the error. PLT had proposed a value form and withdrew it:

- **PLT:** "**V1. Concede.** Five seats keep the error, and 03c *Only a callee head* was a 6-0 clause. My argument was about the repair, not about soundness: a closure is the same program, so no typing hole opens. I withdraw the amendment."
- **Systems:** "**V1. Keep the error.** I oppose plt's value form. A closure that calls the impl-qualified function has no capture, so it compiles to a direct call after inlining. The cost of the repair is zero."
- **DevOps:** "**V1.** Keep the error. ... The closure is needed only on an E0522 clash, which is rare and already a diagnostic."
- **Minimalism:** "`(Trait for T).name` is not a term by 03c (callee head only). Making it a value adds a new value form for a rare clash. Closure is the repair for rare cases."

**V2. A code for it.** Systems withdrew its new code. DevOps had first conceded to Systems, then found that no seat held the code:

- **Systems:** "**V2. I concede.** I withdraw `ImplQualifiedNotCalled`. The existing \"are errors\" text stands. One sentence in the bullet that names the closure repair (devops) is enough."
- **DevOps:** "**V2.** I concede to sys. A diagnostic with no code has no `blink explain` page, no LSP code action, and no suppression handle. If no existing code fits, add `ImplQualifiedNotCalled` with help \"call it, or wrap it in a closure\". I withdraw \"one sentence only\"."

**V3. The E0522 help at a bare reference.** All seats agreed on a closure. Web corrected its own syntax:

- **Web/Scripting:** "**Correction to my own Phase A.** I wrote the closure as `|x| ...`. Blink has no such form (§2.8: closures use `fn`). Every help text must read `fn(n) { (Alpha for Widget).make(n) }`."
- **AI/ML:** "Web's `|x| ...` is wrong: §2.8 says closures use `fn` and have no short form. Web must correct it, or an AI copies a form that does not parse."

**V4. Which binders.** DevOps, AI/ML and Web had written "the type's binders also". All three conceded:

- **PLT:** "A type-scoped fn is not in the scope of the type's parameters. `fn Stack.one[T](x: T) -> Stack[T]` declares its own `T`. If it declares no `[T]`, none is in scope, and no type binder exists to solve."
- **AI/ML:** "I concede. The fn's own list only. §2.12.3 says `fn T.name[A, B]` carries its own binders and the type head takes no list. My Phase A \"plus the type's\" misstated the spec."
- **DevOps:** "I withdraw my Phase A claim. §2.12.3 says the type head takes no list and the fn declares its own binders: `fn Stack.empty[T]()`. So the binders are the fn's own list only."
- **Web/Scripting:** "I concede. ... My sentence \"and, on a generic T, those of T\" is wrong."

**V5. A `self` method reached as `T.name`.** Web: "A name that has a `self` parameter (a trait method reached as `T.name`) is not in the `T.` namespace. It keeps today's diagnostic. No change." Every seat agreed.

**V6. Placement and extra sentences.** All seats put a new paragraph after the payload-variant paragraph and dropped Web's first-sentence edit. They split on the environment sentence:

- **Systems:** "**I concede the \"no environment\" sentence.** It is implementation detail (layout of a fn value), and the project rule keeps that out of sections/. Drop it."
- **AI/ML:** "Add sys's sentence \"The value has no environment\" and plt's \"Method syntax does not reach it\". Both are short and prevent a wrong guess."
- **Minimalism:** "Skip sys's \"no environment\" sentence: it states what follows from \"names a function\"."

**V7. `let s: Stack[Int] = Stack.empty`.**

- **PLT:** "**V7. Keep.** `let s: Stack[Int] = Stack.empty` is E0308 with help \"call it: `Stack.empty()`\". This is the usual function-versus-result mismatch. I ask that the E0308 help be stated once, in the new paragraph."
- **Minimalism:** "**V7. Support plt.** It follows from the existing type rule. No new text, but a test row."
