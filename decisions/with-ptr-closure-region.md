# With-ptr Closure and FFI Regions — Design Rationale

**Gap:** §9.1.1 lists three FFI regions: an `@ffi` body, an `@trusted` body and a `with ffi.scope()` block. A closure literal inherits the region it is written in. A `Bytes.with_ptr` closure gets a `Ptr[U8]` parameter. Is its body a region of its own, or only when it is written inside one? §9.1.3 said `with_ptr` is "for use inside an FFI region only", but the canonical list did not say so. The five `std.libc` `*_bytes` wrappers are plain `pub fn`s that call `with_ptr`, so once E0811 checks bodies (§9.1.1, *E0811 covers bodies*), the answer decides whether they compile.

**Options on the table:** (A) no fourth region; the closure inherits, and the wrappers take `@trusted`. (B) a fourth region: the body of a closure literal passed to `Bytes.with_ptr` or `Bytes.with_mut_ptr`. Three more questions came out of Phase B: how many E0811 reports one such closure gives (Q2), whether the pointer-operation table names the call (Q3), and what the E0811 help line says (Q4).

### Panel Deliberation

Six panelists (systems, web/scripting, PLT, DevOps/tooling, AI/ML, minimalism) deliberated
in independent-proposal → debate → vote rounds. All text below is quoted from the panelists. Cuts are marked "…". Dissent is marked **(dissent)**.

#### Phase A — Independent proposals

All six proposed A first. Each one who raised B said they would vote against it.

- **Systems:** "Codegen (`src/cg_call.bl:4749`, `cc_bytes_with_ptr`) inlines the closure body at the call site. There is no closure object and no call; `p` is `b->data`. So `with_ptr` costs nothing at runtime, and the region rule decides only what the checker allows." … "`ffi.scope()` costs something at runtime. `blink_ffi_scope_new` allocates a list and registers cleanup on every entry." … Rule text: "A closure literal passed to `Bytes.with_ptr` or `Bytes.with_mut_ptr` is **not** a region of its own. It follows the closure rule above: it is in a region only when it is written inside one. Outside a region, its `Ptr[U8]` parameter is a site that E0811 rejects, whether the parameter is named or `_`." … "**The claim goes where the risk is.** The unsafe promise is "C reads only `data.len()` bytes and does not write through a `with_ptr` pointer". That is a `@trusted` claim, and now an audit record holds it."
- **Web/Scripting:** "A closure literal passed to `Bytes.with_ptr` or `Bytes.with_mut_ptr` is not a region of its own. Like any closure literal, it inherits the region it is written in. Outside a region, its `Ptr[U8]` parameter is E0811." … "**One rule to learn.** "Pointers need a region, and closures inherit." There is no special case for one method name." … "If `with_ptr` were a region, `b.with_ptr(fn(p) { p.offset(9999).deref() })` would compile in any file with no annotation. That puts an unaudited raw read one autocomplete away."
- **PLT:** "Treat the region as a mode `r ∈ {safe, ffi}` on the judgment `Γ ⊢_r e`. Only three syntactic forms introduce `ffi` … The closure rule preserves the mode … `Ptr[T]` is well-formed only under `ffi`. So `bs.with_ptr(...)` cannot type in `safe` mode, because its argument type `fn(Ptr[U8]) -> R` mentions `Ptr`. The rule adds nothing new; it is a consequence of E0811 and the type of `with_ptr`. That is the right kind of rule." … "The `@trusted` function is the sealing boundary — the same pattern as `runST` or a safe Rust fn wrapping an `unsafe` block." … "No region is opened by *what function a closure is passed to*. Region status depends only on where a term is written, so it composes under refactoring (extract the closure to a `let`, same result)."
- **DevOps/Tooling:** "A `Bytes.with_ptr` or `Bytes.with_mut_ptr` closure body is not a region on its own. Its `Ptr[U8]` parameter is a pointer site like any other. It is legal only when the call is inside a region." … "Report one error at the call, not one for each `Ptr` expression in the body" … "**The predicate stays syntactic.** A fourth region keyed on a method call matches the *name* `with_ptr`, not the `Bytes` type." … "Today "Bytes→Ptr bridges are forbidden in user code" and "used only inside `std.libc`" exist only as text. D1 makes the compiler enforce them."
- **AI/ML:** "**How I frame the question.** "Is the closure body a region?" turns into one question: *may `with_ptr` / `with_mut_ptr` be called outside an FFI region?*" … "`Bytes.with_ptr` and `Bytes.with_mut_ptr` are pointer operations. A call to either may appear only inside an FFI region." … "The help line names `@trusted`, not `with ffi.scope()`. A scope block with no alloc in it is a cargo-cult fix that models will copy everywhere." … "One rule with no exceptions: "a Ptr appears only in a region." Models fail on special cases, not on rules."
- **Minimalism:** "A closure passed to `Bytes.with_ptr` or `Bytes.with_mut_ptr` is an ordinary closure literal. It is **not** a region on its own. It inherits a region only when it is written inside one. Outside a region, its `Ptr[U8]` parameter is E0811, whether the parameter is named or `_`." … "Today the `c_read` audit text makes a claim about `read_bytes` … a claim about another function's code that its pin does not cover. With `@trusted` on the wrapper, the audit pin hashes the closure and the bound." … On B: "It breaks "purely syntactic, decided without type resolution." To know a call is `Bytes.with_ptr`, the checker must resolve the receiver type."

#### Phase B — Debate highlights

The moderator grouped the proposals into A, B, and three variations: V1 (where E0811 reports), V2 (is the call named a pointer operation), V3 (what the help line says). All six ended round 1 "STABLE, ready to vote".

- **V1, where E0811 reports.**
  - **Systems:** "one error per closure. The primary caret goes on the call. A secondary label on the parameter says "this closure parameter is a `Ptr[U8]`"." … "This is a concession to DevOps and AI/ML. My Phase A text put the error on `p`, but a `_` parameter has no name to point at, and the call is what the user wrote wrong."
  - **PLT:** "In the typing reading, the first term that cannot be typed in safe mode is the closure literal. Its type `fn(Ptr[U8]) -> R` holds `Ptr`. The `p` uses inside it come after that failure." … "Spec text: "E0811 reports once, at the outermost expression whose type holds a `Ptr`.""
  - **Minimalism:** "report **one** error per closure, not one per `Ptr` expression in the body. That should be a general E0811 rule, not a special case for `with_ptr`. When a `Ptr` expression gets its pointer from a site already reported, do not report it again."
  - **DevOps:** "if E0811 fires on every `Ptr` use, a 10-line closure gives 10 errors for one mistake. The LSP then shows 10 squiggles, and a model tries 10 fixes." … "If the panel prefers, the spec can leave the grouping to the tools."
  - **AI/ML:** "A body with five Ptr expressions must not give five errors: an agent that reads five errors makes five edits."
- **V2, name the call a pointer operation.** AI/ML withdrew it: "I concede to PLT. The rule follows from E0811 and the type of `with_ptr`, so a model learns nothing new from a second statement of it. Two statements of one rule invite a model to think they differ." PLT offered a concession: "I accept a non-normative table row that reads "`Bytes.with_ptr` / `with_mut_ptr`: region required, because the closure parameter is `Ptr[U8]` (follows from E0811)"." Minimalism: "Adding `Bytes` methods to it brings back B's problem: entries keyed on method names, and a new row for every future pinning API (`Str.with_ptr`?)."
- **V3, the help line.** All six dropped `with ffi.scope()`. DevOps: "I accept the points from AI/ML and Sys. A `with ffi.scope()` block with no alloc in it costs runtime and is a fix that models will copy everywhere." Web: "I concede to AI/ML, Sys and Min. Drop `with ffi.scope()` from the help line." PLT: "`ffi.scope` means "this block owns pointer lifetimes". Opening one only to make a region misuses the construct". The order split: AI/ML, PLT and Minimalism put `@trusted` first; Systems, Web and DevOps put the no-pointer paths first. Web: "DevOps's `b.get(i)` hint is good, but only when the closure body only reads bytes."

#### Phase C — Final vote

- **Q1: Is a `with_ptr` / `with_mut_ptr` closure body an FFI region?** (6-0 for A)
  - **Systems:** A — "The closure body is inlined at the call site, so the choice changes no generated code, only the checker. A keeps E0811 a three-item check that needs no type resolution, the same predicate `blink audit` uses. It also puts the trust claim ("C reads only `len` bytes and does not write through a `with_ptr` pointer") in an audit record, where the claim belongs. B would give every user a way to get a `Ptr` from `Bytes` without that record." Concern: "If the E0811 body check is turned on before the five wrappers are annotated `@trusted`, every std build that uses them breaks; the order of those two changes must be enforced."
  - **Web/Scripting:** A — "Users learn one rule: "pointers need a region, and closures inherit." No method name gets special treatment. B would let any user file run raw `deref`/`offset` with no annotation, which the 4-2 vote already said must not happen." Concern: "The change that makes E0811 check bodies could land without the corpus and explain-text migration. Then `task ci` goes red, and someone "fixes" it by wrapping calls in an empty `ffi.scope()`."
  - **PLT:** A — "Only three syntactic forms open a region, and a closure keeps the region it is written in. Its parameter type `Ptr[U8]` then makes a `with_ptr` call outside a region an E0811, with no new rule. Option B opens a region based on which function the closure is passed to. That needs type resolution or a match on the method name. The first breaks the syntactic predicate and the second is unsound. B also fails when the closure is first bound with `let`." Concern: "Moving the five wrappers to `@trusted` could produce vague, shared audit records that do not state the real obligations (C does not write through a `with_ptr` pointer, and the length matches the buffer)."
  - **DevOps/Tooling:** A — "E0811 and `blink audit` share one syntactic predicate. A fourth region keyed on a method call breaks that predicate in both tools. Under A, every pin is inside a region the author wrote and has an audit record behind it, so the audit list of `byte-pin` sites is complete." Concern: "the corpus tests that call `with_ptr` from a plain `main()` and the E0814/E0815/E0817 explain texts must move to `@trusted` in the same change. If they do not, the gate goes red or the docs teach code that does not compile."
  - **AI/ML:** A — "A model learns one rule with no exception: "a Ptr appears only in a region." The region test stays syntactic, and the same predicate serves E0811 and `blink audit`. B would either make reading raw memory the easy path or add a special case that needs type information." Concern: "If the E0811 body rule lands before the five wrappers get `@trusted` and the corpus tests are migrated, std.libc breaks. Agents that read the spec would see it contradict the shipped code."
  - **Minimalism:** A — "A adds nothing. It uses the three-item list, closure inheritance and `@trusted` that already exist. B would add a region tied to a method name that only type resolution can identify. That breaks the shared syntactic check that E0811 and `blink audit` use, and it would let any user get a pointer without an audit record. Each future pinning API would also ask for its own region." Concern: "The migration is real work: five std wrappers, the corpus tests and the E0814/E0815/E0817 explain texts all need `@trusted`. If it is done in a hurry, someone may wrap code in an empty `ffi.scope()` block to make the error go away."

  - **Systems:** R-GEN — "In round 1 I asked for R-CALL, but a general rule is the better design. A special case for `with_ptr` would be one more exception to keep in sync with the code. Concern: ""Outermost" needs a precise definition: whether it means the outermost expression in the syntax tree or the first expression in source order.   - **Web/Scripting:** R-GEN — "Users get the outcome I asked for, one error for each mistake, and every `Ptr` site gets it, not only `with_ptr`. Concern: ""Outermost expression whose type holds a `Ptr`" may put the caret on the whole closure literal, not on `p`, so the label must still name the parameter, or users will not see why the closure is wrong."
  - **PLT:** R-GEN — "The count of reports follows from the typing rule. #### Moderator note: `libc.copy_to_buf` left out of the help list

Several panelists listed `libc.copy_to_buf` among the no-pointer fixes. §9.1.3.2 ties the `Buf[U8]` it returns to the innermost `ffi.scope`, so it needs the scope block that Q4 bans from the help line, and the same section keeps it for the sealed-`Buf` path only. The spec text names the curated `*_bytes` wrappers and `b.get(i)` as the no-pointer fixes and does not name `copy_to_buf`.

### Final Spec

```blink
@trusted(audit: "LIBC-WRITE")
pub fn write_bytes(fd: Int, data: Bytes) -> Result[Int, Errno] ! IO {
    // the closure inherits the region of the @trusted body
    let rc = data.with_ptr(fn(p) -> I64 { c_write(fd.to_i32(), p, data.len().to_u64()) })
    if rc < 0 {
        return Err(Errno(c_errno()))
    }
    Ok(rc)
}

fn peek(b: Bytes) -> U8 {
    b.with_ptr(fn(p) -> U8 { p.deref() })  // E0811: `p` is a Ptr[U8] outside every region
}
```

- **Q1 (6-0):** The region list stays at three. A `with_ptr` or `with_mut_ptr` closure is an ordinary closure literal: it inherits the region it is written in, or it has none. Outside a region its `Ptr[U8]` parameter is an E0811 site, named or `_`, so either pin is legal only inside a region. The five `std.libc` `*_bytes` wrappers become `@trusted(audit: K)` `pub fn`s, and each record states that C does not write through a `with_ptr` pointer and that the length matches the buffer. §9.1.3 points to §9.1.1 instead of stating the rule again.
- **Q2 (6-0):** One general E0811 rule: report once, at the outermost expression (by the syntax tree) whose type holds a `Ptr`. A function type whose parameter or return type holds a `Ptr` holds one. A site that gets its pointer from a reported site is not reported again; a separate source reports on its own. For a `with_ptr` closure outside a region the report is on the closure literal, with a label that names the parameter.
- **Q3 (5-1):** No row for `with_ptr` in the pointer-operation table.
- **Q4 (6-0 in Phase D, after 3-3 in Phase C):** The E0811 help puts the no-pointer fixes (a curated `*_bytes` wrapper, `b.get(i)`) before `@trusted`. `b.get(i)` shows only when a syntactic test is certain that `p` is only the receiver of `.deref()` or `.offset(i)` and is never a call argument. The help never suggests `with ffi.scope()`. Neither help line is machine-applicable. The spec fixes the order and these limits, not the words.
- **Spec text:** §9.1.1 (*FFI regions*, *One report per pointer source*, *E0811 help lines*), §9.1.3 (`with_ptr` text, Bridge Doctrine item 1, the `*_bytes` wrapper paragraph), §3.2.3 Bytes method table.
